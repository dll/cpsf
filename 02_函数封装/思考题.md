## 🤔 第1题：封装的"度"

**问题：**

有人说："函数封装越多越好，哪怕只有一行代码也要封装成函数。"

也有人说："过度封装反而不好，到处跳来跳去，看代码像走迷宫。"

你怎么看？**函数封装的"度"在哪里？** 什么时候该封装？什么时候不该封装？

---

## 🤔 第2题：全局变量 vs 函数参数

**问题：**

小明写代码时喜欢用全局变量，因为"不用传来传去，省事"。
比如余额 balance 就定义成全局变量，所有函数都能直接修改它。

小红说："不要用全局变量，应该用函数参数传递。"

请你分析一下：
1. 用全局变量有什么好处？有什么坏处？
2. 用函数参数传递有什么好处？有什么坏处？
3. 你更倾向哪种方式？为什么？
4. 什么情况下全局变量是合理的？

---

## 🤔 第3题：函数的"单一职责"

**问题：**

编程界有个原则叫"单一职责原则"——一个函数只做一件事。

但是现实中你可能会遇到这样的函数：

```c
// 这个函数做了几件事？
int login_and_show_menu_and_handle_choice(char *username) {
    // 1. 登录验证
    // 2. 显示主菜单
    // 3. 读取用户选择
    // 4. 处理选择
    // 5. 显示结果
    // ...
}
```

请思考：
1. 这样的"多功能函数"有什么问题？
2. "单一职责"中的"一件事"到底怎么定义？粒度多细才算"一件事"？
3. 如果一个函数只做一件事，那会不会函数太多，调用关系太复杂？
4. 你觉得怎么平衡"函数大小"和"函数数量"？

我们学了"函数封装"，下一阶段是"模块化编程"（把函数拆到多个文件）。

请你推演一下：

2. 把函数拆到多个文件里，能解决这些问题吗？
3. 拆到多个文件后，又会带来什么新问题？
4. 你觉得怎么解决这些新问题？（猜猜下一阶段会学什么？）

### 第1题：封装的"度"

- 封装的目的是**降低复杂度**，如果封装本身增加了复杂度，那就过度了
- 判断标准：这个函数的功能是不是**内聚**的？能不能用一句话说清楚它做什么？
- 经验法则：
  - 代码重复出现3次以上 → 考虑封装
  - 函数超过50行 → 考虑拆分
  - 函数名需要用"和"来描述（如"登录和显示菜单"） → 应该拆成两个

### 第2题：全局变量 vs 函数参数

- 全局变量好处：方便、不用传参、所有函数都能访问
- 全局变量坏处：
  - 谁都能改，出了bug不知道是谁改的
  - 函数之间隐式耦合（通过全局变量偷偷传递数据）
  - 不利于复用（函数依赖全局变量，拿到别的地方就用不了）
- 函数参数好处：显式、清晰、函数独立、易复用
- 函数参数坏处：参数多了写起来麻烦
- 什么时候用全局变量：真正"全局"的东西（比如配置项、只读的常量）

### 第3题：单一职责

- "一件事"的判断标准：能不能用一个动词+名词来准确描述这个函数？
  - ✅ deposit（存款）—— 一件事
  - ❌ deposit_and_show_balance（存款并显示余额）—— 两件事
- 函数太小太多的问题：调用链太深，追踪起来像走迷宫
- 平衡之道：
  - 高层函数要"抽象"（只描述做什么，不描述怎么做）
  - 底层函数要"具体"（具体实现细节）
  - 就像公司：CEO只说"提高利润"，部门经理想"怎么提高"，员工去具体做

### 第4题：函数的进化

- 单文件的问题：
  1. 文件太大，找东西费劲
  2. 多人协作容易冲突
  3. 代码复用不方便（要复用得把整个文件拷走）
  4. 编译慢（改一行要重新编译整个文件）
- 多文件能解决这些问题，但会带来新问题：
  1. 文件之间怎么联系？（函数声明放哪里？）
  2. 怎么避免重复定义？
  3. 编译的时候怎么把多个文件拼在一起？
- 下一阶段的答案：头文件（.h）+ 多文件编译
