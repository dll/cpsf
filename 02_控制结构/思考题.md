## 💭 题目1：为什么"三种基本结构"就够用了？

**问题**：我们学的顺序、分支、循环只有三种，可现实中的程序千变万化。为什么只用这三种结构，就能组合出任意复杂的程序？

**背景**：ATM 菜单里，三种结构并不是各管一段，而是层层套在一起：

```
main 函数
├── 顺序：定义变量、打印欢迎界面
└── while (running)              ← 最外层：循环
    ├── 顺序：显示菜单、读取输入
    └── switch (choice)          ← 循环里：分支
        ├── case 1：查询余额（顺序）
        ├── case 3：取款（再套 if-else 的更小分支）
        └── case 0：退出（running = 0，让循环条件变假）
```

**思考方向**：
- 三种结构各自解决什么问题？它们能互相替代吗？
- 嵌套（结构里面再放结构）为什么能产生"无限的表达力"？
- 如果去掉其中一种，程序还能写完吗？

**完整参考答案**：
关键在于**"少而够用 + 可以嵌套"**。

- 三种结构各司其职：顺序负责"一步步来"，分支负责"按条件选路"，循环负责"重复做"。
- 它们不能互相替代：分支和循环里，每一段内部仍然是顺序执行；循环要停下来，又常常依赖分支去改变条件（比如 `case 0` 把 `running` 设成 0）。
- 嵌套带来了无限组合：一个循环里能放分支，分支里能再放循环，循环里又能再放循环……就像乐高积木，块数很少，但搭出的造型无限。ATM 的程序骨架就是「循环套分支，分支里再套顺序」。

Böhm 和 Jacopini 在 1966 年用数学证明了：**任何程序都能只用顺序、分支、循环这三种结构表达出来**。所以现代语言都保留这三种结构——它们足够表达一切计算逻辑，又足够简单，这就是"结构化程序设计"的根基。

## 💭 题目2：case 穿透是 bug 还是特性？

**问题**：`switch` 语句中，如果某个 `case` 忘记写 `break`，会发生"case 穿透"——程序会从匹配的 `case` 开始，一直往下执行所有后续 `case`，直到遇到 `break` 或结束。

有人说这是设计缺陷（bug），有人说这是有意为之的特性（feature）。你怎么看？

**背景**：
```c
switch (x)
{
    case 1:
        printf("A");   // 没有 break！
    case 2:
        printf("B");
        break;
}
// 如果 x == 1，会输出 "AB" —— 穿透了！
```

**思考方向**：
- 为什么 C 语言要这么设计？
- 什么时候"穿透"反而有用？
- 现代编程语言（Java、C#、Go）是怎么处理的？

**完整参考答案**：这是一个有争议的话题，主流观点是——**这是 1970 年代遗留的设计，弊大于利**。

- 支持"特性"的理由：
  - 多个 `case` 可以共用同一段代码，比如 `case 1: case 2: case 3: 公共代码; break;`。
  - 某些状态机场景下，穿透能写出更简洁的代码。
- 支持"bug"的理由：
  - 绝大多数情况下，忘记写 `break` 都是程序员的疏忽，不是有意为之。
  - 穿透产生的 bug 非常隐蔽，很难调试——程序"看起来"进了正确的 `case`，却多做了后面的事。
  - 现代语言（Java、C#、Go、Swift）都已**禁止隐式穿透**，必须显式写 `break`。
- 结论：作为学习者，只要记住——**每个 `case` 后面都要加 `break`**，除非你非常明确地知道自己就是要穿透。

## 💭 题目3：循环靠什么结束？死循环是怎么来的？

**问题**：循环能一直转下去，也能突然停下来。它到底靠什么结束？"死循环"又是怎么产生的，怎么排查？

**背景**：ATM 的主循环是这样的：
```c
int running = 1;
while (running)          // 条件为真就一直转
{
    // ...
    // 用户选择"退出"时：
    running = 0;         // 循环条件由真变假，循环结束
}
```

**思考方向**：
- `while` 和 `for` 的"刹车"分别在哪儿？
- `for (int i = 0; i < 10; i++)` 里，如果忘写 `i++` 会怎样？
- `while (1)` 一定是 bug 吗？
- 怎么快速判断一个循环会不会停下来？

**完整参考答案**：循环唯一的"刹车"，就是**让循环条件最终从"真"变成"假"**。

- `while` 的刹车在条件本身：条件里的变量必须能被改变。ATM 靠 `running = 0` 结束循环。
- `for` 的刹车在"更新"这一步：`for (int i = 0; i < 10; i++)` 如果漏写 `i++`，`i` 永远小于 10，条件恒为真 → 死循环。同理，`while` 里忘了修改循环变量，也会死循环。
- 排查方法：**盯住"循环条件里的那个变量"，看它在循环体内到底有没有被改变**。如果一次都没变，基本就是死循环。
- `while (1)` 不一定是 bug：只要循环体里一定有 `break`、`return`，或某个能置条件为假的退出路径，它就是菜单类程序的惯用写法（"一直转，直到用户喊停"）。
- 所有 `for` 都能改写成 `while`，反之亦然：`for` 只是"初始化 + 条件 + 更新"三件套的语法糖。选哪个，看哪种更容易看懂——知道次数用 `for`，条件驱动用 `while`。

## 💭 题目4：结构化程序设计是谁提出来的？

**问题**：我们常说"顺序、分支、循环是程序的三种基本结构"，这句话最早是谁证明的？它和我们后面要学的函数、模块、架构，又有什么关系？

**思考方向**：
- Böhm-Jacopini 定理说的是什么？
- 为什么 `goto` 语句在历史上引发了那么大讨论？
- Dijkstra 的论文《Go To Statement Considered Harmful》核心观点是什么？
- 这个思想和"软件架构"有什么关联？

**完整参考答案**：

**Böhm-Jacopini 定理（1966 年）**：Corrado Böhm 和 Giuseppe Jacopini 两位数学家证明了——**任何复杂的程序，都可以只用顺序、分支、循环三种基本结构来表达**，不需要 `goto`。这是一个数学证明，不是经验总结，说明这三种结构是"图灵完备"的最小集合之一。

**Dijkstra 的论文（1968 年）**：Edsger Dijkstra 发表著名的《Go To Statement Considered Harmful》（《goto 语句有害论》），指出 `goto` 会让执行路径像"意大利面条"一样纠缠，难以理解和验证，从而推动了"结构化程序设计"的普及。

**与软件架构的关系**：
- 结构化程序设计是软件架构的思想源头之一。
- "不要用 `goto`"的本质，是"**代码的执行路径要清晰可控**"。
- 这个思想层层往上：函数是结构化的（每个函数一个入口、一个出口），模块是结构化的（接口清晰、职责单一），分层架构、插件框架，本质上都是在更高层次上做"结构化"——让系统的结构清晰可控。
- 所以本讲学的不只是三条语法，而是一种"把复杂系统拆成清晰结构"的思维方式，它会一直用到最后一讲的插件框架。
