## 💭 题目1：case 穿透是 bug 还是特性？

**问题**：`switch` 语句中，如果某个 `case` 忘记写 `break`，会发生"case穿透"——程序会继续执行下面所有的 `case`，直到遇到 `break` 或结束。

有人说这是设计缺陷（bug），有人说这是有意为之的特性（feature）。你怎么看？

**思考方向**：
- 为什么 C 语言要这么设计？
- 什么时候"穿透"反而有用？
- 现代编程语言（比如 Java、C#、Go）是怎么处理的？

## 💭 题目2：while 与 for 可以互相改写吗？

**问题**：`while` 循环和 `for` 循环本质上是一回事吗？

把下面的 `for` 循环改写成 `while` 循环：
```c
for (int i = 0; i < 10; i++)
{
    printf("%d ", i);
}
```

反过来，所有的 `while` 循环都能改写成 `for` 吗？

**思考方向**：
- 两种循环的本质区别是什么？
- 什么场景下必须用 `while`？
- 什么场景下 `for` 更清晰？

## 📖 参考答案

### 题目1：case 穿透是 bug 还是特性？

**参考答案**：这是一个有争议的话题，但主流观点认为——**这是一个历史遗留的设计，弊大于利**。

支持"特性"的理由：
- 多个 `case` 可以共用同一段代码（比如 `case 1: case 2: case 3: 共用代码; break;`）
- 某些状态机（state machine）场景下，穿透可以写出更简洁的代码

支持"bug"的理由：
- 99% 的情况下，忘记写 `break` 都是程序员的疏忽，不是有意为之
- 穿透导致的 bug 非常隐蔽，很难调试
- 现代语言（Java、C#、Go、Swift 等）都不允许穿透，必须显式写 `break`

**结论**：C 语言的 `switch` 设计于 1970 年代，当时的设计理念和现在不同。作为学习者，你只需要记住——**每个 case 后面加 break**，除非你明确知道自己在做什么。

### 题目2：while 与 for 可以互相改写吗？

**参考答案**：**可以，所有的 for 循环都能改写成 while，所有的 while 循环也都能改写成 for。**

上面的 for 循环改写成 while：
```c
int i = 0;
while (i < 10)
{
    printf("%d ", i);
    i++;
}
```

**本质区别**：没有本质区别，`for` 只是"初始化 + 条件 + 更新"三件套的语法糖。

**什么时候用哪个**：
- **知道循环次数** → 用 `for`（比如遍历数组、打印N次）
- **不知道循环次数** → 用 `while`（比如菜单循环、等待用户输入、读取文件直到结尾）
- **循环的核心是计数器** → 用 `for`
- **循环的核心是条件判断** → 用 `while`

选哪个的标准是：**哪种写法让代码更容易理解**。

### 题目3：不用函数，怎么减少代码重复？

**参考答案**：不用函数的话，确实有几种办法，但都有明显的缺点：

**方法1：宏定义（#define）**
```c
#define CHECK_AMOUNT(amt) if (amt <= 0) { printf("金额无效！"); continue; }
```
缺点：宏是纯文本替换，没有类型检查，容易出诡异的 bug，调试困难。

**方法2：goto 跳转到公共代码段**
```c
if (amount <= 0) goto error_invalid;
if (amount > balance) goto error_no_money;
// ... 正常逻辑
error_invalid:
    printf("金额无效！");
    goto end;
error_no_money:
    printf("余额不足！");
end:
```
缺点：`goto` 让代码的执行路径变得混乱，难以阅读和维护。这就是著名的"goto有害论"。

**方法3：精心组织代码结构**
- 把相似的代码写在一起，加注释标明
- 用统一的变量命名风格

缺点：只是"看起来整齐"，代码重复的问题根本没解决。

**结论**：这些方法都是"权宜之计"，**真正优雅的解决方案是——函数封装**。这正是我们下一讲的主题。函数就是专门为了解决"代码重复"和"代码组织"问题而发明的。

### 题目4：结构化程序设计是谁提出来的？

**参考答案**：

**Böhm-Jacopini 定理**（1966年）：Corrado Böhm 和 Giuseppe Jacopini 两位数学家证明了——**任何复杂的程序，都可以只用顺序、分支、循环三种基本结构来表达**，不需要 goto。

这是一个数学证明，不是经验总结。也就是说，这三种结构是"图灵完备"的最小集合之一。

**Dijkstra 的论文**（1968年）：Edsger Dijkstra 发表了著名的《Go To Statement Considered Harmful》（《goto语句是有害的》），引发了编程范式的大讨论，推动了"结构化程序设计"的普及。

**和软件架构的关系**：
- 结构化程序设计是软件架构的思想源头之一
- "不要用 goto" → 本质是"代码的执行路径要清晰可控"
- 这个思想层层往上：函数是结构化的，模块是结构化的，架构也是结构化的
- 我们后面要学的"分层架构"、"插件框架"，本质上都是在更高层次上做"结构化"——让系统的结构清晰可控
