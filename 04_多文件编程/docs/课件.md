## 一、为什么需要多文件？

### 1.1 第3讲的"痛"

第3讲我们用函数封装重构了 ATM，代码变得清爽了很多。但随着函数越来越多，新的问题出现了：

| 痛点 | 具体表现 |
|:---|:---|
| 文件太长 | 第3讲所有函数都在 `atm_func.c` 一个文件里，250+行起步，函数更多了怎么办？ |
| 全局变量太危险 | `g_balance` 是全局变量，所有函数都能直接改，改乱了找不到"凶手" |
| 不好复用 | 想把"菜单模块"拿到别的项目用？得从一大坨代码里抠出来 |
| 没法协作 | 两个人同时改一个文件？合并代码是噩梦 |

这就像一个**没有分区的衣柜**——所有衣服都堆在一起：
- 找一件外套，得翻遍整堆衣服
- 两件衣服缠在一起，扯一件带出三件
- 想给朋友几件衣服？只能整堆搬过去

### 1.2 多文件就是"给衣柜分区"

把代码按职责拆分到不同文件，就像给衣柜分区：
- 上衣放一层，裤子放一层，袜子放一层
- 找外套？直接去上衣区
- 借衣服给朋友？拿走上衣区就行
- 两个人同时整理？一个弄上衣，一个弄裤子，互不干扰

**多文件编程 = 按职责把代码分到不同文件，每个文件各管各的。**

### 1.3 拆分前后对比

| 对比项 | 第3讲（单文件） | 第4讲（多文件） |
|:---|:---|:---|
| 文件数量 | 1个 `.c` 文件 | 4个 `.c` + 3个 `.h` |
| 文件长度 | 250+行全部在一起 | 每个文件 50-80行，各管各的 |
| 余额可见性 | `g_balance` 全局可见 | `s_balance` 仅 account.c 可见 |
| 修改影响 | 改一处可能碰到不相关代码 | 改 menu.c 不影响 account.c |
| 复用性 | 抠函数复制粘贴 | 拿走 .c + .h 就能用 |
| 协作性 | 两人改一个文件 | 两人改不同文件 |

## 二、头文件与源文件

### 2.1 .h 和 .c 的分工

C语言的多文件编程有两类文件：

| 文件类型 | 内容 | 比喻 |
|:---:|:---|:---|
| 头文件(.h) | 函数声明、类型定义、宏定义 | **菜单**——告诉你有什么菜 |
| 源文件(.c) | 函数定义（具体实现代码） | **厨房**——菜是在这里做的 |

**头文件是接口，源文件是实现。**

其他文件要用某个模块的函数时，只需要 `#include` 头文件（看菜单点菜），不需要关心源文件里怎么实现的（不用进厨房）。

### 2.2 为什么不把声明和定义都放头文件里？

如果把函数定义（函数体）写在头文件里，然后这个头文件被多个 `.c` 文件 `#include`，编译时每个 `.c` 都会包含一份函数定义。链接时链接器发现"同一个函数被定义了多次"，就会报错：

```
error: multiple definition of `print_success'
```

所以规则是：
- **声明**放头文件（可以被多次包含，声明不冲突）
- **定义**放源文件（每个函数只定义一次）

### 2.3 我们的 ATM 拆成三个模块

```
src/
├── main.c        ← 主程序（入口）
├── menu.h        ← 菜单模块接口
├── menu.c        ← 菜单模块实现
├── account.h     ← 账户模块接口
├── account.c     ← 账户模块实现
├── utils.h       ← 工具模块接口
├── utils.c       ← 工具模块实现
└── build.bat     ← 编译脚本
```

**按什么原则拆分？** 按"单一职责"：
- **菜单模块**：负责和用户交互（显示菜单、读取输入）
- **账户模块**：负责业务逻辑（余额管理、存款、取款、转账）
- **工具模块**：负责通用功能（成功提示、错误提示）
- **main.c**：负责调度（调用各模块，串联流程）

## 三、头文件保护

### 3.1 为什么需要头文件保护？

`#include` 本质上是"把头文件内容复制粘贴到当前位置"。如果同一个头文件被间接包含多次，就会重复声明。

例如：
```c
/* menu.c */
#include "menu.h"    /* 包含了 menu.h */
#include "utils.h"    /* utils.h 里可能也包含了一些声明 */
/* 如果 menu.h 被间接包含了两次，里面的声明就会出现两遍 */
```

虽然函数声明重复一般不报错，但**类型定义、宏定义重复**就会报错。

### 3.2 头文件保护的标准写法

每个头文件都要加"保护伞"：

```c
#ifndef MENU_H      /* 如果没有定义 MENU_H */
#define MENU_H      /* 就定义它 */

/* ... 头文件内容 ... */

#endif /* MENU_H */  /* 保护结束 */
```

**原理**：
1. 第一次包含 `menu.h` 时，`MENU_H` 未定义 → 执行 `#define MENU_H`，然后处理头文件内容
2. 第二次包含 `menu.h` 时，`MENU_H` 已定义 → `#ifndef` 为假 → 整个内容被跳过

就像一道"一次性门"——第一次打开后锁上，后面再推就推不动了。保证内容只被处理一次。

### 3.3 命名规范

保护宏的名字通常用 **文件名大写 + 下划线**：
- `menu.h` → `MENU_H`
- `account.h` → `ACCOUNT_H`
- `utils.h` → `UTILS_H`

要确保整个项目中不重名，否则两个头文件用同一个宏名，后一个会被错误跳过。

## 四、static 关键字的两种用法

`static` 是 C 语言中含义最丰富的关键字之一，它在不同位置有完全不同的作用。

### 4.1 用法一：函数内的 static（函数级 static）

```c
void counter(void)
{
    static int count = 0;   /* 函数级 static 变量 */
    count++;
    printf("调用次数：%d\n", count);
}
```

**特点**：
- 变量存放在全局数据区（不在栈上），程序结束才销毁
- **只初始化一次**——第一次调用时初始化，之后保持上次的值
- 但作用域仍然限于函数内部——函数外面看不到它

```c
counter();   /* 输出：调用次数：1 */
counter();   /* 输出：调用次数：2 */
counter();   /* 输出：调用次数：3 */
```

**比喻**：就像一个计数器本子，每次翻开（调用函数）就在上次的数字上加1，合上（函数结束）数字不丢。

### 4.2 用法二：文件级的 static（修饰全局变量或函数）

```c
/* account.c */
static double s_balance = 1000.0;      /* 文件级 static 变量 */
static int validate_amount(double amt);  /* 文件级 static 函数 */
```

**特点**：
- 限制了可见范围——只在本 `.c` 文件内可见
- 其他文件即使 `extern` 声明也访问不到
- 普通全局变量是"全程序可见"，static 全局变量是"仅本文件可见"

**这正是我们在第4讲用到的**：把 `s_balance` 从"全局可见"变成"仅 account.c 可见"。

### 4.3 两种用法的对比

| 对比项 | 函数级 static | 文件级 static |
|:---|:---|:---|
| 修饰对象 | 函数内的局部变量 | 全局变量、函数 |
| 生命周期 | 程序结束才销毁 | 程序结束才销毁 |
| 作用域 | 仅限本函数内 | 仅限本文件内 |
| 核心价值 | 保持状态（跨调用记住值） | 信息隐藏（缩小可见范围） |
| 比喻 | 计数器本子（记住上次的值） | 私有房间（外人进不来） |

### 4.4 从第3讲到第4讲的变化

```c
/* 第3讲：全局变量——全程序可见，谁都能改 */
double g_balance = 1000.0;

/* 第4讲：文件级 static——仅 account.c 可见，安全 */
static double s_balance = 1000.0;
```

这就是**把全局变量关进笼子**——缩小可见范围，降低风险。

外部想查余额？只能通过 `account_get_balance()` 函数。
外部想改余额？只能通过 `account_deposit()` / `account_withdraw()` 函数。

这就是"信息隐藏"——数据私有化，只暴露操作接口。就像银行金库，你不能自己进去拿钱，得通过柜员。

## 五、多文件编译过程

### 5.1 从源文件到可执行文件

单文件编译：`gcc main.c -o program`

多文件编译：`gcc main.c menu.c account.c utils.c -o atm_multi.exe`

表面上只是多列了几个文件名，但背后发生了什么？

### 5.2 编译四阶段（回顾第1讲，深入理解）

```
源文件(.c)  →  预处理  →  编译  →  汇编  →  目标文件(.o)  →  链接  →  可执行文件(.exe)
```

以我们的 ATM 项目为例：

**第1步：预处理（Preprocess）**
- 处理 `#include`：把头文件内容粘贴到源文件里
- 处理 `#ifndef` / `#define`：执行头文件保护逻辑
- 处理 `#define` 宏：文本替换
- 每个 `.c` 文件独立预处理

**第2步：编译（Compile）**
- 语法分析、语义分析
- 检查函数声明是否存在、参数是否匹配
- 生成汇编代码
- **注意**：编译器只看得到声明（来自头文件），不需要看到定义

**第3步：汇编（Assemble）**
- 把汇编代码转成机器码
- 生成目标文件（`.o` 或 `.obj`）
- 每个 `.c` 生成一个 `.o`

```
main.c    →  预处理  →  编译  →  汇编  →  main.o
menu.c    →  预处理  →  编译  →  汇编  →  menu.o
account.c →  预处理  →  编译  →  汇编  →  account.o
utils.c   →  预处理  →  编译  →  汇编  →  utils.o
```

**第4步：链接（Link）**
- 把多个目标文件（`.o`）拼在一起
- **解决外部引用**：main.o 里调用了 `show_menu()`，但不知道它在哪；链接器在 menu.o 里找到了它的定义，把两者关联起来
- 生成最终的可执行文件

```
main.o + menu.o + account.o + utils.o  →  链接器  →  atm_multi.exe
```

### 5.3 编译器和链接器各做了什么？

| 角色 | 做什么 | 不做什么 |
|:---|:---|:---|
| 编译器 | 逐文件编译，检查语法、类型、声明是否存在 | 不负责找函数定义在哪 |
| 链接器 | 把多个目标文件拼起来，解决"谁调用谁"的地址问题 | 不检查语法 |

**关键理解**：编译器在编译 `main.c` 时，看到 `show_menu()` 调用，它检查的是"有没有这个函数的声明"（来自 `menu.h`）。至于 `show_menu()` 的定义在 `menu.c` 里——编译器不在乎，那是链接器的活。

这就是为什么**头文件（声明）和源文件（定义）可以分开**：编译器靠声明就能编译，链接器负责把定义找出来拼上。

### 5.4 常见编译/链接错误

| 错误 | 阶段 | 原因 |
|:---|:---|:---|
| `undeclared identifier` | 编译阶段 | 忘了 `#include` 头文件，或声明写错了 |
| `multiple definition` | 链接阶段 | 同一个函数在多个 `.c` 里都定义了（定义不该放头文件） |
| `undefined reference` | 链接阶段 | 声明了函数但没提供定义（忘了编译某个 `.c` 文件） |

## 六、接口与实现分离

### 6.1 什么是接口？什么是实现？

- **接口（Interface）** = 告诉外部"能做什么"——函数声明（头文件）
- **实现（Implementation）** = 告诉内部"怎么做"——函数定义（源文件）

以账户模块为例：

```
account.h（接口）             account.c（实现）
┌──────────────────┐         ┌──────────────────────┐
│ account_query()  │         │ void account_query() │
│ account_deposit()│  ←──→  │ { 具体代码... }       │
│ account_withdraw()│        │                      │
│ ...              │         │ static s_balance     │
│                  │         │ static validate...   │
└──────────────────┘         └──────────────────────┘
     菜单（对外）               厨房（对内）
```

外部（main.c）只需要看 `account.h`（接口），就知道"能查余额、能存款、能取款"。至于余额怎么存的、怎么验证的——那是 `account.c`（实现）的事。

### 6.2 好处是什么？

**好处1：实现可以随时换**

比如以后余额从单个变量改成数组存多个账户：
```c
/* 旧实现：单账户 */
static double s_balance = 1000.0;

/* 新实现：多账户（未来） */
static double s_balances[100];
static int s_count = 0;
```

只要 `account.h` 里的函数签名不变，`main.c` 一行都不用改。这就是接口不变、实现可换。

**好处2：降低耦合**

`main.c` 不依赖 `account.c` 的具体实现，只依赖 `account.h` 的接口。改 `account.c` 不影响 `main.c`，反之亦然。

**好处3：团队协作**

张三负责 `account.c`，李四负责 `menu.c`。只要双方遵守头文件的接口约定，互不影响。张三改了存款逻辑，李四的菜单代码不用改。

### 6.3 从函数到模块到库——封装的演进

```
第3讲：函数封装     → 把代码片段打包、命名、隐藏细节
第4讲：模块封装     → 把一组相关函数打包成文件，头文件是接口
第9讲：库封装       → 把模块编译成库文件，只暴露头文件
第12讲：框架封装    → 把整个系统的骨架封装起来，只留插件接口
```

每一步都是在更高层次上做"接口与实现分离"。第4讲是这条路上的关键一步——从函数级的封装提升到模块级的封装。

## 七、ATM 多文件项目实战

### 7.1 项目结构

```
src/
├── main.c         主程序：main函数，调度各模块
├── menu.h / .c    菜单模块：show_welcome, show_menu, read_choice
├── account.h / .c 账户模块：query, deposit, withdraw, transfer, get_balance
├── utils.h / .c   工具模块：print_success, print_error
└── build.bat      编译脚本：gcc main.c menu.c account.c utils.c -o atm_multi.exe
```

### 7.2 关键设计决策

**决策1：余额用 static 藏在 account.c**

```c
/* account.c 内部 */
static double s_balance = 1000.0;   /* 外部看不到，改不了 */
```

外部只能通过接口函数间接操作：
- 查余额 → `account_get_balance()`
- 存款 → `account_deposit()`
- 取款 → `account_withdraw()`

**决策2：验证函数也用 static**

```c
/* account.c 内部 */
static int validate_amount(double amount);   /* 内部助手，外部不可见 */
```

金额验证是内部实现细节，不需要暴露给外部。

**决策3：print_success 改为传参接收余额**

```c
/* 第3讲：直接访问全局变量 */
void print_success(char* op, double amount)
{
    printf("...当前余额：%.2f\n", g_balance);   /* 直接访问全局变量 */
}

/* 第4讲：通过参数传入 */
void print_success(const char* op, double amount, double balance)
{
    printf("...当前余额：%.2f\n", balance);      /* 通过参数获取 */
}
```

第4讲余额藏在 account.c 里，utils.c 看不到，所以改为通过参数传入。这降低了模块间的耦合——utils 模块不需要知道余额从哪来。

### 7.3 模块依赖关系

```
main.c
  ├── #include "menu.h"     → 调用 show_welcome, show_menu, read_choice
  ├── #include "account.h"  → 调用 account_query, account_deposit, ...
  └── #include "utils.h"    → 调用 print_error

account.c
  ├── #include "account.h"  → 自己的接口
  └── #include "utils.h"    → 调用 print_success, print_error

menu.c
  └── #include "menu.h"     → 自己的接口

utils.c
  └── #include "utils.h"    → 自己的接口
```

注意：`account.c` 依赖 `utils.h`（因为存款/取款要打印提示），但 `utils.c` 不依赖 `account.h`（工具函数不需要知道账户的事）。这是单向依赖，不是循环依赖。

### 7.4 编译与运行

```bash
# 编译
gcc main.c menu.c account.c utils.c -o atm_multi.exe -Wall

# 运行
./atm_multi.exe
```

也可以分步编译：
```bash
# 先编译成目标文件（不链接）
gcc -c main.c      → main.o
gcc -c menu.c      → menu.o
gcc -c account.c   → account.o
gcc -c utils.c     → utils.o

# 再链接
gcc main.o menu.o account.o utils.o -o atm_multi.exe
```

分步编译的好处：改了 `menu.c` 只需重新编译 `menu.o` 再链接，其他文件不用重新编译。大型项目中这能节省大量时间——这就是 Makefile 的原理。

## 🎯 本讲在主线上的位置

> 全系列统一叙事：**表达式 → 函数 → 模块 → 库 → 插件 → 框架**，六级台阶，一级比一级抽象。

```
① 表达式 ──── 第1讲 ✅   把字打到屏幕上
② 函数   ──── 第3讲 ✅   给代码起名字、打包、复用
③ 模块   ──── 第4讲 ⭐   ← 你在这里：接口与实现第一次真正分家
④ 库     ──── 第9-10讲   模块编译成二进制，跨项目复用
⑤ 插件   ──── 第11-12讲  运行时按需加载，统一接口
⑥ 框架   ──── 第13-14讲  框架反过来调用你写的代码
```

**本讲为终点贡献了什么**

| 本讲做到的 | 后面靠它长出来的 |
|:---|:---|
| 头文件当接口、源文件当实现 | 静态库（第9讲）：只发 `.h` + `.a`，实现彻底藏起来 |
| `static` 把数据关进笼子 | 信息隐藏（第12-13讲）：插件内部状态外部碰不到 |
| 编译单元可单独编译、链接器跨文件接线 | 动态库与运行时加载（第10-11讲）：链接时机往后挪 |
| 模块间单向依赖、松耦合 | 插件框架（第13讲）：主程序只依赖接口，不依赖具体插件 |

**一句话**：模块是"接口与实现分离"第一次真正落地——库、插件、框架，都从这条分界线长出来。

## 💭 思考题

### 题目1
为什么头文件需要 `#ifndef` / `#define` / `#endif` 保护？不加会怎样？

<details>
<summary>参考答案</summary>

`#include` 的本质是"把头文件内容复制粘贴到当前位置"。如果不加保护，同一个头文件被间接包含多次（比如 A.h 包含了 B.h，而 C.c 同时包含了 A.h 和 B.h），头文件内容就会出现多份。

对于函数声明，重复声明一般不报错。但对于**类型定义（struct/enum）、宏定义**，重复定义会导致编译错误。

加了 `#ifndef` 保护后，第一次包含时处理内容并定义宏，后续包含时宏已定义，内容被跳过，保证只处理一次。
</details>

### 题目2
`static` 在函数内部和文件级别分别是什么意思？有什么区别？

<details>
<summary>参考答案</summary>

**函数级 static**（修饰函数内的局部变量）：
- 变量的生命周期延长到程序结束（不随函数返回而销毁）
- 只初始化一次，后续调用保持上次的值
- 作用域仍限于函数内部
- 核心价值：跨函数调用保持状态（如计数器）

**文件级 static**（修饰全局变量或函数）：
- 限制可见范围到本文件内
- 其他文件无法通过 `extern` 访问
- 核心价值：信息隐藏（缩小可见范围，防止外部直接修改）

两者的共同点：生命周期都是整个程序运行期。区别在于用途——一个是为了"记住状态"，一个是为了"藏起来"。
</details>

### 题目3
多文件编译时，编译器和链接器各自做了什么？为什么需要链接器？

<details>
<summary>参考答案</summary>

**编译器**逐文件编译，每个 `.c` 文件独立处理：
- 预处理（展开 `#include`、执行宏替换）
- 语法分析、类型检查
- 生成汇编代码 → 汇编成目标文件（`.o`）
- 编译器只需要函数声明（来自头文件）就能编译，不关心定义在哪

**链接器**把多个目标文件拼成可执行文件：
- 解决外部引用——`main.o` 调用了 `show_menu()`，链接器在 `menu.o` 里找到定义并关联地址
- 合并全局符号表
- 生成最终可执行文件

为什么需要链接器？因为编译器一次只看一个文件。`main.c` 编译时知道 `show_menu()` 的声明（来自 `menu.h`），但不知道它的定义在 `menu.c` 里。链接器负责跨文件"接线"——把调用和定义连起来。
</details>

### 题目4
"接口与实现分离"是什么意思？这样做有什么好处？

<details>
<summary>参考答案</summary>

"接口与实现分离"是指：对外只暴露"能做什么"（接口/头文件/声明），内部"怎么做"藏在实现里（源文件/定义）。

好处：
1. **实现可替换**——只要接口不变，实现可以随时换（如余额从变量改成数组），调用者不受影响
2. **降低耦合**——调用者只依赖接口，不依赖实现。改实现不影响调用者，反之亦然
3. **团队协作**——多人各自负责不同模块，遵守接口约定即可，互不干扰
4. **编译隔离**——改了实现只需要重新编译该模块的 `.c`，其他文件不用重新编译
5. **信息隐藏**——内部细节（如 static 变量、static 函数）不暴露给外部，更安全

这是软件工程最重要的设计原则之一，从函数到模块到库到框架，每一层都在做"接口与实现分离"。
</details>
