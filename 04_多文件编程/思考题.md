## 📖 参考答案

### 题目1：为什么需要头文件保护？

**参考答案**：

`#include` 的本质是**文本复制粘贴**——预处理器把头文件的完整内容原封不动地插入到 `#include` 的位置。

**不加保护的后果**：

如果一个头文件被间接包含多次（很常见），内容就会出现多份。

- **函数声明重复**：一般不报错（C语言允许重复声明），但浪费预处理时间。
- **类型定义重复**：直接报错！

```c
/* 例：不加保护就出错 */
/* animal.h（假设没加保护） */
struct Animal { int age; };

/* dog.h */
#include "animal.h"   /* 第一次粘贴 struct Animal */

/* main.c */
#include "animal.h"    /* 第二次粘贴 struct Animal */
#include "dog.h"       /* dog.h 里又包含了 animal.h → 第三次！ */
/* 报错：redefinition of 'struct Animal' */
```

**加了保护后**：
1. 第一次包含 `animal.h` → `ANIMAL_H` 未定义 → 处理内容并定义 `ANIMAL_H`
2. 后续再包含 `animal.h` → `ANIMAL_H` 已定义 → `#ifndef` 为假 → 整个内容跳过

所以头文件保护是"一次性门"——保证内容只被处理一次，无论被包含多少次。

### 题目2：static 在函数内和文件内的区别

**参考答案**：

**函数级 static**（写在函数内部）：

```c
void counter(void) {
    static int count = 0;   /* 只初始化一次 */
    count++;
    printf("%d\n", count);
}
/* 每次调用，count 保持上次的值，不会重置 */
```

- 生命周期：程序开始到结束（存在全局数据区，不在栈上）
- 作用域：仅限本函数内部
- 核心价值：**保持状态**——跨调用记住值（比喻：计数器本子，翻页加1，合上不丢）

**文件级 static**（写在函数外面）：

```c
/* account.c */
static double s_balance = 1000.0;          /* 仅 account.c 可见 */
static int validate_amount(double amt);     /* 仅 account.c 可调用 */
```

- 生命周期：程序开始到结束
- 作用域：仅限本文件内
- 核心价值：**信息隐藏**——缩小可见范围（比喻：私有房间，外人进不来）

**关键区别**：

| 对比项 | 函数级 static | 文件级 static |
|:---|:---|:---|
| 位置 | 函数内部 | 函数外部（文件级） |
| 生命周期 | 程序结束才销毁 | 程序结束才销毁 |
| 作用域 | 仅本函数 | 仅本文件 |
| 价值 | 保持状态 | 信息隐藏 |

第3讲的 `g_balance`（非 static 全局变量）全程序可见，谁都能改；第4讲的 `s_balance`（static 全局变量）仅 account.c 可见，安全得多。差一个 `static`，差在可见范围。

### 题目3：多文件编译时，编译器和链接器各自做了什么？

**参考答案**：

**编译器**（每个 `.c` 文件独立编译）：

1. 预处理：展开 `#include`（把头文件内容粘贴进来）、处理 `#ifndef` 等条件编译、执行宏替换
2. 编译：语法分析、类型检查、生成汇编代码
3. 汇编：汇编代码 → 机器码 → 目标文件（`.o`）

关键点：编译器在编译 `main.c` 时，看到 `show_menu()` 调用，它**不关心** `show_menu` 的定义在哪个文件里。它只需要检查"有没有 `show_menu` 的声明"（来自 `#include "menu.h"`）。有声明就通过，生成一个"待链接"的调用标记。

**链接器**（把多个 `.o` 拼成 `.exe`）：

1. 收集所有目标文件（`main.o`, `menu.o`, `account.o`, `utils.o`）
2. 建立符号表：记录每个函数/变量的定义在哪个 `.o` 里
3. 解决外部引用：`main.o` 里有个"待链接"的 `show_menu` 调用 → 在 `menu.o` 里找到定义 → 把调用地址填上
4. 生成可执行文件

**如果忘了把 `menu.c` 加到 gcc 命令行**：
- 编译阶段：`main.c` 能编译通过（有 `menu.h` 的声明就够了）
- 链接阶段：报错 `undefined reference to 'show_menu'`——链接器找不到定义！

所以 `undefined reference` 是**链接错误**，不是编译错误。编译只看声明，链接才找定义。

### 题目4：接口与实现分离的好处

**参考答案**：

"接口与实现分离"是指：对外只暴露"能做什么"（接口=头文件=声明），内部"怎么做"藏在实现里（源文件=定义）。外部依赖接口，不依赖实现。

**好处1：实现可替换**

例如账户模块的余额存储方式从单变量改成数组：
```c
/* 旧实现（第4讲） */
static double s_balance = 1000.0;

/* 未来实现（多账户） */
static double s_balances[100];
static int s_account_count = 0;
```
只要 `account.h` 的函数签名不变（`account_query()`, `account_deposit()` 等），`main.c` 一行都不用改。

**好处2：降低耦合**

`main.c` 依赖 `account.h`（接口），不依赖 `account.c`（实现）。改 `account.c` 不影响 `main.c`，改 `main.c` 也不影响 `account.c`。模块之间通过接口松耦合。

**好处3：团队协作**

张三负责 `account.c`，李四负责 `menu.c`。双方只需遵守 `account.h` / `menu.h` 的接口约定，互不影响。张三重构存款逻辑，李四的菜单代码不用改。

**好处4：信息隐藏**

`account.c` 内部的 `s_balance` 和 `validate_amount` 用 static 藏起来，外部看不到、碰不到。外部只能通过公开的接口操作——这就是封装的精髓。

**好处5：编译隔离**

改了 `account.c` 的实现，只需要重新编译 `account.o` 再链接。其他 `.o` 文件不用重新编译。大型项目中这能大幅节省编译时间。

**生活中的例子**：你用 `printf` 时需要知道它内部怎么把字符显示到屏幕上吗？不需要。你只需要知道接口——传一个格式字符串，它就打印。如果哪天 printf 内部换了实现（比如从缓冲IO改成直接系统调用），你的代码需要改吗？不需要——因为接口没变。这就是接口与实现分离的力量。
