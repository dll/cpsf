## 一、从多文件到静态库

### 1.1 第4讲的"痛"

第4讲我们把 ATM 拆成了多个文件，用头文件分离接口和实现。但有个问题：

```bash
# 每次修改主程序，都要把所有源文件重新编译
gcc main.c menu.c account.c utils.c -o atm.exe
```

| 痛点 | 具体表现 |
|:---|:---|
| 重复编译 | account.c 没改过，也要重新编译，浪费时间 |
| 不便分发 | 想给别人用账户模块，要给一堆 .c 源文件 |
| 命令冗长 | 文件越多，gcc 后面跟的文件名越多 |
| 无法保密 | 给源码 = 给全部实现细节 |

### 1.2 静态库就是"代码工具箱"

**静态库 = 把多个目标文件(.o)打包成一个归档文件(.a/.lib)**

就像把散落的工具收进一个工具箱：
- 打包前：account.o、transaction.o 散落各处
- 打包后：libaccount.a 一个文件搞定
- 谁要用？`#include` 头文件 + 链接库就行
- 不用给源码，只给 .a + .h 即可——**保护知识产权**

### 1.3 多文件 vs 静态库

| 对比项 | 第4讲（多文件） | 第9讲（静态库） |
|:---|:---|:---|
| 源文件分发 | 要给所有 .c 文件 | 只给 .a + .h |
| 编译方式 | 每次编译所有 .c | 库预编译好，只编译 main.c |
| 命令 | `gcc main.c a.c b.c -o exe` | `gcc main.c -L. -laccount -o exe` |
| 代码保护 | 源码全部暴露 | 只暴露接口，实现藏在 .a 里 |
| 链接方式 | 所有 .o 拼在一起 | 从 .a 中复制需要的代码 |

## 二、ar 工具详解

### 2.1 创建静态库的命令

```bash
ar rcs libaccount.a account.o transaction.o
```

**三个参数的含义**：

| 参数 | 全称 | 作用 |
|:---:|:---|:---|
| r | replace | 将目标文件插入归档，已存在则替换 |
| c | create | 静默创建归档文件（不存在时不报警告） |
| s | symbol | 建立符号索引表（加速链接器查找） |

**命名规则**：`lib` + `名字` + `.a`，比如 `libaccount.a`。链接时用 `-laccount`，gcc 会自动找 `libaccount.a`。

### 2.2 查看静态库内容

```bash
# 列出库中的目标文件
ar t libaccount.a
# 输出：
# account.o
# transaction.o

# 查看符号表（库中导出了哪些函数）
nm libaccount.a
# 输出类似：
# account.o:
# 00000000 T account_create
# 00000000 T account_deposit
# 00000000 T account_find
# ...
# transaction.o:
# 00000000 T transaction_deposit
# 00000000 T transaction_transfer
# ...
```

### 2.3 静态库的内部结构

```
libaccount.a （归档文件）
┌──────────────────────────────────┐
│  归档头信息                       │
├──────────────────────────────────┤
│  account.o  (目标文件)            │
│  ├─ account_create 函数代码       │
│  ├─ account_deposit 函数代码      │
│  ├─ account_withdraw 函数代码     │
│  ├─ account_find 函数代码         │
│  └─ static 变量数据               │
├──────────────────────────────────┤
│  transaction.o (目标文件)         │
│  ├─ transaction_deposit 函数代码  │
│  ├─ transaction_withdraw 函数代码 │
│  ├─ transaction_transfer 函数代码 │
│  ├─ transaction_print_history     │
│  └─ log_transaction (static函数) │
├──────────────────────────────────┤
│  符号索引表 (ar s 生成)           │
│  account_create -> account.o偏移  │
│  transaction_deposit -> ...        │
└──────────────────────────────────┘
```

## 三、静态链接原理

### 3.1 链接器的工作流程

```
            main.o                    libaccount.a
        ┌──────────┐              ┌──────────────┐
        │ main()   │              │ account.o    │
        │ 调用了     │  链接器       │  account_create() │
        │ account_  │──查找符号──> │  account_deposit() │
        │ create()  │              │  ...         │
        │ account_  │              │ transaction.o│
        │ deposit() │              │  transaction_  │
        └──────────┘              │  deposit()   │
              │                    │  ...         │
              │  复制代码           └──────────────┘
              ▼                          │
        ┌──────────────────────────────────┐
        │  atm_static (可执行文件)          │
        │  ├─ main()        (来自main.o)   │
        │  ├─ account_create()  (从库复制) │
        │  ├─ account_deposit() (从库复制) │
        │  ├─ transaction_deposit()        │
        │  └─ ... 其他需要的函数           │
        └──────────────────────────────────┘
```

**关键理解**：链接器不是把整个库都塞进可执行文件！它只会从库中**提取被用到的函数**，复制到可执行文件中。没用到的函数不会包含。

### 3.2 静态链接的"代码复制"

```
程序A  ──链接──> libaccount.a  ──复制account_create代码──> 程序A.exe (含account_create)
程序B  ──链接──> libaccount.a  ──复制account_create代码──> 程序B.exe (含account_create)
程序C  ──链接──> libaccount.a  ──复制account_create代码──> 程序C.exe (含account_create)

磁盘上有3份 account_create 的副本！
内存中运行时也有3份！
```

这就是"静态"的含义——**链接时就把代码固定复制进去了**，运行时不再需要库文件。

### 3.3 与第4讲多文件编译的对比

| 阶段 | 第4讲（多文件编译） | 第9讲（静态库） |
|:---|:---|:---|
| 编译 | 所有 .c 都要编译 | 库的 .c 预编译好了 |
| 链接 | 所有 .o 直接拼接 | 从 .a 中提取需要的 .o |
| 结果 | 一个 exe | 一个 exe（一样） |
| 区别 | 编译时需要所有源码 | 编译时只需 main.c + .a + .h |

### 4.2 构建流程（四步）

```
第1步：编译目标文件
  gcc -c account.c       →  account.o
  gcc -c transaction.c   →  transaction.o

第2步：打包静态库
  ar rcs libaccount.a account.o transaction.o

第3步：编译主程序
  gcc -c main.c           →  main.o

第4步：链接可执行文件
  gcc -o atm_static main.o -L. -laccount
                              ↑      ↑
                         库目录   库名(自动加lib前缀和.a后缀)
```

```
  └──────────┬──────────────────┘
             │ 链接时从 libaccount.a 提取代码

  ┌──────────────────────────────┐

  │  │  - account_get_balance │  │
  │  │  - account_list_all()  │  │
  │  │  (static: accounts[])  │  │
  │  └────────────────────────┘  │
  │  ┌────────────────────────┐  │
  │  │   transaction.o       │  │

  │  │  - transaction_withdraw│  │
  │  │  - transaction_transfer│  │
  │  │  - transaction_print   │  │
  │  │  (static: log_trans)   │  │
  │  └────────────────────────┘  │
  └──────────────────────────────┘
```

### 4.4 关键代码片段

**创建静态库（Makefile 核心部分）**：
```makefile
# 编译目标文件
account.o: account.c account.h
	gcc -Wall -c account.c -o account.o

transaction.o: transaction.c transaction.h
	gcc -Wall -c transaction.c -o transaction.o

# 用 ar 打包静态库
libaccount.a: account.o transaction.o
	ar rcs libaccount.a account.o transaction.o

# 链接可执行文件（-L. 指定库目录，-laccount 指定库名）
atm_static: main.o libaccount.a
	gcc -o atm_static main.o -L. -laccount
```

**主程序使用（main.c）**：
```c
/* 只需要头文件，不需要源码 */
#include "account.h"
#include "transaction.h"

int main(void) {
    /* 直接调用库中的函数 */
    int id = account_create("张三", 1000.0);
    transaction_deposit(id, 500.0);
    account_list_all();
    return 0;
}
```

## 五、优缺点分析

### 5.1 静态库的优点

| 优点 | 说明 |
|:---|:---|
| 执行速度快 | 代码直接嵌入可执行文件，运行时无加载开销 |
| 部署简单 | 一个可执行文件走天下，不依赖外部库 |
| 兼容性好 | 不怕目标机器缺少某个库版本 |
| 知识产权保护 | 只给 .a + .h，不给 .c 源码 |

### 5.2 静态库的缺点

| 缺点 | 说明 |
|:---|:---|
| 体积大 | 每个程序都复制一份库代码，磁盘占用大 |
| 内存浪费 | 多个程序运行时，内存中有多份相同代码 |
| 更新麻烦 | 库修了 bug，所有用到的程序都要重新链接 |
| 无法热更新 | 程序运行中不能换库的代码 |

### 5.3 使用场景

- **适合**：小型项目、嵌入式系统、对性能要求极高的场景
- **不适合**：大型系统、库频繁更新、多程序共享同一库

整条主线是**六级台阶**：表达式 → 函数 → 模块 → 库 → 插件 → 框架。

| 台阶 | 讲次 | 解决的问题 |
|:---:|:---|:---|
| ① 表达式 | 第1讲 ✅ | 算出值 |
| ② 函数 | 第3讲 ✅ | 把一段逻辑封成一个名字 |
| ③ 模块 | 第4讲 ✅ | 接口与实现分家 |
| **④ 库** | **第9讲 ← 本讲** | **把编译好的二进制当零件复用** |
| ⑤ 插件 | 第11~12讲 | 运行时按需加载、统一接口 |
| ⑥ 框架 | 第13讲 | 框架反过来调用你的代码 |

**本讲为终点贡献了什么**

- 复用的单位，从"源码"升级为"二进制"：`libaccount.a` 里装的是编好的 `.o`，交付时只给 `.a` + `.h`。
- 接口与实现第一次真正分离：界面（`nm` 里的 `T` 符号）露在外面，实现（`static` 数据与函数体）锁在库里。
- 掌握了 C 语言代码复用的基础技能：`gcc -c` → `ar rcs` → `-L. -laccount`。

**但本讲也留下一个硬伤**

静态链接把代码**复制**进每个可执行文件——3 个程序就有 3 份副本，磁盘浪费、内存重复、库修 bug 还要全部重链。
"每个程序复制一份"正是**第10讲动态库**要解决的问题：让多个程序共享同一份代码，从**复制**走向**共享**。

## 💭 思考题

### 题目1
如果有3个程序都链接了 libaccount.a，磁盘上有几份 account_create 函数的代码副本？内存中运行时呢？

<details>
<summary>参考答案</summary>

磁盘上有3份。每个程序的可执行文件中都复制了一份 account_create 的机器码。

内存中如果3个程序同时运行，也有3份 account_create 的代码加载到各自的进程地址空间。

这就是静态库"代码复制"的本质——每个程序自带一份。如果有10个程序用同一个库，就有10份副本。这就是下一讲动态库要解决的问题。
</details>

### 题目2
ar 命令的三个参数 r、c、s 分别是什么意思？如果不加 s 参数会怎样？

<details>
<summary>参考答案</summary>

- r (replace)：将目标文件插入归档，已存在则替换
- c (create)：静默创建归档文件
- s (symbol)：建立符号索引表

如果不加 s，归档文件不会包含符号索引表。链接器在查找符号时需要遍历所有目标文件，效率会降低。某些链接器甚至会报错 "no symbol table"。加 s 相当于运行 ranlib，让链接器能快速通过索引定位符号所在的目标文件。
</details>

### 题目3
静态链接时，链接器会把整个 libaccount.a 都复制进可执行文件吗？为什么？

<details>
<summary>参考答案</summary>

不会。链接器只会从库中**提取被用到的函数**（更准确地说是被用到的目标文件）。

工作原理：链接器扫描 main.o，发现引用了 account_create 符号。它在 libaccount.a 的符号索引中查找，发现 account_create 在 account.o 中，于是把整个 account.o 复制到可执行文件。如果 transaction.o 中的函数也被调用了，也会被复制。但如果库中有些函数从未被任何程序调用，它们不会被包含进可执行文件。

注意：提取的粒度是目标文件(.o)，不是单个函数。如果 account.o 中有10个函数，只要用到了其中1个，整个 account.o 都会被复制。
</details>

### 题目4
静态库的"静态"体现在哪里？与"动态"库的区别是什么？

<details>
<summary>参考答案</summary>

"静态"体现在**链接时机**——在编译链接阶段就把代码固定复制进可执行文件。程序一旦生成，就自带了所有需要的库代码，运行时不再依赖库文件。

动态库则相反：链接时只在可执行文件中记录"需要哪个库的哪个函数"，真正的代码在程序启动时（加载时链接）或运行中（运行时加载）才从动态库中加载到内存。

一句话区别：静态链接 = 链接时复制代码；动态链接 = 运行时共享代码。
</details>

## 📝 小结

### 一句话总结
**静态库用 ar 把目标文件打包成 .a 归档，链接时把用到的代码复制进可执行文件——简单可靠，但每个程序都自带一份副本。**

### 六个知识点

| # | 知识点 | 关键句 |
|---|--------|--------|
| 1 | 静态库概念 | 把多个 .o 打包成一个 .a 归档文件 |
| 2 | ar 工具 | `ar rcs libaccount.a account.o transaction.o` |
| 3 | 静态链接 | 链接器从库中提取代码，复制到可执行文件 |
| 4 | 代码复制 | 每个程序都自带一份库代码（体积大） |
| 5 | 优缺点 | 执行快、部署简单；但体积大、更新需重编 |
| 6 | 与第4讲关系 | 多文件编译是"散装"，静态库是"打包" |

### 预告

静态库解决了代码打包和分发的问题，但"每个程序复制一份"太浪费了。如果有10个程序用同一个库，磁盘上就有10份副本，内存中也有10份。
