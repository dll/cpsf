## 一、静态库的三个痛点

第9讲我们用 `ar rcs libaccount.a account.o transaction.o` 把模块打包成了静态库。这解决了"散装分发"的问题，但"代码复制"的本质留下了三个痛点。

### 1.1 痛点一：体积大（磁盘浪费）

静态链接时，链接器把用到的代码**复制**进每个可执行文件：程序 A、B、C 各自从 `libaccount.a` 复制了一份 `account_create` 的机器码，磁盘上就有 3 份副本。10 个程序共用一个 5MB 的库，就多占 45MB 冗余。

### 1.2 痛点二：内存浪费（运行时膨胀）

更严重的是运行时。3 个程序同时运行，操作系统为每个进程建立独立的地址空间，代码**不共享**——物理内存里同样是 3 份 `account_create`：

```
进程A 地址空间 ── 含 account_create 代码
进程B 地址空间 ── 含 account_create 代码   ← 物理内存里是 3 份！
进程C 地址空间 ── 含 account_create 代码
```

### 1.3 痛点三：更新麻烦（bug 修复成本高）

库修了一个 bug 后的修复成本：

| 链接方式 | 修复成本 |
|:---|:---|
| 静态链接 | 重新编译库 → 重新链接**每一个**用过它的程序 |
| 动态链接 | 只替换库文件本身，程序下次启动自动用新版 |

如果有一个 100 个程序共用的基础库（比如 `libc`），静态链接意味着每次修 bug 都要重新构建 100 次。

### 1.4 一句话概括

> **静态库把代码"复制"给每个程序；我们希望能让所有程序"共享"同一份代码——这就是动态库要解决的问题。**

## 二、什么是动态库

### 2.1 动态库 = 运行时才加载的共享代码

**动态库 = 把多个目标文件(.o)链接成一个独立的二进制文件，程序启动时由操作系统加载进内存，多个进程共享同一份代码。**

| 平台 | 动态库文件名 | 特点 |
|:---|:---|:---|
| Linux | `libaccount.so` | so = shared object |
| Windows | `account.dll` | dll = dynamic link library |
| macOS | `libaccount.dylib` | dylib = dynamic library |

### 2.2 三个必须搞清楚的概念

初学动态库最容易混乱的是这三个词，务必分清楚：

| 概念 | 作用 | 何时使用 | 文件 |
|:---|:---|:---|:---|
| 动态库本体 | 提供真正的函数代码 | 运行时加载 | `account.dll` / `libaccount.so` |
| 导入库 | 告诉链接器符号在哪（本身不含代码） | 链接时 | `libaccount.dll.a` |
| 导出符号 | 声明哪些函数允许外部调用 | 编译库时 | 由 `ACCOUNT_API` 宏标记 |

```
   编译期                                运行时
exe ──链接──> 导入库(libaccount.dll.a)   exe ──加载──> 动态库(account.dll)
             （只记录符号归属，          （OS 把真实的函数代码
               几 KB 的"通讯录"）          映射进进程地址空间）
```

**关键理解**：Windows 下链接时连的是**导入库**（很小），不是动态库本体（几百 KB）。exe 里最终只留下一个"导入表"，记录"我叫过 `account_create`，它在 `account.dll` 里"。

### 2.3 导出宏：动态库的"门禁卡"

静态库的符号天然可见；动态库必须**显式声明**哪些函数允许外部使用（完整宏定义见 7.4 节）：

```c
#ifdef ACCOUNT_EXPORTS
    #define ACCOUNT_API __declspec(dllexport)   /* 编译库时：导出 */
#else
    #define ACCOUNT_API __declspec(dllimport)   /* 使用库时：导入 */
#endif

/* 所有对外接口都带上这个宏 */
ACCOUNT_API int  account_create(const char *name, double initial_balance);
ACCOUNT_API bool account_deposit(int id, double amount);
```

| 场景 | 是否定义 `ACCOUNT_EXPORTS` | 宏展开为 |
|:---|:---:|:---|
| 编译动态库本身 | 定义 `-DACCOUNT_EXPORTS` | `dllexport`（导出） |
| 编译使用库的程序 | 不定义 | `dllimport`（导入） |

交易模块用同样对称的写法定义了 `TRANSACTION_API`，原理完全一致。

## 三、编译动态库

### 3.1 两个关键编译选项

| 选项 | 含义 | 为什么需要 |
|:---|:---|:---|
| `-fPIC` | 生成位置无关代码 | 动态库会被映射到进程地址空间的任意位置，代码不能假设自己的绝对地址 |
| `-shared` | 生成共享库 | 告诉编译器产物是动态库而非可执行文件 |

> **`-fPIC` 是动态库的硬性要求。** 如果库被映射到随机地址（ASLR 安全机制），代码里所有"跳转到某个绝对地址"的指令都会失效。`-fPIC` 让代码用相对寻址，无论加载到哪里都能正确定位。

### 3.2 Linux 与 Windows(MinGW) 写法对照

| 步骤 | Linux (gcc) | Windows / MinGW (gcc) |
|:---|:---|:---|
| 编译动态库 | `gcc -fPIC -shared -o libaccount.so account.c transaction.c` | `gcc -shared -o account.dll account.c transaction.c -Wl,--out-implib,libaccount.dll.a -DACCOUNT_EXPORTS -DTRANSACTION_EXPORTS` |
| 生成导入库 | 不需要（`.so` 自带完整符号表） | `-Wl,--out-implib,libaccount.dll.a` 生成 |
| 链接主程序 | `gcc -o app main.c -L. -laccount -Wl,-rpath,'$ORIGIN'` | `gcc -o app.exe main.c -L. -laccount` |
| 运行依赖 | 按 `-rpath` 查找 `libaccount.so` | 到 exe 同目录查找 `account.dll` |

### 3.3 命令逐段拆解

```bash
# Windows / MinGW
gcc  -shared                              # 生成动态库
     -o account.dll                       # 输出文件名
     account.c transaction.c              # 参与编译的源文件
     -Wl,--out-implib,libaccount.dll.a    # 同时生成导入库（链接时用）
     -DACCOUNT_EXPORTS -DTRANSACTION_EXPORTS   # 定义导出宏
```

| 片段 | 作用 |
|:---|:---|
| `-shared` | 产物是动态库 |
| `-Wl,--out-implib,xxx` | 把选项透传给链接器：额外输出导入库 |
| `-DACCOUNT_EXPORTS` | 预处理时定义宏，让 `ACCOUNT_API` 展开为 `dllexport` |
| `-L. -laccount` | 链接时在当前目录找 `libaccount.dll.a`（Linux 找 `libaccount.so`） |

### 3.4 验证产物

```bash
# 查看 dll 导出了哪些函数（Windows）
objdump -p account.dll | grep -E "account_|transaction_"
# 应输出 11 个符号：
#   account_create / account_deposit / account_find / account_get_balance
#   account_list_all / account_withdraw / account_count
#   transaction_deposit / transaction_withdraw / transaction_transfer
#   transaction_print_history
# 注意：内部的 log_transaction 和 accounts[] 数据不会出现在导出表里

# 查看 exe 依赖哪些 dll（Windows）
objdump -p atm_dynamic.exe | grep "DLL Name"
# 输出包含： account.dll   ← exe 里没有账户代码，只记录了依赖

# Linux 等价命令
nm -D --defined-only libaccount.so     # 看导出符号
ldd atm_dynamic                        # 看运行时依赖
```

## 四、加载时链接原理

这是本讲**最核心**的一节。理解了导入表 IAT，才算真正理解动态库。

### 4.1 链接时：exe 里只有"导入表"

动态链接时，链接器**不复制任何函数代码**，只在 exe 中留下一张"欠条清单"——**导入表（Import Address Table, IAT）**：

```
            链接时：链接器只看"有哪些符号没定义"
main.o ──┐
         ├──► 链接器 ──► atm_dynamic.exe
libaccount.dll.a ──┘     ┌────────────────────────────┐
                         │ main() 的代码               │
                         ├────────────────────────────┤
                         │ 导入表 IAT（欠条清单）       │
                         │  account_create → ???       │  ← 地址先留空
                         │  account_deposit → ???      │
                         │  transaction_deposit → ???  │
                         └────────────────────────────┘
              注意：exe 里没有 account_create 的机器码！
```

### 4.2 加载时：OS 加载器负责"还债"

双击 exe 时，操作系统的加载器依次做这五件事：

```
① 把 exe 映射进新进程的地址空间
② 读 exe 的导入表，发现需要 account.dll
③ 找到 account.dll，把它映射进同一进程地址空间（只读映射）
④ 把 account_create 的"真实地址"填进 IAT 的对应位置
⑤ 跳转到 main() 开始执行
```

之后 `main()` 调用 `account_create()`，实际上是跳进 `account.dll` 里执行——exe 中那段代码只是"IAT 跳转桩"。

### 4.3 为什么能省内存：代码段只读共享

关键在于**同一份 dll 的代码段是只读的**，可以在多个进程之间共享物理内存：

```
进程A ─┐
进程B ─┼── 虚拟地址各不相同，但都指向  ┌──────────────────────┐
进程C ─┘    同一份物理内存页           │  account.dll 代码段   │  ← 物理内存只有 1 份！
                                      │  (只读，可共享)       │
                                      └──────────────────────┘
```

| 对比项 | 静态库 | 动态库 |
|:---|:---|:---|
| 磁盘副本 | 每程序一份 | 全系统一份 |
| 内存中的代码 | 每进程一份 | 多进程共享一份（只读段） |
| 可写数据段 | —— | 每进程一份（各自独立） |

> **注意**：共享的是**代码段**（只读）。库里的**全局变量**是可写的，每个进程各有一份独立副本，互不影响。这也是为什么 `account.c` 里的 `accounts[]` 数组，在进程 A 和进程 B 中是两份不同的数据。

### 4.4 两种链接时机

| 名称 | 时机 | 代表技术 | 本讲/后续 |
|:---|:---|:---|:---|
| 加载时链接 | 程序**启动时**自动加载 | Windows 隐式链接、`-laccount` | **本讲** |
| 运行时加载 | 程序**运行中**手动加载 | `dlopen`/`LoadLibrary` | 第11讲 |

## 五、动态库的优缺点

### 5.1 优点

| 优点 | 说明 |
|:---|:---|
| 节省磁盘 | 多个程序共用一份库文件 |
| 节省内存 | 代码段只读共享，物理内存只有一份 |
| 便于更新 | 替换库文件即可，程序无需重新链接 |
| 支持热更 | 库文件升级后，运行中的程序下次启动即生效 |
| 模块解耦 | 程序与实现分离，可独立开发、独立发布 |

### 5.2 缺点

| 缺点 | 说明 |
|:---|:---|
| 运行时依赖 | 缺少 dll/so 程序就**起不来**（不是功能失效，是直接启动失败） |
| DLL Hell | 多个程序依赖同一个 dll 的不同版本，互相覆盖 |
| 加载开销 | 启动时要加载库、重定位、填 IAT，比静态链接稍慢 |
| 调试稍难 | 崩溃点可能在库内部，需要额外的符号文件 |
| 版本兼容 | 接口变更可能导致旧程序无法使用新库 |

### 5.3 什么是 DLL Hell

经典翻车现场：程序 A 需要 `libfoo.dll v1`，程序 B 需要 `libfoo.dll v2`，而系统只能留一份 `libfoo.dll`——装 A 覆盖成 v1，B 崩溃；装 B 覆盖成 v2，A 崩溃。缓解手段：Windows 用 SxS 程序集让各程序用各自目录下的 dll；Linux 按 SONAME 版本号共存（`libfoo.so.1`、`libfoo.so.2`）；通用做法是把 dll 放在程序自己的目录，不要丢进系统目录。

### 5.4 使用场景

- **适合**：大型系统、多程序共享基础库、需要独立升级的模块、插件架构（本课程目标）
- **不适合**：单文件小工具（部署简单优先）、嵌入式裸机、对启动时间极端敏感的场景

## 六、静态库 vs 动态库逐项对比

| 对比项 | 静态库 (.a/.lib) | 动态库 (.so/.dll) |
|:---|:---|:---|
| 打包工具 | `ar rcs` | `gcc -shared` |
| 链接产物 | exe 内含库代码 | exe 内只有导入表 IAT |
| 运行时依赖 | 无 | 必须有库文件 |
| 磁盘占用 | 每程序一份（大） | 全系统一份（小） |
| 内存占用 | 每进程一份 | 多进程共享只读代码段 |
| 启动速度 | 快（无加载开销） | 稍慢（要加载+重定位） |
| 库更新 | 全部程序重新链接 | 替换库文件即可 |
| 能否热更 | 否 | 是（下次启动生效） |
| 缺库后果 | 不影响（已内置） | 程序直接无法启动 |
| 版本冲突 | 无（各自一份） | 有（DLL Hell） |
| 接口变更 | 重新链接即可 | 可能破坏旧程序兼容 |
| 跨平台命名 | Linux `.a` / Win `.lib` | Linux `.so` / Win `.dll` |
| 典型使用者 | 小工具、嵌入式 | 系统级库、插件、大型软件 |

> **一句话记忆**：静态库是**复制**，动态库是**共享**。

## 七、ATM 动态库实战

### 7.1 项目结构

```
│   ├── transaction.c    交易模块实现

│   ├── build.bat         Windows 构建脚本（MinGW）
│   ├── Makefile          Linux 构建脚本
│   ├── account.dll       编译产物：动态库本体
│   ├── libaccount.dll.a  编译产物：导入库（Windows）
│   └── atm_dynamic.exe   编译产物：主程序
├── docs/
│   ├── 课件.md
│   └── generate_ppt.py
├── 思考题.md
└── video/
    └── 讲解脚本.json
```

### 7.2 构建流程（两步）

```
第1步：编译动态库（同时生成导入库）
  gcc -shared -o account.dll account.c transaction.c \
      -Wl,--out-implib,libaccount.dll.a -DACCOUNT_EXPORTS -DTRANSACTION_EXPORTS
  产物：account.dll（代码） + libaccount.dll.a（导入库）

第2步：链接主程序      gcc -o atm_dynamic.exe main.c -L. -laccount
  产物：atm_dynamic.exe（内含导入表，运行时加载 account.dll）
  运行：./atm_dynamic.exe   （account.dll 必须在同一目录）
```

### 7.3 与静态库版对比

| 阶段 | 第9讲 静态库 | 第10讲 动态库 |
|:---|:---|:---|
| 编译库 | `gcc -c account.c` → `account.o` | `gcc -shared` 直接产出 `account.dll` |
| 打包 | `ar rcs libaccount.a *.o` | 生成导入库 `libaccount.dll.a` |
| 链接 | `gcc main.o -L. -laccount` | `gcc main.c -L. -laccount`（一模一样） |
| 产物 | `libaccount.a` + `atm_static.exe` | `account.dll` + `libaccount.dll.a` + `atm_dynamic.exe` |
| 运行 | 直接跑，无需库文件 | **必须**有 `account.dll` |

### 7.4 关键代码

**导出宏（account.h）**：
```c
#if defined(_WIN32) || defined(_MSC_VER)
    #ifdef ACCOUNT_EXPORTS
        #define ACCOUNT_API __declspec(dllexport)   /* 编译库：导出 */
    #else
        #define ACCOUNT_API __declspec(dllimport)   /* 使用库：导入 */
    #endif
#else
    #define ACCOUNT_API __attribute__((visibility("default")))
#endif
ACCOUNT_API int account_create(const char *name, double initial_balance);
```

**内部实现不导出（account.c / transaction.c）**：
```c
/* static 函数和数据不会进入导出表，外部无法访问 */
static Account accounts[MAX_ACCOUNTS];      /* 内部数据 */
static void log_transaction(...) { ... }    /* 内部辅助函数：不导出 */
```

**主程序（main.c）——与静态库版几乎一模一样**：
```c
#include "account.h"
#include "transaction.h"
int main(void) {
    int id1 = account_create("张三", 1000.0);   /* 调用方式完全相同 */
    transaction_deposit(id1, 500.0);
    account_list_all();
    return 0;
}
```

**Makefile 核心片段（Linux）**：
```makefile
libaccount.so: account.c transaction.c          # -fPIC 位置无关 + -shared 共享库
	gcc -Wall -Wextra -fPIC -shared -o libaccount.so account.c transaction.c \
	    -DACCOUNT_EXPORTS -DTRANSACTION_EXPORTS

atm_dynamic: main.c libaccount.so               # -rpath 让程序到自身目录找库
	gcc -Wall -Wextra -o atm_dynamic main.c -L. -laccount -Wl,-rpath,'$$ORIGIN'
```

```bash
# 实验2：只重新编译 account.dll（改动提示文字），不动 exe → 直接运行旧 exe
# 发现：新版本的库立即生效，exe 完全不用重新编译！
```

实验2 正是"可单独更新库"的直接证据，也是为第11讲"运行时加载"和插件框架埋下的伏笔。

## 💭 思考题

### 题目1
静态库有三个痛点：体积大、内存浪费、更新麻烦。请分别说明每个痛点产生的原因，以及动态库是如何解决的。

<details>
<summary>参考答案</summary>

- **体积大**：静态链接时链接器把用到的目标文件**复制**进每个可执行文件，N 个程序就有 N 份代码。动态库只在磁盘上保存一份，各程序通过导入表引用它。
- **内存浪费**：静态链接的代码嵌在各自进程里，代码不共享，N 个进程内存里有 N 份。动态库的**代码段是只读的**，可被多个进程共享映射到同一份物理内存，只有可写数据段各进程独立。
- **更新麻烦**：静态链接的代码已经"焊死"在 exe 里，库修了 bug 必须重新链接所有使用它的程序。动态库只需替换库文件本身，程序下次启动自动加载新版本。

一句话：静态库是代码复制，动态库是代码共享。
</details>

### 题目2
在 Windows/MinGW 下编译动态库时，`-Wl,--out-implib,libaccount.dll.a` 这个选项是做什么的？为什么链接主程序时连的是 `libaccount.dll.a` 而不是 `account.dll`？

<details>
<summary>参考答案</summary>

`-Wl,--out-implib,libaccount.dll.a` 让链接器**额外生成一个导入库**。

导入库（import library）是一个很小的文件，里面**不包含函数代码**，只记录了"哪些符号由哪个 dll 提供"这份"通讯录"。链接主程序时，链接器需要知道 `account_create` 等符号的位置才能生成导入表 IAT，而这个信息就在导入库里。

为什么不直接链 `account.dll`：因为链接发生在**编译期**，此时根本还没运行程序，链接器只需要"符号索引"就能生成 IAT，不需要函数机器码，更不需要把 dll 复制进 exe。等**运行时**操作系统加载器才会根据 IAT 里的记录去加载真正的 `account.dll`。

补充：Linux 下不需要单独的导入库，因为 `.so` 文件本身既包含代码也包含完整的符号表，可以直接链接。
</details>

### 题目3
`account.c` 里有一个 `static Account accounts[MAX_ACCOUNTS];` 数组。当两个进程 A 和 B 都加载了同一个 `account.dll` 时：

1. `accounts` 数组的代码/数据在物理内存里有几份？
2. 如果进程 A 调用 `account_create` 新增一个账户，进程 B 能看到吗？
3. 为什么"代码段共享"和"数据段不共享"是合理的？

<details>
<summary>参考答案</summary>

1. **数据只有一份在磁盘/库文件里，但运行时每个进程各有一份独立的可写副本。** 物理内存中，`account.dll` 的**代码段**（函数机器码）只有一份被共享；而**数据段**（`accounts` 数组、`next_id`、`account_count_val`）是可写的，操作系统用写时复制（Copy-on-Write）机制为每个进程维护独立副本，所以运行时有两个独立的 `accounts` 数组。

2. **看不到。** 进程 A 和 B 各自操作的是自己地址空间里的独立副本，A 新增的账户对 B 完全不可见。进程间要共享数据必须借助共享内存、文件、管道等 IPC 机制。

3. **合理，而且是必需的。**
   - 代码段只读（函数机器码不会变），共享无害且省内存，所以共享。
   - 数据段可写，如果共享，两个进程会互相篡改对方的数据——进程 A 给张三加钱，进程 B 的账本就莫名变了，这完全不可接受。所以必须各自独立。

这也解释了为什么"多个程序共享同一份代码"能省内存，但"共享数据"必须显式设计（第11讲之后的插件框架会用到）。
</details>

### 题目4
把 `account.dll` 从程序目录移走，`atm_dynamic.exe` 会怎样？请对比说明"动态链接失败"和"静态链接"在程序行为上的差异，并解释为什么动态库更新后程序无需重新链接就能用上新版本。

<details>
<summary>参考答案</summary>

**移走 `account.dll` 后**：程序在**启动阶段**就失败，Windows 弹出"找不到 account.dll"的错误，Linux 报 `error while loading shared libraries`。注意——**不是程序跑起来之后功能失效，而是根本启动不了**。因为加载器在填充导入表 IAT 时找不到符号，只能终止进程。这是动态链接最典型的"缺库后果"。

**两者行为差异**：

| 场景 | 静态链接程序 | 动态链接程序 |
|:---|:---|:---|
| 删掉库文件 | 完全不受影响，照常运行 | 无法启动 |
| 库代码有 bug | 必须重新链接才能修 | 替换库文件即可 |

**为什么动态库更新后无需重新链接**：

因为 exe 里根本**没有库代码**，只有一个"符号名 → 地址未知"的导入表。程序每次启动时，操作系统的加载器都会重新去加载当时的 `account.dll`，然后把**当前版本**函数入口的真实地址填进 IAT。

所以替换 `account.dll` 后：
- exe 的导入表内容（符号名字）没变，不需要重新链接；
- 加载器这次填进去的是**新版本函数**的地址；
- 程序自然就用上了新代码。

这正是动态库最实用的价值，也是软件能做到"只升级某个模块"的基础。下一篇讲运行时加载，我们会把这种能力从"启动时"推迟到"运行中"，那才是插件的真正雏形。
</details>

## 🎯 本讲在主线上的位置

全系列有一条主线，是六级台阶，一级比一级抽象：

```
① 表达式  →  ② 函数  →  ③ 模块  →  ④ 库  →  ⑤ 插件  →  ⑥ 框架
 第1讲       第3讲       第4讲      本讲      第11-12讲   第13讲
```

| 台阶 | 解决什么问题 | 代表讲次 |
|:---:|:---|:---|
| ① 表达式 | 一个值怎么算出来 | 第1讲 |
| ② 函数 | 一段逻辑怎么封成名字 | 第3讲 |
| ③ 模块 | 接口和实现怎么分家 | 第4讲 |
| **④ 库** | **代码怎么打包复用、被多个程序共享** | **第9讲（静态库）· 本讲（动态库）** |
| ⑤ 插件 | 运行时按需加载、按名字调用 | 第11-12讲 |
| ⑥ 框架 | 框架反过来调用你的代码（控制反转） | 第13讲 |

**本讲站在第④级"库"上。** 前三级解决的是"代码怎么组织"，到"库"这一级，问题变成了"代码怎么复用和分发"。

- 第9讲静态库解决"可分发"：用 `ar` 把 `.o` 打包成一个文件，链接时把代码**复制**进 exe。
- **本讲动态库解决"可共享"**：库独立成 `.dll/.so`，exe 里只留一张导入表 IAT，**运行时**由操作系统映射进进程，多个进程共享同一份只读代码段。

**本讲为终点（插件框架）贡献了什么？**

| 本讲带走的能力 | 在插件框架里的用途 |
|:---|:---|
| 库可以独立成文件、独立发布 | 插件就是一个动态库 |
| exe 只依赖导入表，不复制库代码 | 宿主与插件解耦，插件可单独替换 |
| 库可单独升级、无需重链程序 | "换一个插件文件"即可扩展功能 |
| 代码段只读共享、数据段各自独立 | 多实例插件的内存模型基础 |

> **但本讲还留着一条限制**：加载发生在**程序启动时**，而且加载哪个库在**编译链接时**就写死进了导入表。
>
> 第11讲要把这条限制再往后推——让加载发生在**运行中**，加载哪个库由**程序自己**按名字挑。那时，"往目录里丢一个文件，程序就多一个功能"就成为现实，**插件的雏形**就此诞生。

## 📝 小结

### 一句话总结
**动态库把库代码放在独立的 .dll/.so 文件里，exe 中只保留一张导入表；程序启动时操作系统把库映射进进程，多个进程共享同一份只读代码段——代码共享，磁盘和内存双省，还能单独更新库。**

### 六个知识点

| # | 知识点 | 关键句 |
|---|--------|--------|
| 1 | 静态库三痛点 | 体积大、内存浪费、更新麻烦——根因是"代码复制" |
| 2 | 动态库概念 | 库代码独立成 .dll/.so，运行时加载共享 |
| 3 | 导出宏 | `ACCOUNT_API` / `TRANSACTION_API`，编译库时 `dllexport` |
| 4 | 编译命令 | Linux `-fPIC -shared`；Windows `-shared` + 导入库 |
| 5 | 加载时链接 | exe 里只有 IAT，OS 启动时映射库并回填地址 |
| 6 | 共享机制 | 代码段只读共享（省内存），数据段每进程独立 |

### 预告

动态库解决了"共享"问题，但"加载时链接"意味着**程序一启动就必须有库**，而且加载的是**编译时就确定好的**那一个库。

如果我们希望在程序**运行过程中**动态决定加载哪个库、调用哪个函数呢？

**下一讲：运行时加载 —— 用 `dlopen` / `LoadLibrary` 在运行中打开库、查找函数、调用函数，插件的雏形就此诞生！**
