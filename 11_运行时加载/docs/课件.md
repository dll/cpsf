## 一、第10讲的"死依赖"痛点

### 1.1 回顾：动态库是怎么被加载的

第10讲我们做出了 `account.dll`，主程序 `atm_dynamic.exe` 里只留了一张导入表（IAT）。程序一启动，操作系统加载器依次做：

```
① 把 exe 映射进进程地址空间
② 读导入表，发现"我还需要 account.dll"
③ 去 exe 所在目录找 account.dll —— 找到了就映射进来
④ 把 account_create 的真实地址回填进 IAT
⑤ 跳转到 main() 开始执行
```

注意第 ③ 步：**找不到库，第 ⑤ 步就永远不会发生**。程序不是"跑起来之后功能失效"，而是**根本启动不了**。

```bash
# 实验：把 account.dll 改名，模拟"缺库"
mv account.dll account.dll.bak && ./atm_dynamic.exe
# → 报错：找不到 account.dll，程序无法启动
```

### 1.2 三个"死"在哪儿

| 痛点 | 具体表现 |
|:---|:---|
| **依赖是死的** | 启动前库必须到位，缺一个就起不来 |
| **时机是死的** | 加载发生在"程序启动"，而不是"真正用到"的那一刻 |
| **对象是死的** | 加载哪个库在**编译链接时**就写死进导入表了 |

### 1.3 一个自然的想法

> 为什么不能让程序**自己**决定：什么时候加载、加载哪个库、调用哪个函数？甚至……**运行时才发现一个新库，也能立刻把它用起来**？

如果真能做到，"往某个目录里丢一个新文件，程序就多一个新功能，而且不用重新编译程序"——这就叫**插件**。

第10讲做不到，因为它的加载是"编译期定好、启动时执行"。我们要把决定权从**操作系统**手里，拿回到**程序自己**手里。

## 二、运行时加载的概念

### 2.1 三个问题的答案

**运行时加载（run-time loading）** = 程序在**运行过程中**，自己调用 API 去打开动态库、查找函数、调用函数，用完还能卸载。

| 问题 | 加载时链接（第10讲） | 运行时加载（第11讲） |
|:---|:---|:---|
| **什么时候加载？** | 程序启动时，由 OS 自动加载 | 程序运行到需要时，由**代码自己**加载 |
| **谁决定加载哪个？** | 编译器/链接器（写死在导入表） | **程序在运行时**按名字挑 |
| **能不能卸载？** | 不能，跟随进程生命周期 | 可以，`dlclose`/`FreeLibrary` 主动卸载 |
| **库不存在会怎样？** | 程序无法启动 | 加载失败返回空句柄，程序**继续跑** |

### 2.2 一个比喻：餐厅的两种备菜方式

```
加载时链接 = 自助餐：开餐前必须把所有菜都摆齐
             少一道菜，餐厅今天就不开了（缺库 = 起不来）

运行时加载 = 点菜：客人点到哪道菜，厨房才现做哪道
             某道菜今天没有？告诉客人"这道没有"，其他照常
```

自助餐厅的菜单**开业前就定死**；点菜餐厅的菜单可以**边营业边加**——新菜（新插件）只要往厨房里放好，客人（宿主）立刻就能点到。

### 2.3 关键差别：库从"必需"变成了"可选"

```
第10讲：exe ──必须有──> account.dll       （缺了活不了）
第11讲：exe ──可选地加载──> 任意插件库      （缺了照样跑）
```

这一字之差打开了插件世界的大门：因为库变成了"可选"，程序就能支持"**有多少用多少**"——plugins 目录放三个库就加载三个，放十个就加载十个，一个都没有也只是"今天没有插件可用"，程序依然健在。

## 三、两套 API 对照

### 3.1 核心函数对照表

Linux 和 Windows 各有一套运行时加载 API，**做的事情一模一样，只是名字不同**：

| 作用 | Linux（`dlfcn.h`） | Windows（`windows.h`） | 说明 |
|:---|:---|:---|:---|
| 打开动态库 | `dlopen(path, RTLD_LAZY)` | `LoadLibraryA(path)` | 返回句柄，失败返回 `NULL` |
| 按名字找符号 | `dlsym(handle, "name")` | `GetProcAddress(handle, "name")` | 返回符号地址，失败返回 `NULL` |
| 关闭 / 卸载 | `dlclose(handle)` | `FreeLibrary(handle)` | 引用计数减 1，归零则卸载 |
| 取错误信息 | `dlerror()` | `GetLastError()` + `FormatMessage` | 告诉你怎么失败的 |
| 返回值类型 | `void *` | `HMODULE`（本质也是指针） | 都是"句柄" |

> **记忆口诀**：`dlopen` 就是 `LoadLibrary`，`dlsym` 就是 `GetProcAddress`，`dlclose` 就是 `FreeLibrary`。学一套，另一套自动会。

### 3.2 平台专有的细节

| 细节 | Linux | Windows |
|:---|:---|:---|
| 库文件后缀 | `.so` | `.dll` |
| 链接时是否加选项 | 要，`-ldl`（libdl） | 不用，`kernel32` 默认就有 |
| 路径查找 | 按 `RPATH`/`LD_LIBRARY_PATH`/系统目录 | 先 exe 目录，再系统目录、`PATH` |
| 加载模式 | `RTLD_LAZY`（用时才解析）/ `RTLD_NOW`（立刻全解析） | 无对应参数，默认按需解析 |

### 3.3 原始写法长什么样

```c
/* ---------- Linux 写法 ---------- */
#include <dlfcn.h>

void *h = dlopen("plugins/deposit_plugin.so", RTLD_LAZY);
if (h == NULL) {
    fprintf(stderr, "加载失败: %s\n", dlerror());   /* 立刻取错误信息 */
}
/* dlsym 返回 void*，必须转成正确的函数指针类型才能调用 */
int (*exec)(double) = (int (*)(double))dlsym(h, "plugin_execute");
if (exec == NULL) { /* 找不到符号 */ }
exec(500.0);
dlclose(h);
```

```c
/* ---------- Windows 写法 ---------- */
#include <windows.h>

HMODULE h = LoadLibraryA("plugins\\deposit_plugin.dll");
if (h == NULL) { /* 可用 GetLastError() 取错误码 */ }
/* GetProcAddress 返回 FARPROC（函数指针），同样要转换 */
int (*exec)(double) = (int (*)(double))GetProcAddress(h, "plugin_execute");
if (exec == NULL) { /* 符号不存在 */ }
exec(500.0);
FreeLibrary(h);
```

两段代码除了名字，**结构完全一致**。既然一致，就没必要在每个业务文件里都写一遍 `#ifdef`——封装它。

## 四、跨平台封装实践：`dynlib.h`

### 4.1 设计目标

```
                  ┌──────────────────────────────────┐
   业务代码 ──────►│  dynlib_open / dynlib_sym / ...  │  ← 只认这套
   （host.c）      └───────────────┬──────────────────┘
                                  │  #ifdef _WIN32 在里面分岔
                    ┌─────────────┴─────────────┐
                    ▼                           ▼
              LoadLibrary               dlopen（Linux）
```

**核心思想**：把"会因平台而变的东西"全部关进一个小盒子（`dynlib.h`），盒子外面只留一套统一接口。业务代码从此与平台无关。

### 4.2 句柄：操作系统给的一张"提货单"

```c
#ifdef _WIN32
    typedef HMODULE dynlib_handle;
#else
    typedef void *dynlib_handle;
#endif
```

**句柄（handle）到底是什么？** 它不是"函数地址"，而是操作系统在你打开动态库之后发给你的一张**不透明凭证**——就像寄存行李时拿到的号牌。

- 你**不需要知道**号牌背后是哪个货架（句柄内部结构是实现细节）
- 你只要**拿着号牌**就能取东西：`dynlib_sym(号牌, "函数名")`
- 最后**还回号牌**：`dynlib_close(号牌)`

Linux 给的号牌是 `void *`，Windows 给的叫 `HMODULE`，**本质都是指针**，用 typedef 统一成 `dynlib_handle`。这与第5讲"指针就是地址"、第7讲 `FILE *` 的思路一脉相承。

### 4.3 四个封装函数

```c
/* 打开（加载）动态库 */
static inline dynlib_handle dynlib_open(const char *path)
{
#ifdef _WIN32
    return LoadLibraryA(path);
#else
    return dlopen(path, RTLD_LAZY);       /* 延迟解析符号，加载更快 */
#endif
}

/* 按名字查找符号：返回 void*，使用时强转成函数指针 */
static inline void *dynlib_sym(dynlib_handle handle, const char *name)
{
#ifdef _WIN32
    return (void *)GetProcAddress(handle, name);   /* FARPROC → void* */
#else
    return dlsym(handle, name);
#endif
}

/* 关闭（卸载）动态库 */
static inline void dynlib_close(dynlib_handle handle)
{
    if (handle == DYNLIB_INVALID) return;          /* 空句柄直接忽略 */
#ifdef _WIN32
    FreeLibrary(handle);
#else
    dlclose(handle);
#endif
}

/* 取错误信息（细节略，见源码 dynlib_error） */
static inline const char *dynlib_error(void);
```

> **为什么用 `static inline` 写在头文件里？** 每个 `.c` 都能 `#include` 一次，不产生重复定义，也不用额外编译 `dynlib.c`。对教学小工程最省事。

### 4.4 一个容易被忽略的编码坑

Windows 的 `FormatMessageA` 返回**本地 ANSI 编码**（简体中文系统是 GBK），而源文件里的中文是 UTF-8，直接拼接输出就会一半正常一半花屏。解决办法：改用宽字符版 `FormatMessageW` 拿到宽字符串，再用 `WideCharToMultiByte(CP_UTF8, ...)` 转成 UTF-8——让整个程序的输出编码保持一致。细节见 `dynlib.h`。

## 五、按名字找函数：符号约定

### 5.1 为什么能"按名字找函数"

动态库编译出来时，除了机器指令，还带一张**符号表**——正是第9讲用 `nm` 看过的那种表，`T` 开头的就是导出的函数：

```
    符号表（导出部分）
    ┌──────────────────────┬───────────────────┐
    │ 名字                 │ 在库中的位置       │
    ├──────────────────────┼───────────────────┤
    │ plugin_name          │ 0x1000            │
    │ plugin_execute       │ 0x1080            │
    └──────────────────────┴───────────────────┘
```

`dlsym` / `GetProcAddress` 干的事就是**拿名字去查这张表**，查到就返回函数入口地址，查不到就返回 `NULL`。

```bash
# 亲手看看库导出了哪些符号（Windows）
objdump -p deposit_plugin.dll | grep -i plugin   # → plugin_name / plugin_execute

# Linux 等价命令
nm -D --defined-only plugins/deposit_plugin.so | grep plugin
```

### 5.2 为什么必须先"约定"函数名

一个动态库里可能有几十个函数，宿主怎么知道**哪个是入口**？答案：**提前约定**。就像接站要让对方举个写着你名字的牌子，否则出站口人山人海根本认不出。

本讲的约定（写在 `plugin_api.h`）：

| 约定符号 | 签名 | 含义 |
|:---|:---|:---|
| `plugin_name` | `const char *plugin_name(void)` | 返回插件名字，宿主用来打印"我加载了谁" |
| `plugin_execute` | `int plugin_execute(double amount)` | 功能入口，`0` 成功、非 `0` 失败 |

```c
/* plugin_api.h —— 把"接头暗号"写成宏，避免到处手写字符串打错字 */
#define PLUGIN_SYM_NAME     "plugin_name"
#define PLUGIN_SYM_EXECUTE  "plugin_execute"

/* 函数指针类型：宿主用它接收查找结果 */
typedef const char *(*plugin_name_fn)(void);
typedef int         (*plugin_execute_fn)(double amount);
```

### 5.3 必须导出，也必须用 C 编译

```c
/* plugin_api.h —— 跨平台导出宏 */
#ifdef _WIN32
    #define PLUGIN_API __declspec(dllexport)              /* 标记"我要导出" */
#else
    #define PLUGIN_API __attribute__((visibility("default")))
#endif

/* deposit_plugin.c —— 用宏标记约定符号 */
PLUGIN_API const char *plugin_name(void)   { return "存款插件"; }
PLUGIN_API int  plugin_execute(double amt) { /* ... */ }
```

| 失败原因 | 现象 |
|:---|:---|
| 忘了加导出宏 | `GetProcAddress` 返回 `NULL` |
| 用 C++ 编译（名字被修饰） | 名字变成 `_Z13plugin_execute...`，查不到 |
| 函数写成 `static` | 不进入导出表，查不到 |
| 符号名拼错一个字母 | 返回 `NULL`（本讲专门演示了这种错误） |

> **教训**：运行时加载把"调用哪个函数"的决定权交给了一个**字符串**。字符串最脆弱——错一个字母就全盘失效。所以宿主必须把"查不到符号"当成**正常情况**来处理，绝不能想当然地直接调用。

### 5.4 对比第10讲：从"编译期绑定"到"运行期绑定"

| 对比项 | 第10讲 加载时链接 | 第11讲 运行时加载 |
|:---|:---|:---|
| 名字何时确定 | 编译链接时（写进导入表） | 运行时（一个字符串） |
| 名字错了何时报错 | 链接时报 `undefined reference` | 运行时返回 `NULL` |
| 谁来负责校验 | 链接器、加载器 | **宿主程序员自己** |

## 六、目录扫描 + 自动加载 = 插件雏形

### 6.1 从"写死一个"到"扫一遍目录"

```c
/* 太死板：加一个插件就要改一次代码、重新编译一次宿主 */
dynlib_handle h = dynlib_open("plugins/deposit_plugin.dll");
```

真正的插件系统应该反过来：**宿主不关心有哪些插件，只负责"把目录里所有合格的库都加载一遍"**。于是新增功能 = 往 `plugins/` 丢一个文件，**宿主一行代码都不用改**。

### 6.2 完整流程图

```
┌─────────────────────────────────────────────────────────────┐
│                       plugins/ 目录                          │
│   deposit_plugin.dll    withdraw_plugin.dll                  │
│   query_plugin.dll      broken_plugin.dll  ← 不守约的反例     │
└───────────────────────────┬─────────────────────────────────┘
                            │ ① 扫描目录，筛出 .dll / .so
                            ▼
                ┌───────────────────────┐
                │  dynlib_open(路径)    │ ② 运行时加载
                └───────────┬───────────┘
                    成功 ↙      ↘ 失败
          ┌──────────────────┐  └──► 打印错误（dynlib_error），跳过
          │ dynlib_sym 取    │ ③ 按约定名字取符号
          │  plugin_name     │
          │  plugin_execute  │
          └────────┬─────────┘
              成功 ↙   ↘ 取不到 plugin_execute
     ┌─────────────────┐   └──► 判定"不是合法插件"，卸载并跳过
     │ 调用 get_name() │ ④ 打印插件名字
     │ 调用 execute()  │ ⑤ 执行插件功能（函数指针调用）
     └────────┬────────┘
              ▼
     ┌─────────────────┐
     │ dynlib_close()  │ ⑥ 用完卸载，内存释放
     └─────────────────┘
```

### 6.3 跨平台扫描也要条件编译

```c
#ifdef _WIN32
    /* Windows：_findfirst / _findnext / _findclose */
    struct _finddata_t fd;
    intptr_t hfile = _findfirst("plugins\\*.dll", &fd);
    if (hfile == -1) { /* 目录不存在 or 没有 dll */ }
    do {
        printf("发现插件: %s\n", fd.name);
        /* 加载、取符号、调用…… */
    } while (_findnext(hfile, &fd) == 0);
    _findclose(hfile);
#else
    /* Linux：opendir / readdir / closedir */
    DIR *dir = opendir("plugins");
    struct dirent *entry;
    while ((entry = readdir(dir)) != NULL) {
        if (strstr(entry->d_name, ".so") != NULL) {
            printf("发现插件: %s\n", entry->d_name);
            /* 加载、取符号、调用…… */
        }
    }
    closedir(dir);
#endif
```

**实际应用**：VS Code 的扩展目录、Eclipse 的 `dropins`、Photoshop 的插件目录，走的都是"**扫描固定目录 → 发现文件 → 加载 → 注册**"这一套。

### 6.4 到这里，插件已经"诞生"了

| 能力 | 带来的自由 |
|:---|:---|
| 运行时加载 | 加载时机由程序决定，不必开机就绪 |
| 按名字取符号 | 调用哪个函数由字符串决定，不必编译期写死 |
| 扫描目录 | 加载哪些库由目录内容决定，宿主不必认识它们 |
| 用完卸载 | 内存可以回收，模块可插可拔 |

> **宿主不再"认识"任何具体插件，它只认"约定"。** 只要某个动态库导出了 `plugin_name` + `plugin_execute`，宿主就会把它当插件用起来——这就是插件的雏形，也是第13讲"插件框架"的起点。

## 七、ATM 运行时加载实战

### 7.1 项目结构

```
11_运行时加载/
├── src/
│   ├── dynlib.h           跨平台动态加载封装（本讲核心）
│   ├── plugin_api.h       插件契约：约定的导出符号 + 导出宏
│   ├── deposit_plugin.c   存款插件（独立编译成 dll/so）
│   ├── withdraw_plugin.c  取款插件
```

### 7.3 关键代码

**宿主：加载一个插件的完整过程（host.c）**

```c
static int load_and_call(const char *path, double amount)
{
    /* ① 运行时加载 —— 这一步才把库拉进进程 */
    dynlib_handle handle = dynlib_open(path);
    if (handle == DYNLIB_INVALID) {
        printf("    ✗ 加载失败（已优雅跳过）：%s\n", dynlib_error());
        return -1;
    }

    /* ② 按约定名字取符号 */
    plugin_name_fn    get_name = (plugin_name_fn)dynlib_sym(handle, PLUGIN_SYM_NAME);
    plugin_execute_fn execute  = (plugin_execute_fn)dynlib_sym(handle, PLUGIN_SYM_EXECUTE);

    /* 取不到 plugin_execute → 这不是一个合格插件，优雅跳过 */
    if (execute == NULL) {
        printf("    ✗ 该文件缺少约定符号 \"%s\"，不是合法插件，已跳过\n",
               PLUGIN_SYM_EXECUTE);
        dynlib_close(handle);          /* 关键：失败也要先卸载 */
        return -1;
    }

    /* ③ 调用（就是第5讲学的函数指针调用） */
    printf("    → 加载成功，插件名字：%s\n",
           (get_name != NULL) ? get_name() : "(未提供名字)");
    execute(amount);

    /* ④ 用完卸载 */
    dynlib_close(handle);
    return 0;
}
```

**插件：存款插件实现契约（deposit_plugin.c）**

```c
#include "plugin_api.h"
#include <stdio.h>

static double g_balance = 1000.0;         /* 插件自己的状态 */

PLUGIN_API const char *plugin_name(void) { return "存款插件"; }

PLUGIN_API int plugin_execute(double amount)
{
    if (amount <= 0.0) return -1;         /* 参数校验 */
    g_balance += amount;
    printf("    [存款插件] 存入 %.2f 元，当前余额 %.2f 元\n", amount, g_balance);
    return 0;
}
```

> `g_balance` 是 `static` 的——它活在**被加载进宿主进程**的那块内存里，一直存在到插件被卸载。这正好说明"库是一个活着的、有状态的模块"，而不只是一段代码。

## 八、新痛点：函数名统一了，可接口还没统一

### 8.1 宿主在运行时遇到了什么尴尬

仔细看 7.3 节的 `load_and_call`，会发现一个绕不过去的硬伤：

```c
/* 宿主必须"知道"插件的函数长什么样，才能写死这个调用 */
execute(amount);        /* 所有插件都只能接收一个 double，返回 int */
```

| 尴尬 | 具体表现 |
|:---|:---|
| **参数不够用** | 想加"转账"插件（转出账户 + 转入账户 + 金额），一个 `double` 塞不下 |
| **参数多余** | 查询插件根本不需要金额，却被迫带一个 `amount` 形参（只能 `(void)amount;` 忽略） |
| **能力太单一** | 一个插件只能有一个入口。想再提供"初始化""清理""查询元数据"，宿主就得再约定更多符号名，越约定越乱 |
| **元数据没处放** | 插件的版本号、作者、功能描述统统没地方声明 |
| **宿主被硬编码** | 宿主里写死了 `"plugin_execute"` 和它的参数类型，插件形态一变，宿主就得改 |

一句话总结：**本讲只统一了"函数名"，没有统一"接口"。** 就像规定所有人都要在门口举牌子，但牌子上写什么、见面后怎么交谈全凭各自发挥——人一多，必然乱套。

### 8.2 怎么办：从"散装函数名"到"统一接口"

设想 USB 是怎么解决外设混乱的：不管插的是鼠标、键盘还是 U 盘，电脑只管按 **USB 协议**通信，不关心设备内部怎么实现。

软件世界也需要一个"USB 接口"——**把所有插件都要提供的行为打包成一个结构体接口**：

```c
/* 第12讲预告：统一接口的雏形 */
typedef struct Plugin {
    char name[32];                                        /* 元数据：名字 */
    char version[16];                                     /* 元数据：版本 */
    int  (*init)(struct Plugin *self);                    /* 行为：初始化 */
    int  (*execute)(struct Plugin *self, double amount);  /* 行为：执行 */
    void (*cleanup)(struct Plugin *self);                 /* 行为：清理 */
} Plugin;
```

于是宿主只要取**一个**符号（比如 `get_plugin`）就能拿到整个接口，然后统一调用：

```c
/* 不管什么插件，调用方式完全一样 —— 这就是多态 */
plugin->init(plugin);
plugin->execute(plugin, 500.0);
plugin->cleanup(plugin);
```

### 8.3 本讲与第12讲的分工

| 讲次 | 解决的问题 | 关键手段 |
|:---|:---|:---|
| **第11讲（本讲）** | 库怎么在**运行时**被加载、调用、卸载 | `dlopen`/`dlsym`/`dlclose` + 目录扫描 |
| **第12讲** | 加载进来之后，怎么**统一地**调用它们 | 结构体 + 函数指针 = 统一接口 + 多态 |

> 第11讲让插件"能进来"，第12讲让插件"能管理"。**先有加载，才有接口可谈**——顺序不能反。

## 💭 思考题

### 题目1

`dlopen`/`LoadLibrary` 返回的"句柄"到底是什么东西？它和函数指针有什么区别？为什么 `dlsym(handle, "name")` 需要一个句柄，而不能直接 `dlsym("deposit_plugin.dll", "name")`？

<details>
<summary>参考答案</summary>

**句柄是"一个已打开的库"的代表凭证**，通常是一个不透明的指针（Linux 是 `void *`，Windows 是 `HMODULE`），指向操作系统内部维护的"已加载模块记录"，里面有这个库被映射到进程的基址、符号表位置等。

| 对比项 | 句柄（handle） | 函数指针 |
|:---|:---|:---|
| 代表什么 | 整个"库"这一个模块 | 库里"某一个函数" |
| 从哪来 | `dlopen`/`LoadLibrary` | `dlsym`/`GetProcAddress` |
| 怎么用 | 传给 `dlsym` 查符号、传给 `dlclose` 卸载 | 直接加括号调用 |
| 能不能调用 | 不能，它不是可执行代码 | 能，它就是代码入口地址 |

**为什么必须传句柄**：

1. **要先"打开"才能"查询"**。库文件只是磁盘上的二进制，只有经过 `dlopen` 加载、建立好内存映射和符号表之后，符号地址才存在。`dlsym("xxx.dll", ...)` 相当于让一个还没进门的库回答"你家里有什么"。
2. **同名符号可能来自不同的库**。进程里可能加载了多个都含 `plugin_execute` 的库，必须靠句柄区分"我要的是**这个**库里的那一个"。
3. **句柄还承担生命周期管理**。`dlclose(handle)` 要知道卸载哪一个，也要靠句柄做引用计数。

一句话：**句柄代表"哪一个库"，函数指针代表"哪一个函数"——先有库，才能有函数。**
</details>

### 题目2

宿主用 `dynlib_sym(handle, "plugin_execute")` 取符号，如果返回 `NULL`（找不到），为什么不直接忽略、继续往下调用？请说出至少三种会导致"找不到符号"的真实原因，以及宿主应该怎么正确处理。

<details>
<summary>参考答案</summary>

**为什么不能忽略继续调用**：`dynlib_sym` 返回的是函数入口地址，`NULL` 意味着"这个地址不存在"。此时若直接写 `execute(amount)`，就相当于**调用空地址**——程序立刻崩溃（Windows 上是访问违规，Linux 上是段错误）。运行时加载的"优雅"恰恰在于把这类失败**当作正常情况**处理，不让一个不合格的插件拖垮整个宿主。

**三种常见原因**：

1. **符号名写错了**。比如把 `plugin_execute` 打成 `plugin_exectue`（本讲实测里故意演示过）。按名字找函数，错一个字母就失效。
2. **插件忘了加导出宏**。没有 `__declspec(dllexport)`（Windows）或 `visibility("default")`，函数不会进入导出表，`GetProcAddress` 自然查不到。
3. **用 C++ 编译，或把函数写成了 `static`**。C++ 会做名字修饰（`plugin_execute` 变成 `_Z13plugin_executed` 之类），`static` 函数则只是文件内部符号，都不会导出。

**宿主应该怎么处理**：

```c
execute = (plugin_execute_fn)dynlib_sym(handle, PLUGIN_SYM_EXECUTE);
if (execute == NULL) {
    printf("该文件缺少约定符号 \"%s\"，不是合法插件，已跳过\n",
           PLUGIN_SYM_EXECUTE);
    dynlib_close(handle);      /* 关键：已经打开的库必须卸载 */
    return -1;
}
```

**要点**：任何一步失败，都要先把已加载的资源还回去（`dynlib_close`）再返回错误码——这是"资源获取即释放"的基本纪律。
</details>

### 题目3

请从"代码放在哪、何时加载、谁来决定、缺库后果、能否卸载、新增功能要不要改程序"六个维度，对比**静态链接**（第9讲）、**加载时链接**（第10讲）、**运行时加载**（第11讲）。并说明：为什么只有运行时加载能实现"热插拔"？

<details>
<summary>参考答案</summary>

| 维度 | 静态链接（第9讲） | 加载时链接（第10讲） | 运行时加载（第11讲） |
|:---|:---|:---|:---|
| **代码放在哪** | 复制进 exe 内部 | 独立的 `.dll`/`.so` | 独立的 `.dll`/`.so` |
| **何时加载** | 链接时复制，运行时无需库 | 程序**启动时**由 OS 自动加载 | 程序**运行到需要时**由代码主动加载 |
| **谁来决定** | 链接器（编译期写死） | 链接器写进导入表，OS 执行 | 程序自己（运行时按名字挑） |
| **缺库后果** | 不受影响（已内置） | **程序无法启动** | 加载失败返回 NULL，程序**继续跑** |
| **能否卸载** | 不需要（就在 exe 里） | 不能，跟随进程生命周期 | 能，`dlclose`/`FreeLibrary` 主动卸载 |
| **新增功能要不改程序** | 必须重新链接 | 必须重新链接（导入表要加符号） | **不用改**，丢个文件到目录即可 |

**为什么只有运行时加载能实现"热插拔"**：

热插拔的两个硬性条件是 **① 加载时机由程序决定；② 新增模块不需要动宿主程序**。

- **静态链接出局**：代码已经"焊死"在 exe 里，新增功能必须重新编译、链接、分发整个程序。
- **加载时链接出局**：库虽然独立，但"需要哪些库"在编译期就写进了 exe 的导入表。想加一个新库就得改导入表——也就是**重新链接**宿主；而且库必须在启动前就位。
- **运行时加载胜出**：宿主里没有硬编码任何插件名，只是"扫描 plugins 目录，谁在就加载谁"。于是加载时机可控、加载对象由目录内容决定、用完还能卸载。

一句话：热插拔的本质是"**宿主与插件只靠约定（协议）通信，不靠编译期的硬编码绑定**"。前两种都有编译期绑定，第三种把绑定推迟到了运行时。
</details>

### 题目4

本讲的宿主用字符串 `"plugin_execute"` 和固定签名 `int (double)` 调用所有插件。请指出这种"只统一函数名、不统一接口"的做法会带来哪些具体问题，并给出至少两种改进思路及其优缺点。

<details>
<summary>参考答案</summary>

**具体问题**：

1. **参数类型被写死，表达力不足**。所有插件都只能收一个 `double`。想加"转账插件"（转出账户 + 转入账户 + 金额）塞不进去；"打印对账单插件"不需要金额，又被迫带一个用不上的参数。
2. **返回信息太单一**。只能返回一个 `int` 表示成败，想回传余额、错误详情、提示文字都做不到。
3. **一个插件只能有一个入口**。无法提供"初始化""清理""获取元数据"等能力，除非宿主再约定更多符号名——越加越乱，宿主越来越难维护。
4. **宿主被字符串硬编码**。插件形态一变，宿主必须跟着改、重新编译，违背"扩展不改代码"的初衷。
5. **没有元数据**。宿主无法知道插件的版本、作者、功能描述，也没法做版本兼容判断。

**改进思路**：

**思路一：把函数指针打包成结构体接口（推荐，第12讲的做法）**

```c
typedef struct Plugin {
    char name[32];
    char version[16];
    int  (*init)(struct Plugin *self);
    int  (*execute)(struct Plugin *self, double amount);
    void (*cleanup)(struct Plugin *self);
} Plugin;
```

插件导出 `Plugin *get_plugin(void)`，宿主只取这一个符号就能拿到全部能力，调用方式统一（多态）。

- 优点：参数、返回值、生命周期、元数据一次性解决；宿主只依赖接口不依赖实现，真正"加插件不改代码"。
- 缺点：需要提前设计接口，接口一定下来改动会影响所有插件（需要版本兼容策略）。

**思路二：用 `void *` 传递通用参数（灵活派）**

```c
typedef struct Plugin {
    int (*execute)(struct Plugin *self, void *arg);
} Plugin;
```

- 优点：参数完全自由，任何类型都能通过 `void *` 传，接口永远不用改。
- 缺点：**丢失类型安全**，全靠调用双方"心中有数"，类型不匹配时编译期发现不了，只能在运行时出错。

**思路三：参数存在插件内部，`execute` 不带参数**

```c
typedef struct Plugin {
    void *user_data;                     /* 参数先存这里 */
    int (*execute)(struct Plugin *self); /* 调用时不传参数 */
} Plugin;
```

- 优点：接口最简洁稳定。
- 缺点：需要额外的"设置参数"约定，多一步交互；状态管理更复杂。

**结论**：实际工程通常**以思路一为主**（结构体接口 + 统一生命周期），个别需要传任意数据的场合**配合思路二的 `void *`**（如 GStreamer、Linux 内核驱动模型）。这正是第12讲要展开的内容。

## 🎯 本讲在主线上的位置

全系列有一条主线，是六级台阶，一级比一级抽象：

```
① 表达式  →  ② 函数  →  ③ 模块  →  ④ 库  →  ⑤ 插件  →  ⑥ 框架
 第1讲       第3讲       第4讲      第9-10讲   本讲        第13讲
```

| 台阶 | 解决什么问题 | 代表讲次 |
|:---:|:---|:---|
| ① 表达式 | 一个值怎么算出来 | 第1讲 |
| ② 函数 | 一段逻辑怎么封成名字 | 第3讲 |
| ③ 模块 | 接口和实现怎么分家 | 第4讲 |
| ④ 库 | 代码怎么打包复用、被多个程序共享 | 第9-10讲 |
| **⑤ 插件** | **运行时按需加载、按名字调用、随时卸载** | **本讲** |
| ⑥ 框架 | 框架反过来调用你的代码（控制反转） | 第13讲 |

**本讲是"插件"诞生的那一级台阶。** 前四级解决的都是"代码怎么组织、怎么复用"，到"插件"这一级，问题变成了"**程序怎么在运行中把别人的代码用起来**"。

| 本讲之前 | 本讲之后 |
|:---|:---|
| 库是**加载时链接**：启动前必须齐，缺一个都起不来 | 库是**运行时加载**：用到才加载，缺了照样跑 |
| 加载哪个库在**编译期写死**进导入表 | 加载哪个库由**运行时的代码**按名字挑 |
| 想加一个库 → 重新链接宿主程序 | 想加一个库 → 往目录里丢一个文件 |

**本讲为终点（插件框架）贡献了什么？**

| 本讲带走的能力 | 在插件框架里的用途 |
|:---|:---|
| 运行时加载（`dlopen`/`LoadLibrary`） | 插件能在宿主跑起来之后被加载进来 |
| 按名字取符号（`dlsym`/`GetProcAddress`） | 宿主按约定"接头暗号"找到插件入口 |
| 目录扫描 + 自动加载 | 插件目录就是功能清单，宿主不认识具体插件 |
| 用完卸载（`dlclose`/`FreeLibrary`） | 插件可插可拔，模块可回收 |
| 优雅处理失败（NULL / 坏插件） | 一个坏插件不能拖垮整个宿主 |

> **但本讲还留着一个新痛点**：约定只统一了"函数名"，没统一"接口"。
>
> 宿主是靠字符串 `"plugin_execute"` 和写死的参数类型 `double` 去调用的——查询插件被迫带一个用不上的金额，转账插件一个 `double` 又不够用；每加一种能力，宿主都得改代码去认新的符号名。
>
> **第12讲要给所有插件装一个统一的"USB 插头"**：用"结构体 + 函数指针"定义统一的 Plugin 接口，让宿主只认接口、不认实现。插件"能进来"之后，还要"能被统一管理"。

## 📝 小结

### 一句话总结
**运行时加载让程序在运行中自己决定"何时加载、加载哪个库、调用哪个函数、用完卸载"——用 `dlopen`/`LoadLibrary` 把库从"编译期必需的依赖"变成了"运行期可选的资源"，再配合目录扫描，插件的雏形就此诞生。**

### 六个知识点

| # | 知识点 | 关键句 |
|---|--------|--------|
| 1 | 第10讲的死依赖 | 加载时链接：缺库 = 程序根本起不来，加载对象编译期定死 |
| 2 | 运行时加载的概念 | 加载时机、对象由程序自己决定；失败返回 NULL，程序继续跑 |
| 3 | 两套 API 对照 | `dlopen/dlsym/dlclose` ↔ `LoadLibrary/GetProcAddress/FreeLibrary` |
| 4 | 跨平台封装 | `#ifdef _WIN32` 把平台差异关进 `dynlib.h`，对外只留统一接口 |
| 5 | 符号约定与句柄 | 句柄 = 库的凭证；`dlsym` 按名字查符号表，查不到返回 NULL |
| 6 | 目录扫描 = 插件雏形 | "谁在目录里就加载谁"，宿主不认识插件，只认约定 |

### 新痛点 → 预告

本讲让插件"能被加载"，但宿主是靠着字符串 `"plugin_execute"` 和写死的参数类型去调用的：

- 查询插件不需要金额，却被迫接收 `amount`；
- 想加"转账插件"要多个参数，一个 `double` 不够用；
- 每增加一种能力，宿主都得改代码去认新的符号名。

**只统一"函数名"还不够，还得统一"接口"。**

> **下一讲：接口抽象 —— 用"结构体 + 函数指针"定义统一的 Plugin 接口，让宿主只认接口不认实现，不同插件多态调用！**
