## 思考题 ①：两套 API 的对应与句柄的本质

**题目**

1. 请写出 Linux 与 Windows 两套运行时加载 API 的对应关系。
2. `dlopen` / `LoadLibrary` 返回的**句柄**到底是什么？它和**函数指针**有什么区别？
3. 为什么 `dlsym(handle, "name")` 需要一个句柄，而不能直接 `dlsym("deposit_plugin.dll", "name")`？

**背景**

同一个动作，两个平台两套名字。Linux 在 `<dlfcn.h>` 里提供 `dlopen` / `dlsym` / `dlclose` / `dlerror`；Windows 在 `<windows.h>` 里提供 `LoadLibrary` / `GetProcAddress` / `FreeLibrary` / `GetLastError`。它们做的事情**一模一样**，只是名字不同。

**思考方向**

- 先想"要先打开才能查询"：库文件躺在磁盘上时，符号地址存在吗？
- 再想"同名符号可能来自不同的库"：进程里同时加载两个都含 `plugin_execute` 的库，怎么区分？
- 最后想生命周期：卸载时要靠什么知道"卸哪一个"？

**参考答案**

**1. 两套 API 的对应关系**

| 作用 | Linux（`dlfcn.h`） | Windows（`windows.h`） |
|:---|:---|:---|
| 打开动态库 | `dlopen(path, RTLD_LAZY)` | `LoadLibraryA(path)` |
| 按名字找符号 | `dlsym(handle, "name")` | `GetProcAddress(handle, "name")` |
| 关闭 / 卸载 | `dlclose(handle)` | `FreeLibrary(handle)` |
| 取错误信息 | `dlerror()` | `GetLastError()` + `FormatMessage` |
| 是否需要额外链接 | 要，`-ldl` | 不用，`kernel32` 默认就有 |

> 记忆口诀：`dlopen` 就是 `LoadLibrary`，`dlsym` 就是 `GetProcAddress`，`dlclose` 就是 `FreeLibrary`。学一套，另一套自动会。

**2. 句柄 vs 函数指针**

**句柄是"一个已打开的库"的代表凭证**，通常是一个不透明的指针（Linux 是 `void *`，Windows 是 `HMODULE`），指向操作系统内部维护的"已加载模块记录"。

| 对比项 | 句柄（handle） | 函数指针 |
|:---|:---|:---|
| 代表什么 | 整个"库"这一个模块 | 库里"某一个函数" |
| 从哪来 | `dlopen` / `LoadLibrary` | `dlsym` / `GetProcAddress` |
| 怎么用 | 传给 `dlsym` 查符号、传给 `dlclose` 卸载 | 直接加括号调用 |
| 能不能调用 | 不能，它不是可执行代码 | 能，它就是代码入口地址 |

**3. 为什么必须传句柄**

1. **要先"打开"才能"查询"**。库文件只是磁盘上的二进制，只有经过 `dlopen` 加载、建立好内存映射和符号表之后，符号地址才存在。`dlsym("xxx.dll", ...)` 相当于让一个还没进门的库回答"你家里有什么"。
2. **同名符号可能来自不同的库**。进程里可能加载了多个都含 `plugin_execute` 的库，必须靠句柄区分"我要的是**这个**库里的那一个"。
3. **句柄还承担生命周期管理**。`dlclose(handle)` 要知道卸载哪一个，也要靠句柄做引用计数。

> 一句话：**句柄代表"哪一个库"，函数指针代表"哪一个函数"——先有库，才能有函数。**

## 思考题 ②：找不到符号，为什么不能硬调用？

**题目**

宿主用 `dynlib_sym(handle, "plugin_execute")` 取符号，如果返回 `NULL`（找不到），为什么不直接忽略、继续往下调用？

1. 直接调用 `NULL` 会发生什么？
2. 请说出至少三种会导致"找不到符号"的真实原因。
3. 宿主应该怎么正确处理？为什么失败时也要 `dynlib_close`？

**背景**

本讲实测里出现过两次"取不到"：`broken_plugin.dll` 没导出 `plugin_execute`；宿主故意拼错成 `plugin_exectue`（少了一个 c）。两次返回的都是 `NULL`。运行时加载把"调用哪个函数"的决定权交给了一个**字符串**——字符串最脆弱。

**思考方向**

- `dynlib_sym` 返回的是什么？`NULL` 代表什么地址？
- 想想"函数名"是怎么进符号表的：导出宏、C/C++ 名字修饰、`static`。
- 资源纪律：`dynlib_open` 成功之后，中途 return 前要还什么？

**参考答案**

**1. 直接调用 NULL 的后果**

`dynlib_sym` 返回的是**函数入口地址**，`NULL` 意味着"这个地址不存在"。此时若直接写 `execute(amount)`，就相当于**调用空地址**——程序立刻崩溃（Windows 上是访问违规 Access Violation，Linux 上是段错误 Segfault）。

运行时加载的"优雅"恰恰在于：把这类失败**当作正常情况**处理，不让一个不合格的插件拖垮整个宿主。

**2. 三种常见原因**

1. **符号名写错了**。比如把 `plugin_execute` 打成 `plugin_exectue`（本讲实测里故意演示过）。按名字找函数，错一个字母就失效。
2. **插件忘了加导出宏**。没有 `__declspec(dllexport)`（Windows）或 `visibility("default")`（Linux），函数不会进入导出表，`GetProcAddress` / `dlsym` 自然查不到。
3. **用 C++ 编译，或把函数写成了 `static`**。C++ 会做名字修饰（`plugin_execute` 变成 `_Z13plugin_executed` 之类），`static` 函数只是文件内部符号，都不会导出。

**3. 正确处理方式**

```c
execute = (plugin_execute_fn)dynlib_sym(handle, PLUGIN_SYM_EXECUTE);
if (execute == NULL) {
    printf("该文件缺少约定符号 \"%s\"，不是合法插件，已跳过\n",
           PLUGIN_SYM_EXECUTE);
    dynlib_close(handle);      /* 关键：已经打开的库必须卸载 */
    return -1;
}
```

**为什么失败时也要 `dynlib_close`**：`dynlib_open` 一旦成功，库就被映射进了进程、占用了句柄资源。任何一步失败，都要先把已加载的资源**还回去**再返回错误码——这是"资源获取即释放"（RAII）的基本纪律。忘了它，宿主每遇到一个坏插件就泄漏一份库资源。

## 思考题 ③：三种链接方式的全方位对比

**题目**

请从"代码放在哪、何时加载、谁来决定、缺库后果、能否卸载、新增功能要不要改程序"六个维度，对比：

- **静态链接**（第9讲）
- **加载时链接**（第10讲）
- **运行时加载**（第11讲）

**背景**

这三种方式不是三个孤立的知识点，而是一条演进线：从"把库焊进程序"，到"启动时加载库"，再到"运行中按需加载"。每一级都在解决上一级留下的限制。

**思考方向**

- 每个维度都追问一句"**为什么**会有这个差异"？
- 特别注意"新增功能要不要改程序"这一维度——它是三者的分水岭。

**参考答案**

| 维度 | 静态链接（第9讲） | 加载时链接（第10讲） | 运行时加载（第11讲） |
|:---|:---|:---|:---|
| **代码放在哪** | 复制进 exe 内部 | 独立的 `.dll`/`.so` | 独立的 `.dll`/`.so` |
| **何时加载** | 链接时复制，运行时无需库 | 程序**启动时**由 OS 自动加载 | 程序**运行到需要时**由代码主动加载 |
| **谁来决定** | 链接器（编译期写死） | 链接器写进导入表，OS 执行 | 程序自己（运行时按名字挑） |
| **缺库后果** | 不受影响（已内置） | **程序无法启动** | 加载失败返回 NULL，程序**继续跑** |
| **能否卸载** | 不需要（就在 exe 里） | 不能，跟随进程生命周期 | 能，`dlclose`/`FreeLibrary` 主动卸载 |
| **新增功能要改程序吗** | 必须重新链接 | 必须重新链接（导入表要加符号） | **不用改**，丢个文件到目录即可 |

**为什么会有这些差异**：三者其实是"绑定发生在哪个阶段"的三种答案——

- 静态链接把绑定放在**链接期**：符号和代码都被固化进 exe；
- 加载时链接把绑定放在**装载期**：符号写进导入表，由 OS 在启动时回填；
- 运行时加载把绑定推迟到**运行期**：一切都靠运行时用一个字符串去查。

绑定越晚，灵活性越高，代价是"问题发现得越晚"（静态链接编译期报错，运行时加载得靠程序员自己判断）。

## 思考题 ④：为什么只有运行时加载能"热插拔"？

**题目**

本讲实现了"往 `plugins/` 目录丢一个新插件，宿主不用改一行代码、不用重新编译，就多一个功能"。这就是热插拔。

1. 热插拔需要满足哪两个硬性条件？
2. 为什么静态链接、加载时链接都做不到？
3. 用一句话概括"热插拔"的本质。

**背景**

`host.exe` 的编译命令里**没有任何插件**——它只 `#include "plugin_api.h"` 拿到两个字符串约定。运行起来后，它才去扫描目录，发现谁就加载谁。

**思考方向**

- 两个条件：**加载时机由程序决定**、**新增模块不动宿主程序**。
- 逐一代入三种链接方式，看它们"卡"在哪一步。
- 别忘了回头看第10讲的结论：加载时链接的"需要哪些库"是写进**导入表**的。

**参考答案**

**1. 热插拔的两个硬性条件**

1. **加载时机由程序决定**：想什么时候加载就什么时候加载，不必开机就绪。
2. **新增模块不需要动宿主程序**：往目录里丢一个文件就完成扩展，宿主不重新编译、不重新分发。

**2. 为什么前两种做不到**

- **静态链接出局**：代码已经"焊死"在 exe 里，新增功能必须重新编译、链接、分发整个程序。
- **加载时链接出局**：库虽然独立，但"需要哪些库"在编译期就写进了 exe 的导入表。想加一个新库就得改导入表——也就是**重新链接宿主**；而且库必须在启动前就位。
- **运行时加载胜出**：宿主里**没有硬编码任何插件名**，只是"扫描 `plugins` 目录，谁在就加载谁"。于是加载时机可控、加载对象由目录内容决定、用完还能卸载。

**3. 一句话概括本质**

> **热插拔的本质是：宿主与插件只靠"约定（协议）"通信，不靠编译期的硬编码绑定。**

前两种都有编译期绑定（静态链接绑定代码，加载时链接绑定符号），第三种把绑定推迟到了运行时。

也正因为只靠"约定"，本讲还留着一个新痛点：**约定只统一了函数名，没统一接口**——宿主靠字符串 `"plugin_execute"` 和写死的参数类型 `double` 去调用，查询插件被迫带一个用不上的金额，转账插件一个 `double` 又不够用。这正是**第12讲"接口抽象"**要解决的问题。
