## 题目1：为什么结构体+函数指针能模拟多态？与C++虚函数表有什么关系？

**问题**：我们在C语言中用"结构体+函数指针"实现了多态——不同插件实现同一个 `Plugin` 接口，调用方通过 `plugin->execute(plugin, amount)` 统一调用，不同插件执行不同操作。

C++ 用"虚函数"实现多态。C++ 的虚函数底层用"虚函数表（vtable）"实现。请思考：C语言的"结构体+函数指针"和C++的虚函数表本质上是同一个东西吗？

```c
/* C语言：手动填充函数指针 */
typedef struct Plugin {
    int  (*execute)(struct Plugin* self, double amount);
} Plugin;

Plugin deposit = { .execute = deposit_execute };
Plugin withdraw = { .execute = withdraw_execute };
```

**思考方向**：
- C++ 的虚函数表（vtable）内部存的是什么？（提示：函数指针数组）
- C 语言手动填充函数指针，C++ 编译器自动生成 vtable，本质一样吗？
- 为什么说"C语言是 C++ 的子集"在底层机制上也成立？

---

### 参考答案

**本质上是同一个东西。**

C++ 的虚函数表（vtable）就是一个**函数指针数组**，存放在结构体的内存布局中。编译器自动维护这张表，调用时自动查找。

```
C++ 层面:
┌──────────────────┐
│  class Plugin {   │
│    virtual int   │  ← 虚函数
│      execute();  │
│  }                │
└──────────────────┘
         │ 编译器自动生成
         ▼
┌──────────────────────────┐
│  vtable:                  │
│  [0] → &execute           │  ← 函数指针！
│  [1] → &init              │
│  [2] → &cleanup           │
└──────────────────────────┘

C 语言层面:
┌──────────────────────────┐
│  struct Plugin {          │
│    int (*execute)(...);   │  ← 手动填写函数指针
│    int (*init)(...);      │
│    void (*cleanup)(...); │
│  }                        │
└──────────────────────────┘
```

**区别只在于"谁维护"**：
- C 语言：程序员手动填充函数指针字段
- C++：编译器自动生成 vtable，程序员只需写 `virtual` 关键字

**结论**：C++ 的虚函数机制，本质上就是 C 语言"结构体+函数指针"的编译器自动化版本。理解了 C 语言的接口抽象，C++ 的多态就不再神秘。

## 题目2：如果两个插件的 execute() 参数不同，怎么统一到同一接口？

**问题**：我们的 `Plugin` 接口定义 `execute(Plugin* self, double amount)`，金额作为参数。但有些插件不需要金额（比如查询余额），有些插件需要更多参数（比如转账需要目标账户和金额）。怎么在统一接口中处理这种差异？

```c
/* 查询插件：不需要 amount */
static int query_execute(Plugin* self, double amount) {
    /* amount 参数没用到... */
    printf("余额: %.2f\n", balance);
    return 0;
}

/* 转账插件：需要目标账户ID + 金额，但接口只有 amount... */
/* 怎么办？ */
```

**思考方向**：
- 能不能用 `void*` 通用指针传递任意参数？（类似 `void*` 在第5讲的应用）
- 能不能把所有可能的参数打包成一个结构体，用 `void*` 传递？
- 这种做法的优缺点是什么？

---

### 参考答案

**方案1：用 `void*` 传递通用参数（推荐）**

修改接口，用 `void*` 代替具体参数类型：

```c
typedef struct Plugin {
    /* execute 接收通用参数指针 */
    int (*execute)(struct Plugin* self, void* arg);
} Plugin;

/* 存款插件：把金额包装后传入 */
int deposit_execute(Plugin* self, void* arg) {
    double amount = *(double*)arg;  /* 从 void* 取出金额 */
    balance += amount;
    return 0;
}

/* 查询插件：不使用参数 */
int query_execute(Plugin* self, void* arg) {
    (void)arg;  /* 显式忽略参数 */
    printf("余额: %.2f\n", balance);
    return 0;
}

/* 转账插件：用结构体传递多个参数 */
typedef struct {
    int target_id;
    double amount;
} TransferArgs;

int transfer_execute(Plugin* self, void* arg) {
    TransferArgs* t = (TransferArgs*)arg;
    /* 用 t->target_id 和 t->amount 执行转账 */
    return 0;
}
```

**优点**：接口统一，灵活适应各种参数需求。
**缺点**：失去类型安全，需要手动类型转换，容易出错。

**方案2：在 Plugin 结构体内部存储参数**

```c
typedef struct Plugin {
    void* user_data;  /* 插件私有数据 */
    int (*execute)(struct Plugin* self);
} Plugin;

/* 参数存在 user_data 里，execute 不接收额外参数 */
/* 由插件自己从 self->user_data 取参数 */
```

**实际应用**：Linux 内核的驱动模型、GStreamer 多媒体框架都用类似的 `void*` 方案。

## 题目3：目录扫描时如何判断一个 .dll/.so 是合法插件？

**问题**：目录扫描时，我们检查文件后缀是 `.dll` 或 `.so` 就认为是插件。但如果用户随便放了一个同后缀的文件（比如 `test.dll`，根本不是插件），加载时会崩溃。怎么判断一个文件是合法的插件？

```c
/* 简单做法：只看后缀，不够安全 */
if (strstr(filename, ".dll")) {
    void* h = dlopen(filename, RTLD_LAZY);
    /* 如果这不是插件，dlsym 会返回 NULL... */
}
```

**思考方向**：
- 插件文件中应该有哪些"标志"？（提示：特定导出符号）
- dlsym 获取不存在的符号会返回什么？
- 能否约定每个插件都导出一个 `get_plugin()` 函数作为"身份标识"？

---

### 参考答案

**方案：约定统一的导出符号作为"插件身份验证"**

每个合法插件都必须导出一个约定的函数（如 `get_plugin`），通过 `dlsym` 检查这个符号是否存在，就能判断文件是否是合法插件：

```c
Plugin* load_plugin_from_file(const char* filepath) {
    /* 1. 加载动态库 */
    void* handle = dlopen(filepath, RTLD_LAZY);
    if (handle == NULL) {
        printf("加载失败: %s\n", dlerror());
        return NULL;
    }

    /* 2. 检查是否有约定的导出符号——身份验证！ */
    Plugin* (*get_plugin)(void) = (Plugin* (*)(void))dlsym(handle, "get_plugin");
    if (get_plugin == NULL) {
        printf("不是合法插件（缺少 get_plugin 导出符号）\n");
        dlclose(handle);
        return NULL;
    }

    /* 3. 获取 Plugin 接口 */
    Plugin* p = get_plugin();
    if (p == NULL) {
        printf("插件返回空指针\n");
        dlclose(handle);
        return NULL;
    }

    /* 4. 进一步检查：init/execute/cleanup 是否为空 */
    if (p->init == NULL || p->execute == NULL || p->cleanup == NULL) {
        printf("插件接口不完整\n");
        dlclose(handle);
        return NULL;
    }

    return p;
}
```

**每个插件文件内部**：

```c
/* deposit_plugin.c —— 合法插件的实现 */
Plugin deposit_plugin = { ... };

/* 必须导出这个函数作为身份标识 */
Plugin* get_plugin(void) {
    return &deposit_plugin;
}
```

**原理**：非插件文件不会导出 `get_plugin` 符号，`dlsym` 返回 NULL，据此过滤非法文件。这种"约定符号"的方式是插件系统的标准做法。

## 题目4：插件注册时为什么要检查重复？不检查会怎样？

**问题**：`plugin_register()` 函数中，我们先遍历链表检查插件名称是否已存在，然后才插入。为什么要检查重复？如果不检查，会发生什么问题？

```c
int plugin_register(Plugin* p) {
    /* 为什么要这段检查？ */
    PluginNode* cur = plugin_head;
    while (cur != NULL) {
        if (strcmp(cur->plugin->name, p->name) == 0) {
            printf("插件[%s]已注册，跳过\n", p->name);
            return -2;
        }
        cur = cur->next;
    }
    /* 然后才创建节点、头部插入... */
}
```

**思考方向**：
- 如果同一个插件被注册两次，遍历链表执行 execute() 时会发生什么？
- 目录扫描时，同一个文件可能被扫描到两次吗？（比如软链接）
- 重复的插件节点会导致什么内存问题？

---

### 参考答案

**不检查重复会导致的问题**：

**问题1：同一插件被执行多次**

```
链表中有两个"存款"插件节点：
head -> [存款] -> [取款] -> [存款] -> NULL

遍历执行 execute(500.0) 时：
  第1次"存款": +500 (余额 10500)
  第2次"取款": -500 (余额 10000)
  第3次"存款": +500 (余额 10500)  ← 不应该执行第二次！
```

同一插件的 `execute()` 被调用两次，操作重复执行，结果错误。

**问题2：内存泄漏**

如果重复注册时创建了新的链表节点（malloc），但两个节点指向同一个 Plugin 实例，在销毁链表时会 free 两次不同的节点。虽然节点本身不冲突（malloc 了不同的内存），但管理混乱——`plugin_count` 统计不准，打印列表出现重复项。

**问题3：目录扫描的重复触发**

实际场景中，目录扫描可能因为以下原因重复加载同一文件：
- 软链接/硬链接导致同一文件出现多次
- 扫描时文件被修改，触发重扫
- 多线程同时扫描

**总结**：注册时检查重复是一种防御性编程，确保每个插件只注册一次，避免重复执行、统计错误和内存管理混乱。虽然检查增加了 O(n) 的遍历成本，但保证了插件系统的正确性。
