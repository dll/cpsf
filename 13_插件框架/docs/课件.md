- 理解插件的**完整生命周期**：`init → start → execute → stop → cleanup` 五阶段

- 实现**插件管理器**：用链表统一管理所有插件的加载/启动/停止/清理

- 掌握**配置化菜单**：菜单项就是链表节点，注册即挂载、卸载即摘除
- 理解**开闭原则**：对扩展开放、对修改关闭——加插件不改主程序
- 理解**框架 vs 库**的本质：**控制反转（IoC）**第一次真正登场
- **把 ATM 升级为完整插件框架：主程序只剩三行调用**


### 六级台阶的一句话区分

| 台阶 | 一句话 | 控制权在谁手上 |
|:---:|:---|:---|
| ① 表达式 | 能算出一个值的代码片段 | 你 |
| ② 函数 | 把一段逻辑封成一个名字，可以反复调用 | 你 |
| ③ 模块 | `.h` 说"能做什么"，`.c` 说"怎么做" | 你 |
| ④ 库 | 编译成二进制，跨项目复用（静态库 / 动态库） | 你 |
| ⑤ 插件 | 运行时才决定加载谁、组装谁 | 你（但由你来决定装配） |
| **⑥ 框架** | **你填插槽，框架在合适的时机回调你** | **框架** |

### 为什么说第⑥级"最特别"

前面五级都有一个共同点：**控制流只向下走**。`main()` 主动调用函数、调用库函数、调用插件函数——你是导演，你决定调用顺序。

到了框架这一级，方向变了：

```
   普通调用（第①~⑤级）             控制反转（第⑥级，本讲）
   ─────────────────────           ─────────────────────────
   main() ──调用──▶ 你的代码         main() ──▶ framework_start()
                                             │
                                             ├─▶ manager_init_all()
                                             │        └─▶ deposit_plugin.init()   ← 框架回调你
                                             └─▶ manager_start_all()
                                                      └─▶ deposit_plugin.start()  ← 框架回调你
```

控制流从 `main` 进入框架，**又从框架"折返"回你写的插件代码**——这个"折返"就是**控制反转（IoC, Inversion of Control）**。

好莱坞原则说得好：

> **Don't call us, we'll call you.** —— 别来找我们，我们会找你。

插件（你）只要填好 5 个函数指针；框架（导演）按状态机在正确的时机回调你。

### 本讲为终点贡献了什么

| 本讲新增的能力 | 具体成果 | 对"加插件不改主程序"的贡献 |
|:---|:---|:---|
| **五阶段生命周期** | `init → start → execute → stop → cleanup` | 顺序不再靠程序员记性，资源不会漏释放 |
| **状态机** | `UNLOADED → … → CLEANED → UNLOADED` | 非法操作被当场拒绝并说明理由 |
| **插件管理器** | `manager_*` 系列：链表 + 批量操作 + 查找执行 | 一句话交代一批，主程序不再逐个调度 |
| **扩展点设计** | 菜单项 / 命令 / 事件 | 插件只填插槽，不必知道框架长什么样 |
| **配置化菜单** | 菜单项 = 链表节点，`menu_handle` 零 `switch` | 新增插件改 0 处菜单代码 |
| **开闭原则落地** | 函数指针 + 链表 + 稳定契约 | 加"转账"只做三次"新增"，没有一次"修改" |

把这六条合起来，得到本讲的标志性成果——**`main.c` 从 60 多行瘦到 3 行**：

```c
int main(void)
{
    framework_start();   /* 初始化 + 注册 + init + start */
    framework_run();     /* 显示菜单 + 交互循环 */
    framework_stop();    /* stop + cleanup + destroy */
    return 0;
}
```

### 还差最后两块拼图

本讲框架已经"骨架完整"，但还有一处是**半成品**：4 个插件是"内置"的（`framework_start()` 里写明注册谁，`create_deposit_plugin()` 直接返回静态结构体地址）。

- 第11讲的 `dlopen` / `dlsym`：让插件真的**从文件里来**；
- 第12讲的目录扫描：让框架自己**发现有哪些插件**。

**第14讲把这两块拼图接进来**：框架自动扫描 `plugins/` 目录、动态加载、按符号取工厂函数——那时连"有哪些插件"都不再由代码决定，**控制反转才真正完整**，整条主线也就走到了终点。

## 一、第12讲留下的三个坑

第12讲做成了两件大事：定义统一 `Plugin` 接口、实现注册与发现。但跑通之后冷静看，还留着三个坑。

### 1.1 坑一：生命周期无人管

第12讲只有三步，而且**全靠调用方自觉**：

```c
if (p->init)    p->init(p);
if (p->execute) p->execute(p, amount);
if (p->cleanup) p->cleanup(p);
```

`main()` 里手动 `plugin_init_all()` → `plugin_execute_all()` → `plugin_cleanup_all()`，顺序全靠程序员记性。插件一多就要出事：init 失败后仍被 execute（在"半成品"状态下处理业务）、cleanup 被调两次（重复释放内存，直接崩溃）、忘记调 cleanup（资源泄漏）。更麻烦的是，想"暂停服务但保留状态"——3 阶段模型根本表达不了。

**根本原因**：3 个阶段描述不了真实状态。"分配了资源"和"对外提供服务"本来是两件事。

### 1.2 坑二：注册靠手动

```c
plugin_register(&deposit_plugin);
plugin_register(&withdraw_plugin);
plugin_register(&query_plugin);
```

说得客气叫"显式注册"，实际是**手工记账**。加了新插件忘记注册，程序照样编译通过、照样启动，只是功能静默消失——最难查的一类 Bug。

### 1.3 坑三：菜单硬编码，加功能要改三处

第2讲的主菜单长这样：

```c
printf("1. 存款\n");
printf("2. 取款\n");
printf("3. 查询余额\n");

switch (choice) {
    case 1: deposit();  break;
    case 2: withdraw(); break;
    case 3: query();    break;
    default: printf("无效选择\n");
}
```

现在要加"转账"，得改三处：`printf` 加一行、`switch` 加一个 `case`、还要保证编号对得上。**加功能 = 改主程序**，这正是开闭原则最反对的事。

> 本讲要用一个"框架"，同时填掉这三个坑。

## 二、完整生命周期：五阶段状态机

### 2.1 从 3 阶段到 5 阶段

| 阶段 | 干什么 | 次数 |
|:---:|:---|:---:|
| `init` | 分配资源、初始化数据（**还不能对外服务**） | 一次 |
| `start` | 开始提供服务（挂菜单、开监听、启线程） | 一次 |
| `execute` | 执行核心业务功能 | **多次** |
| `stop` | 停止服务（摘菜单、关监听、停线程） | 一次 |
| `cleanup` | 释放资源，回到干净状态 | 一次 |

**为什么必须把 init 和 start 分开？** 想象 ATM 开机要加载 4 个插件：存款插件 init 成功、立即可用；取款插件 init 时发现清算文件被占用、失败。此时系统处在"一半可用"的尴尬状态，而失败的插件已经分配了资源，却没有回滚的时机。拆成两阶段就能做**事务式的整体启动**：

```
阶段一：全部 init   → 任何一个失败，整体中止，谁都不许 start
阶段二：全部 start  → 大家一起开始对外服务
```

一句话：**init 是"进货"，start 是"开门营业"；stop 是"打烊"，cleanup 是"清算关店"。**

### 2.2 状态枚举（framework.h 里的契约）

```c
typedef enum {
    PLUGIN_UNLOADED = 0,     /* 未加载 */
    PLUGIN_LOADED,           /* 已加载（已注册到管理器） */
    PLUGIN_INITIALIZED,      /* 已初始化（init 成功） */
    PLUGIN_STARTED,          /* 已启动（start 成功） */
    PLUGIN_STOPPED,          /* 已停止（stop 成功） */
    PLUGIN_CLEANED           /* 已清理（cleanup 成功） */
} PluginState;
```

### 2.3 状态迁移图

```
                     manager_register()
  ┌──────────┐  挂插件链表 + 挂菜单项   ┌──────────┐
  │ UNLOADED │ ───────────────────────▶ │  LOADED  │
  └──────────┘                          └────┬─────┘
        ▲                                    │ manager_init_all() / init()
        │                                    ▼
        │                            ┌───────────────┐
        │                            │  INITIALIZED  │
        │                            └───────┬───────┘
        │                                    │ manager_start_all() / start()
        │                                    ▼
        │                            ┌───────────────┐
        │                            │    STARTED    │◀── execute() 可反复调用
        │                            └───────┬───────┘
        │                                    │ manager_stop_all() / stop()
        │                                    ▼
        │                            ┌───────────────┐
        │                            │    STOPPED    │
        │                            └───────┬───────┘
        │                                    │ manager_cleanup_all() / cleanup()
        │                                    ▼
        │                            ┌───────────────┐
        └────────────────────────────│    CLEANED    │
            manager_destroy()（free） └───────────────┘
```

**管理器的职责就是守着这张图**：状态不对就拒绝，并打印原因。比如对还没 start 的插件调用 execute：

```text
  [执行失败] 插件[存款] 当前状态 LOADED，未启动不可执行
```

**把错误挡在门口，而不是让它跑起来再崩。**

## 三、插件管理器：给插件请一个"管家"

### 3.1 manager 系列接口

| 函数 | 职责 | 状态变化 |
|:---|:---|:---|
| `manager_init()` | 初始化管理器（链表置空） | — |
| `manager_register(p)` | 注册插件，挂插件链表 + 挂菜单项 | `UNLOADED → LOADED` |
| `manager_init_all()` | 批量初始化 | `LOADED → INITIALIZED` |
| `manager_start_all()` | 批量启动 | `INITIALIZED → STARTED` |
| `manager_stop_all()` | 批量停止 | `STARTED → STOPPED` |
| `manager_cleanup_all()` | 批量清理 | `→ CLEANED` |
| `manager_destroy()` | 释放插件链表 | `CLEANED → UNLOADED` |
| `manager_find(name)` | 按名称查找 | 只读 |
| `manager_execute(name, amt)` | 执行插件（要求 `STARTED`） | 只读 |
| `manager_count()` / `manager_print_all()` | 计数 / 打印状态表 | 只读 |

**批量操作的价值**：`main()` 里再也不用写"先 init 谁、再 start 谁"，一句话搞定一批。

### 3.2 链表实现（衔接第8讲）

```c
/* 链表头尾指针 + 计数（模块级 static，外部只能通过函数操作） */
static PluginNode* g_plugin_head  = NULL;
static PluginNode* g_plugin_tail  = NULL;
static int         g_plugin_count = 0;

/* 注册 = 挂到链尾 */
node->plugin = p;
node->next   = NULL;
if (g_plugin_tail == NULL) {          /* 空链表：头尾都指向它 */
    g_plugin_head = node;
    g_plugin_tail = node;
} else {                              /* 非空：挂到尾后，更新尾指针 */
    g_plugin_tail->next = node;
    g_plugin_tail = node;
}
g_plugin_count++;
```

> **一个设计取舍**：第12讲注册用"头部插入 O(1)"，本讲改成"尾部插入"。因为头部插入会让链表顺序与注册顺序**相反**，`manager_print_all()` 打印出来是"转账、查询、取款、存款"，和菜单顺序（1 存款、2 取款…）对不上，演示很别扭。用尾指针 `g_plugin_tail` 依然 **O(1)**，顺序还与注册一致——**要顺序，也要性能**。

### 3.3 批量操作要"尊重状态"

以 `manager_init_all()` 为例，核心是**先检查状态，再决定放不放行**：

```c
if (p->state != PLUGIN_LOADED) {
    printf("  [%-6s] 跳过：当前状态 %s，不允许 init\n", p->name, state_name(p->state));
} else if (p->init(p) == 0) {
    p->state = PLUGIN_INITIALIZED;      /* LOADED → INITIALIZED */
    ok++;
} else {
    printf("  [%-6s] init 失败，保持 LOADED（不会被启动）\n", p->name);
}
```

三个细节：**状态前置校验**（避免重复 init）、**失败不升状态**（后面 `start_all` 自然跳过它，失败会自己"传染"到后续阶段，不必另写判断）、**返回成功条数**（框架据此判断是否全军覆没）。

### 3.4 对照 C++ 的 PluginManager 类

| 面向对象（C++） | C 语言（本讲） |
|:---|:---|
| `class PluginManager { vector<Plugin*> plugins; }` | `static PluginNode* g_plugin_head;` |
| `void add(Plugin* p) { plugins.push_back(p); }` | `int manager_register(Plugin* p)` |
| `manager.plugins.size()` | `manager_count()` |
| `for (auto p : plugins) p->start();` | 遍历链表，`p->start(p)` |
| 对象方法调用 `obj.method()` | 函数 + 隐式全局状态 `manager_xxx()` |

**差别只在语法**：C++ 的"成员方法"在 C 里就是"函数 + 那组 static 链表"。第12讲用结构体 + 函数指针模拟了"多态"，本讲又用文件级 static 变量 + 函数模拟了"类"。**C 语言不是不能面向对象，只是需要你亲手把"类"拼出来。**

## 四、扩展点设计：插件能挂在哪里？

一个框架好不好用，看它留了多少"插槽"。本讲留了三类扩展点：

| 扩展点 | 载体 | 本讲状态 | 典型例子 |
|:---|:---|:---:|:---|
| **菜单项** | `menu_id` + `menu_label` + 菜单链表 | ✅ 已实现 | 存款、取款、查询、转账 |
| **命令** | `manager_find()` + `manager_execute()` | ✅ 已实现 | 命令行 `run deposit 500` |
| **事件** | 预留：插件注册回调，框架在事件发生时回调 | 🔜 第14讲 | 登录成功、余额变动 |

**菜单项扩展点**——插件只填两个字段，剩下交给框架：

```c
static Plugin transfer_plugin = {
    .name       = "转账",
    .menu_id    = 4,          /* ← 菜单编号 */
    .menu_label = "转账",      /* ← 菜单文字 */
    /* ... 五个生命周期函数 ... */
};
```

**插件不知道菜单长什么样，菜单也不知道自己长什么样**——它只是一个链表节点，谁注册，谁就在里面。

**命令扩展点**——同一批插件，给脚本用的调用方式：

```c
/* 不经过菜单，直接按名字找插件执行 */
if (manager_find("存款") != NULL) {
    manager_execute("存款", 500.0);
}
```

同一批插件，能被菜单调用、被命令行调用、被将来的 Web API 调用——**这就是扩展点的意义**。

## 五、配置化菜单：第8讲链表的核心应用

### 5.1 菜单项节点 = 链表节点

```c
typedef struct MenuItem {
    int  id;                        /* 数据域：菜单编号 */
    char label[40];                 /* 数据域：菜单文字 */
    Plugin* plugin;                 /* 数据域：关联的插件（关键！） */
    struct MenuItem* next;          /* 指针域：下一个菜单项 */
} MenuItem;
```

**和普通链表唯一的不同**：多了 `plugin` 指针，把"用户看到的一行字"和"背后干活的插件"挂在一起。有了它，菜单处理就变成纯粹的**查表 + 多态**。

### 5.2 硬编码 vs 配置化

```c
/* 第2讲：硬编码 */
printf("1. 存款\n");
printf("2. 取款\n");
switch (choice) {
    case 1: deposit(amount);  break;
    case 2: withdraw(amount); break;
}

/* 第13讲：配置化 —— 显示（遍历链表） */
while (cur) { printf("  %d. %s\n", cur->id, cur->label); cur = cur->next; }

/* 第13讲：配置化 —— 分发（查表 + 多态） */
while (cur) {
    if (cur->id == choice) return manager_execute(cur->plugin->name, amount);
    cur = cur->next;
}
```

**没有 switch，没有 `case 1`，没有一处写着"存款"。** 菜单处理函数从"知道所有功能"变成"什么功能都不知道"——这是极其重要的进步。

### 5.3 增删菜单，就是链表增删

| 操作 | 用户视角 | 链表视角 | 代码 |
|:---|:---|:---|:---|
| 挂载 | 菜单多一行 | 尾插一个节点 | `menu_add(id, label, plugin)` |
| 摘除 | 菜单少一行 | 摘掉一个节点 | `menu_remove(id)` |
| 显示 | 看到菜单 | 遍历打印 | `menu_show()` |
| 分发 | 选了个功能 | 查找 + 多态调用 | `menu_handle(choice, amount)` |

**注册即挂菜单**——`manager_register()` 的最后一步：

```c
if (p->menu_id != 0) {
    menu_add(p->menu_id, p->menu_label, p);   /* 自动挂载，插件不写菜单代码 */
}
```

**卸载即摘菜单**——`menu_remove(3)` 一句就摘掉"查询余额"：

```text
  [菜单] 已摘除菜单项： 3. 查询余额
```

主程序一行未改。这就是"配置化"三个字的分量。

### 5.4 收益与代价

| 维度 | 硬编码 switch | 配置化链表 |
|:---|:---|:---|
| 加功能 | 改 3 处（打印/分支/编号） | **改 0 处**（插件自带 id/label） |
| 删功能 | 容易残留死分支 | `menu_remove(id)` 一句 |
| 可读性 | 一眼看懂 | 需理解"数据驱动"，初看抽象 |
| 运行开销 | 零开销 | 多一次 O(n) 遍历（n 很小，可忽略） |
| 出错风险 | 编号重复、漏改 | 编号重复会被 `menu_add` 拒绝并打印原因 |

**结论**：功能少且几乎不变的小程序，硬编码更简单；只要功能会持续增长，配置化就一定赢。而"功能会持续增长"——正是 ATM 系统的宿命，也是所有真实系统的宿命。

## 六、开闭原则：对扩展开放，对修改关闭

> **对扩展开放**：可以增加新功能；
> **对修改关闭**：增加新功能**不需要改已有代码**。

### 6.1 加"转账"插件，到底改了什么？

本讲相对第12讲新增了"转账"，真实改动只有三处，且**全部是"新增"**：

| # | 改动 | 性质 |
|:--:|:---|:---|
| 1 | 新建 `plugin_transfer.c` | 新增（扩展） |
| 2 | `plugins.h` 加一行 `create_transfer_plugin` 声明 | 新增（扩展） |
| 3 | `framework_start()` 加一行 `manager_register(...)` | 新增（扩展） |

**没有改动的地方**（这才是重点）：`menu_show()` 不知道有转账，照样显示；`menu_handle()` 不知道有转账，照样分发；`main.c` 完全不知道转账存在；`framework.h` 契约未变。

### 6.2 开闭原则在 C 语言中如何落地

| 支柱 | 本讲对应物 | 作用 |
|:---|:---|:---|
| **函数指针（多态）** | `Plugin` 里的 5 个函数指针 | 让"调用"与"实现"解耦 |
| **链表（数据驱动）** | 插件链表 + 菜单链表 | 让"结构"由数据决定，而非由代码决定 |
| **稳定的接口契约** | `framework.h` 不可变 | 让扩展点长期可靠 |

回顾演进路径，我们一直在向开闭原则靠拢：

```
第2讲   if-else 硬编码菜单           → 加功能必须改主程序       ❌
第7讲   结构体 + 函数指针             → 行为可以"装"进去         ⚠️
第12讲  Plugin 接口 + 注册            → 能统一调用，菜单仍硬编码  ⚠️
第13讲  框架 + 配置化菜单 + 生命周期   → 加功能零改动主程序       ✅
```

## 七、框架 vs 库：控制反转（IoC）第一次登场

### 7.1 一眼看穿的差别

| | 库（Library） | 框架（Framework） |
|:---|:---|:---|
| 谁调用谁 | **你调用库** | **框架调用你** |
| 主程序角色 | 导演，指挥每一步 | 启动器，只说"开始/结束" |
| 控制权 | 在你手上 | 在框架手上 |
| 典型代表 | `libc`、`libaccount.a`、`json-c` | Qt、Spring、VS Code、本讲 framework |
| 扩展方式 | 你自己写代码调它 | 你填"插槽"，框架来调你 |

**一句话**：库是你去它的工具箱里拿工具；框架是它给你一张表格，让你填上名字，然后按表格来找你。

### 7.2 main.c 的"三行震撼"

```c
int main(void)
{
    framework_start();   /* 初始化 + 注册 + init + start */
    framework_run();     /* 显示菜单 + 交互循环 */
    framework_stop();    /* stop + cleanup + destroy */
    return 0;
}
```

第12讲的 `main()` 有 60 多行，手动注册、手动 init、手动执行、手动清理；本讲只有三句——**因为控制权交出去了**。

### 7.3 控制反转的调用链

```
① 你调用库（普通函数调用，控制权在你）
   main()  ──── 调用 ───▶  account_deposit()

② 库被你链接进程序（第9/10讲）

③ 框架加载插件（第11讲 dlopen，本讲为静态注册）
   framework  ──── 加载 ───▶  create_deposit_plugin()

④ 框架回调你的代码（控制反转！控制权交给框架）
   manager_init_all()   ────▶  deposit_plugin.init()
   manager_start_all()  ────▶  deposit_plugin.start()
   menu_handle(1, 500.0) ───▶  deposit_plugin.execute()
   manager_stop_all()   ────▶  deposit_plugin.stop() / cleanup()
```

注意第 ④ 步的方向：控制流从 `main` 进入框架，**又从框架"折返"回你写的插件代码**。这个"折返"就是反转。好莱坞原则说得好：

> **Don't call us, we'll call you.** —— 别来找我们，我们会找你。

插件（你）只要填好 5 个函数指针；框架（导演）按状态机在正确的时机回调你。

### 7.4 代价：反转不是免费的

| 收益 | 代价 |
|:---|:---|
| 加功能零改动主程序，扩展性极强 | 调用链被"藏"起来，debug 要先找"谁回调了我" |
| 生命周期由框架统一保证，不会漏 | 必须严格遵守契约，状态不对就被拒绝 |
| 插件可独立开发、独立测试 | 需要提前设计好扩展点，设计成本前置 |

**这就是架构的常态：用"前期的设计成本"换"后期的扩展自由"。**

### 8.3 关键代码：注册即挂菜单

```c
int manager_register(Plugin* p)
{
    if (p == NULL) { printf("[注册失败] 插件指针为空，拒绝注册\n"); return -1; }

    if (p->execute == NULL) {          /* 拒绝"不是插件"的东西 */
        printf("[注册失败] 插件[%s] 没有实现 execute()，不是合法插件\n", p->name);
        return -1;
    }
    /* 遍历链表 strcmp 比较，同名插件拒绝重复注册 */
    /* malloc 节点 + 尾插 + g_plugin_count++ */

    p->state = PLUGIN_LOADED;          /* UNLOADED → LOADED */

    if (p->menu_id != 0) {             /* 配置化菜单：注册即挂载 */
        menu_add(p->menu_id, p->menu_label, p);
    }
    return 0;
}
```

**四道关卡全部带"人话"提示**：错在哪、为什么拒绝，一目了然。

### 8.4 关键代码：菜单分发（零 switch）

```c
int menu_handle(int choice, double amount)
{
    MenuItem* cur = g_menu_head;

    while (cur != NULL) {
        if (cur->id == choice) {
            if (cur->plugin == NULL) {
                printf("  [菜单] 编号 %d 未关联插件，无法执行\n", choice);
                return -1;
            }
            return manager_execute(cur->plugin->name, amount);  /* 查表 + 多态 */
        }
        cur = cur->next;
    }
    printf("  [菜单] 无效选择：没有编号 %d 的功能\n", choice);
    return -1;
}
```

**请数一数这里面有几个 `case`**：答案是 **0 个**。这个函数对未来新增的插件完全"无知"，却能为它们正确分发。

## 💭 思考题

### 题目1：init 与 start 为什么要分开？

`init` 成功后插件已经"可用"了，为什么还要多一个 `start`？请结合"ATM 开机时 4 个插件中有一个初始化失败"这个场景说明。

<details>
<summary>参考答案</summary>

**核心：`init` 是"准备"，`start` 是"对外服务"，这是两种不同性质的状态。**

只有 3 阶段时，init 成功就意味着"立即可用"。若 4 个插件中有一个 init 失败，系统就处在"部分可用"状态（能存款不能取款），用户看到的是功能残缺的 ATM；更糟的是失败插件的资源已分配，却没有回滚时机。

拆出 `start` 后，启动变成两阶段提交：**全部 init 成功 → 才允许全部 start**。好处有三条：① **可以整体回滚**，任一插件 init 失败则 `framework_start()` 返回 -1，主程序不进入交互循环；② **"准备好了"与"开始服务"解耦**，像连接池先预热、再放开流量；③ **多了 `stop` 台阶**，`stop` 可逆（还能再 start），`cleanup` 不可逆，两级台阶让"暂停服务"成为可能，3 阶段做不到。

一句话：**init 是进货，start 是开门营业。没有进货不该开门，货到了也不一定立刻开门。**
</details>

### 题目2：配置化菜单的收益与代价

配置化之后加功能不用改主程序了，但这方案是"免费"的吗？请从代码复杂度、可读性、运行开销、出错风险分析，并回答什么情况下反而应该用硬编码菜单。

<details>
<summary>参考答案</summary>

**收益**：扩展性（改 0 处主程序）、一致性（显示与处理共用同一份数据）、可测试（菜单是纯数据）、编号冲突自动拒绝。

**代价**：代码复杂度上升（多一个结构体 + 5 个函数）；可读性下降（想知道系统有哪些功能，得看每个插件的 `menu_id`，不像 switch 一眼看全）；运行开销 O(n) 遍历；调试链变长（用户点 3 → 菜单链表 → 插件指针 → `manager_execute` → 插件 `execute`）；出错风险转移到"数据"（`menu_id` 填重、填 0 都会出问题）。

**反而应该硬编码的情况**：① 功能极少且稳定（如"1 开始 2 退出"的小工具），杀鸡用牛刀；② 性能敏感且菜单项上千，需要数组或哈希索引；③ 菜单结构复杂（二级菜单、动态灰置、权限交叠），纯链表表达力不够；④ 一次性脚本或教学演示，可读性优先。

**结论**：配置化不是"更高级所以更好"，而是**用前期抽象成本换后期扩展自由**。判断标准只有一条：**这个菜单会持续增长吗？**
</details>

### 题目3：开闭原则在 C 语言中如何落地？

有人说"开闭原则是面向对象的东西，C 语言没有继承多态，谈不了开闭原则"。这个说法对吗？请以本讲框架为例说明。

<details>
<summary>参考答案</summary>

**说法是错的。** 开闭原则是**设计目标**，不是某种语言特性；任何图灵完备的语言都能实现，只是手段不同。C 语言靠三根支柱：

**① 函数指针 = 多态**：`menu_handle()` 里写的是 `cur->plugin->execute(cur->plugin, amount)`，**编译期根本不知道会调用哪个函数**，要等运行时看链表里挂的是谁。编译期绑定换成运行期绑定，这就是 C 语言的多态。

**② 链表 = 数据驱动**：功能清单不再写死在 `switch` 里，而是存在链表中。**代码表达"怎么处理"，数据表达"处理什么"**。加功能 = 加一个节点，代码从来就不认识你。

**③ 稳定契约 = 可扩展的前提**：`framework.h` 冻结语义，扩展才能在契约之上生长。如果框架天天改接口，插件开发者永远在追着改。

本讲的证据：三次改动（新文件、加声明、加注册）**全部是"新增"，没有一行"修改"**——这正是开闭原则的定义。

**代价也要说清**：没有编译期检查（漏填 `execute` 只能靠运行时校验）；没有访问控制；手动管理 `malloc/free`。所以更准确的说法是：**C 语言做开闭原则"能做但更费手"，而不是做不到**。Linux 内核、Redis、Nginx 全都重度使用函数指针表 + 回调注册——那就是 C 语言版的开闭原则。
</details>

### 题目4：框架与库的本质区别

请用"控制反转（IoC）"解释框架和库的区别，并用本讲与第12讲的 `main.c` 做对比说明。

<details>
<summary>参考答案</summary>

**一句话区别：库是"你调用它"，框架是"它调用你"。** 控制权在谁手上，就是分界线。

第12讲的 `main()` 是典型"库的用法"——**主程序是导演**：手动 `plugin_manager_init()`、手动 `plugin_register()`、手动 `plugin_init_all()`、手动 `plugin_find()` 后执行、手动 `plugin_cleanup_all()`，60 多行，每一步都由主程序发起。

第14讲的 `main()` 是典型"框架的用法"——**主程序只是启动器**：`framework_start()` / `framework_run()` / `framework_stop()` 三行。主程序不知道有"存款"这个插件，也不知道插件有几个，控制权完全交出去了。

**控制反转具体反在哪里？** 正常控制流是 `main()` 主动调用各函数一路向下。反转后：

```
main() → framework_start() → manager_init_all()
                                   ├─▶ deposit_plugin.init()    ← 框架回调你的代码
                                   └─▶ withdraw_plugin.init()   ← 框架回调你的代码
```

控制流从 `main` 进入框架，**又从框架"折返"回你写的插件代码**。这个"折返"就是反转。即好莱坞原则：**Don't call us, we'll call you**——演员（插件）只需登记资料（函数指针），导演（框架）按剧本（状态机）在正确时机喊人。

**补充**：本讲框架还只是"半自动"——插件是**静态注册**的（`framework_start()` 里写明注册哪 4 个）。第11讲 `dlopen` + 第12讲目录扫描才是完全体。**第14讲会整合**：框架自动扫描 `plugins/` 目录、`dlopen` 加载、`dlsym` 取工厂函数——那时连"有哪些插件"都不再由代码决定，控制反转才真正完整。
</details>

## 📝 小结

### 一句话总结

**插件框架用状态机管住生命周期、用管理器管住秩序、用配置化菜单管住扩展点——把控制权从主程序收归框架，于是"加插件不改主程序"从口号变成了现实。**

### 六个知识点

| # | 知识点 | 关键句 |
|:--:|:---|:---|
| 1 | 五阶段生命周期 | `init → start → execute(多次) → stop → cleanup`，init 准备、start 营业 |
| 2 | 状态机 | `UNLOADED → LOADED → INITIALIZED → STARTED → STOPPED → CLEANED → UNLOADED` |
| 3 | 插件管理器 | `manager_*` 系列：链表 + 批量 init/start/stop/cleanup + find/execute |
| 4 | 扩展点设计 | 菜单项 / 命令 / 事件，本质都是"链表 + 回调" |
| 5 | 配置化菜单 | 菜单项 = 链表节点；注册即挂载、卸载即摘除；`menu_handle` 零 switch |
| 6 | 框架 vs 库 | 库是你调用它，框架是它调用你 —— **控制反转 IoC** |
