## 题目1：`init` 与 `start` 为什么要分开？

**背景**：第12讲的插件只有三个阶段——`init → execute → cleanup`。本讲把它扩成五个阶段，中间插进了 `start` 和 `stop`：

```c
int  (*init)(struct Plugin* self);                    /* 分配资源 */
int  (*start)(struct Plugin* self);                   /* 开始对外服务 */
int  (*execute)(struct Plugin* self, double amount);  /* 执行核心功能 */
int  (*stop)(struct Plugin* self);                    /* 停止对外服务 */
void (*cleanup)(struct Plugin* self);                 /* 释放资源 */
```

看起来 `init` 成功之后插件就已经"能用"了，为什么还要多一个 `start`？请结合"ATM 开机时 4 个插件中有一个初始化失败"这个场景说明。

**思考方向**：
- 只有 3 阶段时，某个插件 `init` 失败会造成什么局面？剩下 3 个插件该不该启动？
- 已经 `init` 成功的插件要不要"回滚"？3 阶段模型里有没有回滚的时机？
- "暂停服务但保留状态"这种需求，3 阶段能不能表达？`stop` 和 `cleanup` 在可逆性上有什么不同？

---

### 参考答案

**核心：`init` 是"准备"，`start` 是"开门营业"，这是两种性质完全不同的状态。**

只有 3 阶段时，`init` 成功就意味着"立即可用"。若 4 个插件中取款插件 `init` 失败，系统会卡在"一半可用"的尴尬状态——用户看到的是一个功能残缺的 ATM；更糟的是，失败插件可能已经分配了部分资源，却没有回滚的时机。

拆出 `start` 之后，启动变成**两阶段提交**：

```
阶段一：全部 init   →  任何一个失败，整体中止，谁都不许 start
阶段二：全部 start  →  大家一起开始对外服务
```

好处有三条：

1. **可以整体回滚**。任一插件 `init` 失败，`framework_start()` 返回 -1，主程序不进入交互循环，用户不会看到半残的系统。
2. **"准备好了"与"开始服务"解耦**。像连接池先预热、再放开流量；数据库先建连接、再接受查询。
3. **多出 `stop` 这一级台阶，服务变得可逆**。`stop` 之后还能再 `start`（暂停服务、灰度下线、热升级）；`cleanup` 不可逆，走完就回到干净状态。3 阶段模型里没有这级台阶，"暂停服务"根本无从表达。

本讲 `src/framework.c` 的实现正是按这个思路写的：

```c
/* manager_init_all()：只允许 LOADED → INITIALIZED */
if (p->state != PLUGIN_LOADED) {
    printf("  [%-6s] 跳过：当前状态 %s，不允许 init\n", p->name, state_name(p->state));
} else if (p->init(p) == 0) {
    p->state = PLUGIN_INITIALIZED;
}   /* init 失败不升状态 → start_all 自然跳过它 */
```

**一句话**：`init` 是进货，`start` 是开门营业。没有进货不该开门；货到了，也不一定立刻开门。

## 题目2：配置化菜单的收益与代价

**背景**：第2讲的菜单是硬编码的，加一个功能要改三处；本讲把菜单项做成了链表节点：

```c
typedef struct MenuItem {
    int  id;                        /* 菜单编号 */
    char label[40];                 /* 菜单文字 */
    Plugin* plugin;                 /* 关联的插件（关键！） */
    struct MenuItem* next;
} MenuItem;
```

显示菜单 = 遍历链表；分发 = 查表 + 多态，一行 `case` 都没有。加"转账"功能改 0 处主程序。

但这套方案是"免费"的吗？请从代码复杂度、可读性、运行开销、出错风险四个角度分析，并回答什么情况下反而应该用硬编码菜单。

**思考方向**：
- 想知道"系统一共有哪些功能"，硬编码和配置化分别要怎么看？哪个更快？
- 多一次链表遍历有多少成本？菜单项上千时还够用吗？
- 原来"编码错误"出现在 `switch` 里，现在转移到了哪里？
- 一个只有"1 开始、2 退出"的小工具，值得上链表吗？

---

### 参考答案

**收益**

| 维度 | 说明 |
|:---|:---|
| 扩展性 | 加功能改 0 处主程序，插件自带 `menu_id` / `menu_label` |
| 一致性 | 显示与分发共用同一份数据，不会"显示了却点不动" |
| 可测试 | 菜单是纯数据，可以脱离 UI 单独构造和断言 |
| 容错 | 编号重复会被 `menu_add()` 当场拒绝，并打印占用者 |

**代价**

| 维度 | 说明 |
|:---|:---|
| 代码复杂度 | 多一个结构体 + 5 个函数（`menu_add/remove/show/handle/destroy`） |
| 可读性 | 想知道系统有哪些功能，得逐个插件看 `menu_id`，不像 `switch` 一眼看全 |
| 运行开销 | 每次分发多一次 O(n) 遍历；菜单项上千时需要数组或哈希索引 |
| 调试链 | 用户点 3 → 菜单链表 → 插件指针 → `manager_execute` → 插件 `execute`，链路变长 |
| 出错风险转移 | 风险从"忘写 case"变成"`menu_id` 填重、填 0"，从编码错误变成数据错误 |

**反而应该硬编码的情况**

1. **功能极少且稳定**：如"1 开始、2 退出"的小工具，杀鸡不必用牛刀。
2. **性能敏感且菜单项极多**：上千项菜单需要数组下标或哈希索引，链表 O(n) 不合适。
3. **菜单结构复杂**：二级菜单、动态灰置、权限交叠，纯链表表达力不够，需要更结构化的描述。
4. **一次性脚本或课堂演示**：可读性优先，让读者一眼看全。

**结论**：配置化不是"更高级所以更好"，而是**用前期的抽象成本，换后期的扩展自由**。判断标准只有一条——**这个菜单会持续增长吗？**"功能会持续增长"正是 ATM 系统的宿命，也是所有真实系统的宿命。

## 题目3：开闭原则在 C 语言中如何落地？

**背景**：有人说"开闭原则是面向对象的东西，C 语言没有继承多态，谈不了开闭原则"。

但本讲的框架确实做到了：新增"转账"插件，相对第12讲只有三处改动，且**全部是"新增"**——

| # | 改动 | 性质 |
|:--:|:---|:---|
| 1 | 新建 `plugin_transfer.c` | 新增（扩展） |
| 2 | `plugins.h` 加一行 `create_transfer_plugin` 声明 | 新增（扩展） |
| 3 | `framework_start()` 加一行 `manager_register(...)` | 新增（扩展） |

没有改动的地方才是重点：`menu_show()` 不知道有转账，照样显示；`menu_handle()` 不知道有转账，照样分发；`main.c` 完全不知道转账存在；`framework.h` 契约未变。

这个说法对吗？请以本讲框架为例说明。

**思考方向**：
- `menu_handle()` 里的 `cur->plugin->execute(cur->plugin, amount)` 是在编译期确定调用谁，还是运行期？
- 功能清单存在哪里？代码和数据的职责分别是什么？
- 如果框架天天改接口，插件开发者会怎样？
- C 语言做开闭原则，要付出什么代价？

---

### 参考答案

**这个说法是错的。** 开闭原则是**设计目标**，不是某种语言的特性；任何图灵完备的语言都能实现，只是手段不同。

C 语言靠三根支柱撑起开闭原则：

**① 函数指针 = 多态**

```c
int menu_handle(int choice, double amount) {
    MenuItem* cur = g_menu_head;
    while (cur != NULL) {
        if (cur->id == choice) {
            return manager_execute(cur->plugin->name, amount);
        }                       /* 查表 + 多态：编译期不知道是谁 */
        cur = cur->next;
    }
    return -1;
}
```

这里面的 `case` 有几个？**0 个**。编译期根本不知道会调用哪个 `execute`，要等运行时看链表里挂的是谁。**编译期绑定换成运行期绑定**，这就是 C 语言的多态，也正是 C++ 虚函数表（vtable）的手工版本。

**② 链表 = 数据驱动**

功能清单不再写死在 `switch` 里，而是存在链表中。**代码表达"怎么处理"，数据表达"处理什么"**。加功能 = 加一个节点，代码从来就不认识你。同理，菜单的增删也不过是链表节点的增删：

| 操作 | 用户视角 | 链表现角 | 代码 |
|:---|:---|:---|:---|
| 挂载 | 菜单多一行 | 尾插一个节点 | `menu_add(id, label, plugin)` |
| 摘除 | 菜单少一行 | 摘掉一个节点 | `menu_remove(id)` |
| 显示 | 看到菜单 | 遍历打印 | `menu_show()` |
| 分发 | 选了个功能 | 查找 + 多态调用 | `menu_handle(choice, amount)` |

**③ 稳定契约 = 可扩展的前提**

`framework.h` 冻结语义（函数名、参数、结构体字段、状态枚举一律不改），扩展才能在契约之上生长。如果框架天天改接口，插件开发者永远在追着改，开闭原则无从谈起。

**代价也要说清**：没有编译期检查（漏填 `execute` 只能靠运行时校验）、没有访问控制、需要手动 `malloc` / `free`。所以更准确的说法是：**C 语言做开闭原则"能做，但更费手"**，而不是做不到。Linux 内核的 `file_operations`、Redis 的命令表、Nginx 的模块体系，全都是"函数指针表 + 回调注册"——那就是 C 语言版的开闭原则。

## 题目4：框架与库的本质区别

**背景**：第12讲的 `main()` 有 60 多行，手动注册、手动 `init`、手动执行、手动清理；第13讲只剩三句：

```c
int main(void)
{
    framework_start();   /* 初始化 + 注册 + init + start */
    framework_run();     /* 显示菜单 + 交互循环 */
    framework_stop();    /* stop + cleanup + destroy */
    return 0;
}
```

请用"控制反转（IoC）"解释框架和库的区别，并用本讲与第12讲的 `main.c` 做对比说明。

**思考方向**：
- 第12讲的 `main()` 和第14讲的 `main()`，谁在"指挥"？
- 控制流的方向发生了什么变化？"折返"发生在哪一步？
- 好莱坞原则 "Don't call us, we'll call you" 在这里对应什么？
- 控制反转有没有代价？

---

### 参考答案

**一句话区别：库是"你调用它"，框架是"它调用你"。** 控制权在谁手上，就是分界线。

| | 库（Library） | 框架（Framework） |
|:---|:---|:---|
| 谁调用谁 | 你调用库 | 框架调用你 |
| 主程序角色 | 导演，指挥每一步 | 启动器，只说"开始 / 结束" |
| 控制权 | 在你手上 | 在框架手上 |
| 典型代表 | `libc`、`libaccount.a`、`json-c` | Qt、Spring、VS Code、本讲 framework |
| 扩展方式 | 你自己写代码调它 | 你填"插槽"，框架来调你 |

**第12讲的 `main()` 是典型"库的用法"**：主程序是导演——手动 `plugin_manager_init()`、手动 `plugin_register()`、手动 `plugin_init_all()`、`plugin_find()` 后执行、手动 `plugin_cleanup_all()`，60 多行，每一步都由主程序发起。

**第14讲的 `main()` 是典型"框架的用法"**：主程序只是启动器——三行。主程序不知道有"存款"这个插件，不知道一共有几个插件，控制权完全交出去了。

**控制反转具体反在哪里？**

```
main() → framework_start() → manager_init_all()
                                   ├─▶ deposit_plugin.init()    ← 框架回调你的代码
                                   └─▶ withdraw_plugin.init()   ← 框架回调你的代码
```

正常控制流是 `main()` 主动调用各函数一路向下。反转之后，控制流从 `main` 进入框架，**又从框架"折返"回你写的插件代码**。这个"折返"就是反转。即好莱坞原则：**Don't call us, we'll call you**——演员（插件）只需登记资料（函数指针），导演（框架）按剧本（状态机）在正确的时机喊人。

**代价：反转不是免费的**

| 收益 | 代价 |
|:---|:---|
| 加功能零改动主程序，扩展性极强 | 调用链被"藏"起来，debug 要先找"谁回调了我" |
| 生命周期由框架统一保证，不会漏 | 必须严格遵守契约，状态不对就被拒绝 |
| 插件可独立开发、独立测试 | 需要提前设计好扩展点，设计成本前置 |

**补充**：本讲框架还只是"半自动"——插件是**静态注册**的（`framework_start()` 里写明注册哪 4 个）。第11讲 `dlopen` + 第12讲目录扫描才是完全体。**第14讲会整合**：框架自动扫描 `plugins/` 目录、`dlopen` 加载、`dlsym` 取工厂函数——那时连"有哪些插件"都不再由代码决定，控制反转才真正完整。
