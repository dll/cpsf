# 第一部分 · 完整项目实战

## 1.1 需求：一个可插拔的 ATM 系统

需求只有两句话：

> 做一个 ATM，有**存款 / 取款 / 查询余额 / 转账**四项功能，
> 并且——**增加第五项功能时，不改主程序一行代码。**

第一句是老需求，从第2讲就开始了；第二句才是本讲真正的门槛。它意味着：

- 主程序不能 `#include "deposit.h"`，否则就被绑死了；
- 主程序不能写 `switch (choice) { case 1: deposit(); }`，否则每加一个功能都要改；
- 主程序甚至**不能知道**"一共有几个功能"——功能清单必须是**运行时**才知道的。

结论只有一条：**功能必须以"插件"的形态，在运行时从外部装进来。**

| 约束 | 含义 | 来自哪一讲 |
|:---|:---|:---|
| 统一接口 | 所有插件长得一样，框架用同一行代码调用它们 | 第12讲 |
| 五阶段生命周期 | init / start / execute / stop / cleanup，顺序由框架管 | 第13讲 |
| 运行时加载 | 插件是一个个 `.dll` 文件，扫目录后按需装载 | 第11讲 |
| 数据共享 | 主程序和所有插件看到同一份账户数据 | 第10讲（共享库） |
| 配置化菜单 | 菜单项由插件自己声明，主程序零硬编码 | 第8讲（链表） |
| 优雅降级 | 某个插件加载失败，框架照常启动，只少一项功能 | 本讲新增 |

│  └──────────────┘ └──────────────┘ └──────────────────────┘  │
│   统一契约：plugin.h（Plugin 结构体 + get_plugin 入口符号）     │
└───────────────────────────┬──────────────────────────────────┘

┌───────────────────────────▼──────────────────────────────────┐
│ 第三层：插件层 plugins/*.dll                                   │
│  ┌────────┐ ┌────────┐ ┌────────┐ ┌────────┐                  │
│  │存款插件 │ │取款插件 │ │查询插件 │ │转账插件 │ ← 可无限增加    │
│  │menu=1  │ │menu=2  │ │menu=3  │ │menu=4  │                  │
│  └────────┘ └────────┘ └────────┘ └────────┘                  │
│   插件只关心自己的业务，不碰 UI、不碰主循环                     │
└───────────────────────────┬──────────────────────────────────┘
                            │ 只依赖 account.h / transaction.h
┌───────────────────────────▼──────────────────────────────────┐
│ 第四层：账务核心 atmcore.dll（共享库，全局唯一一份数据）        │
│   account.c 账户数组（1001 张三 / 1002 李四）                  │
│   transaction.c 流水链表（来一笔 malloc 一个节点，挂链尾）      │
└──────────────────────────────────────────────────────────────┘
```

**为什么第四层必须是"共享库"而不是静态库？** 这是本讲最容易踩的坑：

> Windows 下每个 DLL 里的全局变量都是**各自一份**。如果 `account.c` 被分别编进四个插件，
> "存款"插件存的 500 元就存在**它自己那份** `accounts[]` 里，而"查询"插件读的是
> **它自己那份** `accounts[]`，读到的还是 10000 元。

所以账务数据必须放进**所有模块共享的动态库** `atmcore.dll`。
这正是第9讲（静态库）→ 第10讲（动态库）那一步抽象在工程上的真实价值：
**抽象不是为了好写，是为了让数据只有一个真相。**

│   ├── build.bat / Makefile         ← 一键构建
│   ├── atmcore.dll / libatmcore.a   ← 构建产物：共享账务核心 + 导入库
│   └── atm_framework.exe            ← 构建产物：主程序
└── docs/  video/                    ← 课件与讲解视频
```

**看目录就能读出架构：**

- `plugin.h` 在 `src/` 根目录 → 它是**所有模块的共同契约**，不是某个模块的私有文件；
- `plugins/` 与 `framework.c` **平级** → 插件不是框架的一部分，是**外挂**；
- `account.c / transaction.c` 单独列出 → 它们是**被复用的一方**，不是主程序的内部实现；
- `dynamic_loader.*` 独占一层 → 平台差异被**隔离**，不污染框架主体。

## 1.4 构建流程

三步走，顺序不能乱（第二步要链接第一步产出的导入库）：

```bat
REM 第 1 步：共享账务核心
gcc -Wall -O2 -shared -o atmcore.dll account.c transaction.c ^
    -Wl,--out-implib,libatmcore.a -DATMCORE_BUILD

REM 第 2 步：四个插件 DLL
for %%P in (deposit withdraw query transfer) do (
    gcc -Wall -O2 -shared -DPLUGIN_DLL -o plugins\%%P_plugin.dll ^
        plugins\%%P_plugin.c -I. -Iplugins -L. -latmcore
)

REM 第 3 步：主程序
gcc -Wall -O2 -o atm_framework.exe main.c framework.c dynamic_loader.c ^
    plugins\deposit_plugin.c plugins\withdraw_plugin.c plugins\query_plugin.c ^
    plugins\transfer_plugin.c -I. -Iplugins -L. -latmcore
```

**细节一：`-DATMCORE_BUILD` 只出现在第一步。** 一个宏完成"我是生产者还是消费者"的身份切换：

```c
#ifdef _WIN32
    #ifdef ATMCORE_BUILD
        #define ATMCORE_API __declspec(dllexport)   /* 编译库时：导出 */
    #else
        #define ATMCORE_API __declspec(dllimport)   /* 别人引用：导入 */
    #endif
#else
    #define ATMCORE_API
#endif
```

**细节二：`-DPLUGIN_DLL` 只出现在第二步。** 同一份源码，编成 DLL 时是"外挂插件"，
编进主程序时是"内置回退实现"：

```c
/* 只有作为动态库编译时，才导出框架约定的入口符号 */
#ifdef PLUGIN_DLL
PLUGIN_EXPORT Plugin* get_plugin(void) { return &g_deposit_plugin; }
#endif
```

**细节三：第三步要把插件源码一起编进来**，为的是拿到 `xxx_plugin_create()`，
作为"内置回退插件"登记进框架——它们只在对应 DLL 缺失时才真正上场。

## 1.6 关键代码走读

### 1.6.1 框架入口：`main.c`

```c
int main(void)
{
    /* 登记"内置回退插件"：同名 DLL 加载失败时启用它们 */
    Plugin* builtins[4];
    builtins[0] = deposit_plugin_create();
    builtins[1] = withdraw_plugin_create();
    builtins[2] = query_plugin_create();
    builtins[3] = transfer_plugin_create();
    framework_set_builtins(builtins, 4);

    /* 框架三段式：启动 → 运行 → 停止 */
    framework_start();   /* 动态加载 + 注册 + init_all + start_all */
    framework_run();     /* 菜单交互循环 */
    framework_stop();    /* stop_all + cleanup_all + 卸载 DLL */

    return 0;
}
```

整个 `main.c` 没有出现一次"存款""取款""查询""转账"，也没有出现过一次 `switch`。
它只做两件事：**登记兜底方案**、**把控制权交给框架**。

| 讲次 | `main()` 长什么样 | 控制权在谁手上 |
|:---:|:---|:---|
| 第2讲 | 一个大 `while` + `switch`，业务逻辑全在里面 | 主程序 |
| 第13讲 | 三行：`framework_start / run / stop`，功能静态注册 | 框架（局部） |
| 第14讲 | 三行 + 一段回退登记，功能**运行时**从目录发现 | 框架（完整） |

从第2讲到第14讲，`main()` 从几十行瘦到三行，少掉的全是"调度代码"。
这就是**控制反转**最直观的度量方式。

### 1.6.2 插件接口：`plugin.h`

```c
typedef struct Plugin {
    /* ---- 元数据 ---- */
    char name[32];              /* 插件名称（唯一标识） */
    char version[16];           /* 版本号 */
    char description[64];       /* 功能描述 */
    int  menu_id;               /* 菜单编号（0 表示不挂菜单） */
    char menu_label[40];        /* 菜单显示文字 */
    int  need_amount;           /* 1=框架先读金额；0=插件自己读 */

    /* ---- 生命周期方法（函数指针 = 行为） ---- */
    int  (*init)(struct Plugin* self);
    int  (*start)(struct Plugin* self);
    int  (*execute)(struct Plugin* self, double amount);
    int  (*stop)(struct Plugin* self);
    void (*cleanup)(struct Plugin* self);

    void* user_data;            /* 私有数据（类比 C++ private 成员） */
    PluginState state;          /* 运行时状态 */
} Plugin;

#define PLUGIN_ENTRY_NAME "get_plugin"   /* 框架按这个名字找插件 */
```

**① 结构体打包的是"行为"，不是"数据"。** 第7讲的结构体打包数据，
本讲的结构体打包行为。C 语言没有 `class`，但有函数指针——
于是我们自己"手搓"了一张虚函数表（vtable）。

**② `need_amount` 一个 int，省掉一个 switch。** 转账需要"目标账户 + 金额"两个参数，
统一接口只能传一个 `double`。最直觉的做法是改接口签名——但那样所有插件都要改。
本讲选了另一条路：**接口保持最小公约数，插件自己声明需要什么。**

```c
/* framework.c：是否需要框架先读金额，由插件自己声明 */
if (p->need_amount) {
    printf("请输入金额: ");
    if (fgets(line, sizeof(line), stdin) == NULL) break;
    amount = atof(line);
}
p->execute(p, amount);   /* 多态调用：同一行代码，不同插件不同行为 */
```

四个插件里，存款 / 取款 `need_amount = 1`，查询 / 转账 `= 0`（转账自己读目标账户和金额）。
框架里**没有任何一处** `if (strcmp(p->name, "转账") == 0)`。

**③ `state` 存在插件自己身上。** 所以 `framework_run()` 里那句
`if (p->state != PLUGIN_STARTED) continue;` 就能挡住所有"没启动成功却想执行"的调用。
**状态不是给人看的，是给代码做判断用的。**

### 1.6.3 动态加载：`dynamic_loader.c`

第11讲学过，两个平台的加载 API 完全不一样：

| 动作 | Windows | Linux / macOS |
|:---|:---|:---|
| 加载库 / 取符号 / 卸载库 | `LoadLibrary` / `GetProcAddress` / `FreeLibrary` | `dlopen` / `dlsym` / `dlclose` |
| 错误信息 / 扫描目录 | `GetLastError`+`FormatMessage` / `FindFirstFile` | `dlerror` / `opendir` |

直接写进 `framework.c`，框架里就会到处是 `#ifdef _WIN32`。所以加一层薄封装：

```c
DllHandle dll_load(const char *path, char *err, size_t errlen);
void     *dll_symbol(DllHandle handle, const char *name);
void      dll_unload(DllHandle handle);
const char *dll_extension(void);                  /* ".dll" 或 ".so" */
int       dll_scan_dir(const char *dir, const char *ext,
                       DllFileCallback cb, void *user);
```

上层只认这五个函数。**这本身就是"接口抽象"（第12讲）在另一处的应用**：
平台是"实现"，`dll_*` 是"接口"。凡"会变的东西"，都值得关进一个接口里。

Windows 实现里有个贴心细节——把错误码翻译成人话：

```c
DWORD code = GetLastError();
FormatMessageA(FORMAT_MESSAGE_FROM_SYSTEM | FORMAT_MESSAGE_IGNORE_INSERTS,
               NULL, code, 0, msg, (DWORD)sizeof(msg), NULL);
/* 系统消息可能带换行，压成单行，避免打印串行 */
for (i = 0; msg[i] != '\0'; i++)
    if (msg[i] == '\r' || msg[i] == '\n') msg[i] = ' ';
snprintf(err, errlen, "系统错误码 %lu（%s）", (unsigned long)code, msg);
```

不翻译，用户看到的是 `错误 193`；翻译了，才叫**能给用户看的错误**。

### 1.6.4 配置化菜单

菜单不是数组，是链表。这是"零改动扩展"的关键。

```c
typedef struct MenuItem {
    int  id;                        /* 菜单编号 */
    char label[40];                 /* 菜单文字 */
    Plugin* plugin;                 /* 关联插件（NULL = 内置功能） */
    struct MenuItem* next;          /* 下一个菜单项 */
} MenuItem;
```

和普通链表唯一的不同，是多了 `plugin` 指针——它把"用户看到的一行字"
和"背后干活的插件"挂在一起。有了它，菜单处理退化成纯粹的**查表 + 多态**：

```c
int framework_run(void)
{
    char line[64];
    while (1) {
        int choice; MenuItem* item; Plugin* p; double amount = 0.0;
        menu_show();                       /* 遍历链表打印，不是一行行 printf */
        printf("请选择操作: ");
        if (fgets(line, sizeof(line), stdin) == NULL) break;
        choice = atoi(line);
        if (choice == 0) break;            /* 退出 */

        item = menu_find(choice);
        if (item == NULL) { printf("  [错误] 无效的菜单编号: %d\n", choice); continue; }
        if (item->plugin == NULL) { manager_print_all(); continue; }   /* 内置项 */

        p = item->plugin;
        if (p->state != PLUGIN_STARTED) {  /* 状态机挡在门口 */
            printf("  [错误] 插件[%s] 当前状态为 %s，无法执行\n",
                   p->name, plugin_state_name(p->state));
            continue;
        }
        if (p->need_amount) { /* 读金额 */ }
        p->execute(p, amount);             /* 多态调用 */
    }
    return 0;
}
```

**数一数这里面有几个 `case`：答案是 0 个。**

「注册即挂菜单」是唯一需要写一行代码的地方：

```c
/* manager_start_all() 内部 */
p->state = PLUGIN_STARTED;
if (p->menu_id != 0) {
    menu_add(p->menu_id, p->menu_label, p);   /* 【关键】注册即挂载 */
}
```

`menu_add` 用的是第8讲的**有序插入**：

```c
/* 情况1：空链表，或新节点应排在最前 */
if (g_menu_head == NULL || g_menu_head->id > id) {
    node->next = g_menu_head;  g_menu_head = node;  g_menu_count++;
    return 0;
}
/* 情况2：找到第一个 id 更大的节点，插在它前面 */
cur = g_menu_head;
while (cur->next != NULL && cur->next->id < id) { cur = cur->next; }
node->next = cur->next;  cur->next = node;  g_menu_count++;
```

有序插入带来一个很实际的收益：**菜单顺序与插件加载顺序无关。**
看真实输出——加载顺序是 `存款 → 查询 → 转账 → 取款`（目录返回顺序），
菜单却是 `1 存款 → 2 取款 → 3 查询 → 4 转账`（按 id 排序）。
若用尾插法，菜单顺序就会跟着文件名顺序变，那不算一个能用的产品。

## 1.7 动态加载失败时的优雅降级

一个真实的插件系统必须回答：**插件文件坏了、缺失了、或者根本不是本框架的插件，会怎样？**
反面教材是"一崩了之"；正面做法是**能力退化，体验不退化**。

本讲在 `on_plugin_file()` 回调里实现了三级降级：

```c
static void on_plugin_file(const char* fullpath, void* user)
{
    ScanCtx* ctx = (ScanCtx*)user;
    char err[512] = {0};
    DllHandle h;  PluginEntry entry;  Plugin* p;

    printf("  [发现] %s\n", fullpath);

    /* 第 1 步：加载动态库（失败则优雅降级） */
    h = dll_load(fullpath, err, sizeof(err));
    if (h == NULL) {
        printf("  [降级] 加载失败，跳过该文件。原因: %s\n", err);
        ctx->failed++;  return;
    }
    /* 第 2 步：查找约定的入口符号 get_plugin */
    entry = (PluginEntry)dll_symbol(h, PLUGIN_ENTRY_NAME);
    if (entry == NULL) {
        printf("  [降级] 未导出符号 \"%s\"，不是本框架的插件，跳过\n",
               PLUGIN_ENTRY_NAME);
        dll_unload(h);  ctx->not_plugin++;  return;
    }
    /* 第 3 步：取得插件实例并注册 */
    p = entry();
    if (p == NULL) {
        printf("  [降级] get_plugin() 返回空，跳过\n");
        dll_unload(h);  ctx->failed++;  return;
    }
    p->state = PLUGIN_LOADED;
    if (manager_register(p) == 0) {
        remember_lib(h, fullpath);   /* 注册成功才记住句柄 */
        ctx->loaded++;
    } else {
        dll_unload(h);  ctx->failed++;   /* 注册失败立刻卸载 */
    }
}
```

| 防线 | 触发条件 | 处理方式 |
|:---:|:---|:---|
| ① | DLL 损坏 / 依赖缺失，`dll_load` 失败 | 打印系统错误原因，跳过该文件 |
| ② | 是合法 DLL 但没有 `get_plugin` 符号 | 卸载并跳过，计入"非插件" |
| ③ | 有 `get_plugin` 但返回 NULL | 卸载并跳过 |
| ④ | 上面任意一种发生后，功能缺失 | `framework_register_fallbacks()` 启用**内置实现** |

第四道防线就是 `main.c` 登记 `builtins` 的用途：

```c
for (i = 0; i < g_builtin_count; i++) {
    Plugin* p = g_builtins[i];
    if (p == NULL) continue;
    if (manager_find(p->name) != NULL) {
        printf("  [OK]   [%s] 已由动态库提供，不使用内置实现\n", p->name);
        continue;
    }
    printf("  [降级] [%s] 未从 plugins/ 加载到，启用内置实现\n", p->name);
    p->state = PLUGIN_LOADED;
    manager_register(p);
}
```

**实测一：删掉 `plugins/transfer_plugin.dll`。**

```
  [结果] 扫描 3 个文件：成功 3，失败 0，非插件 0

=== 检查内置回退插件 ===
  [OK]   [存款] 已由动态库提供，不使用内置实现
  [OK]   [取款] 已由动态库提供，不使用内置实现
  [OK]   [查询] 已由动态库提供，不使用内置实现
  [降级] [转账] 未从 plugins/ 加载到，启用内置实现
  [注册] 转账     v1.0  menu=4  在当前账户与目标账户之间转账
  ...
=== 框架启动完成，菜单项 5 个 ===
```

**转账功能照常可用**，菜单依然是 5 项，只是实现来自内置回退，用户完全无感。

**实测二：塞进两个坏文件**（一个损坏的 DLL，一个没有导出 `get_plugin` 的 DLL）。

## 2.3 复用范围的扩大

```
函数内复用  →  文件内复用  →  项目内复用  →  进程内复用  →  系统级复用
    │              │              │              │               │
 第1-2讲        第3讲          第4讲         第9-10讲        第11-14讲
    │              │              │              │               │
  一个值         一段逻辑       一组功能      一份二进制       一个生态
    │              │              │              │               │
  复制粘贴       函数调用      #include       链接库         运行时装载
```

| 复用范围 | 复用的"单位" | 复用方式 | 改一处影响 |
|:---:|:---|:---|:---|
| 函数内 | 一个值 / 一个表达式 | 直接写 | 一行 |
| 文件内 | 一段逻辑 | 函数调用 | 一个文件 |
| 项目内 | 一组相关函数 | `#include` 头文件 | 重新编译整个项目 |
| 进程内 | 一份二进制功能 | 链接库（`.a` / `.dll`） | 重新链接，或换库文件 |
| 系统级 | 一整套能力 | 运行时加载 + 接口约定 | **什么都不用改** |

最后一行是本讲的价值所在：当复用范围扩展到"系统级"，扩展功能**不需要重新编译任何东西**。
往 `plugins/` 里丢一个 DLL，功能就出现了——这是软件工程里少见的"免费午餐"。

代价是什么？**你失去了编译期检查。** 插件里写错函数名，编译器不会告诉你，
只有运行时才能发现。所以在 1.7 节，我们才需要那么多道防线。
**收益与代价，永远是同一个决定的两面。**

## 2.4 控制反转 IoC：从"你调用库"到"框架调用你"

```
   传统方式（第1-10讲）                        框架方式（第13-14讲）
   ─────────────────────                       ─────────────────────

   你调用库                                    插件被框架加载
   ┌──────────────┐                            ┌──────────────┐
   │   你的 main   │                            │   你的 main   │
   │      │       │                            │      │       │
   │      ▼       │                            │      ▼       │
   │  library()   │  ← 你决定何时调用           │ 启动框架      │ ← 你只交出控制权
   └──────────────┘                            └──────┬───────┘
                                                      │
   库被你链接                                          ▼
   ┌──────────────┐                            ┌──────────────┐
   │  libxxx.a    │  ← 链接期静态装入           │   框架        │
   └──────────────┘                            │  manager_*   │
                                               └──────┬───────┘
                                                      │
                                                      ▼
                                               ┌──────────────┐
                                               │  你的插件     │ ← 框架反过来调用你
                                               │  init/start/ │
                                               │  execute/... │
                                               └──────────────┘
```

一句话说清楚：**Don't call us, we'll call you. —— 别来找我们，我们会找你。**

**为什么叫"反转"？** 对比两条调用链：

```
【没有反转】main → 存款函数 → 账户模块 → 返回
             控制流从 main 出发一路向下，最后回到 main。main 全程是导演。

【发生反转】main → framework_start → manager_init_all
                  → 插件 init()        ← 控制流在这里"折返"了
                  → manager_start_all → 插件 start()   ← 又折返一次
             framework_run → 菜单 → p->execute()        ← 每次执行业务都折返
```

关键就在那个"折返"：**控制流走出了框架，进入了你自己写的代码。**
框架并不知道 `deposit_execute` 里有什么，它只是照着函数指针调下去。

**交出控制权值不值？** 看本讲的账：

| 项目 | 交出之前（第2讲做法） | 交出之后（本讲） |
|:---|:---|:---|
| 加一个功能 | 改 3 处：菜单打印、`switch` 分支、编号分配 | 往 `plugins/` 放一个 DLL |
| 主程序行数 | 一个 `switch` 撑起几十行 | 三行 |
| 功能清单 | 编译期写死在代码里 | 运行时扫目录才知道 |
| 单人写小工具 | 够用，甚至更快 | 过度设计 |
| 多人长期维护 | 每加一个功能都要动主程序，冲突不断 | 各写各的插件，互不干扰 |

结论不是"框架永远更好"，而是：

> **当"功能会持续增长、且彼此独立"时，交出控制权是划算的；
> 当"功能极少且几乎不变"时，硬编码反而更快更清楚。**

## 2.5 设计模式入门：C 语言里的四个影子

学完这 14 讲，你其实已经在无意中用过几个经典设计模式了。
它们在 C++ / Java 里是"模式"，在 C 里只能自己"手搓"——但思想完全一样。

| 设计模式 | 一句话定义 | 本系列里的对应实现 | 出自 |
|:---|:---|:---|:---:|
| **策略模式** Strategy | 把"算法"抽出来，运行时换一个 | `Plugin` 的函数指针：同一行 `p->execute(p, amount)`，换成存款插件就是存钱、换成取款插件就是取钱 | 第12-14讲 |
| **工厂模式** Factory | 不直接 `new`，交给一个函数去造 | `xxx_plugin_create()` 返回单例实例；`get_plugin()` 是"插件工厂"的统一入口 | 第14讲 |
| **观察者模式** Observer | 主体状态变了，通知一批订阅者 | `manager_init_all()` 遍历插件链表逐个回调 `p->init(p)`——链表就是"订阅者名单" | 第13-14讲 |
| **模板方法** Template Method | 骨架固定，可变步骤留给子类 | 五阶段生命周期就是"模板"：框架规定顺序，插件只填每一步做什么 | 第13-14讲 |

**它们在本讲项目里的 C 语言长相：**

```c
/* ① 策略模式：同一行代码，换 p 就换行为 */
p->execute(p, amount);          /* p 是存款插件 → deposit_execute()  */
                                /* p 是取款插件 → withdraw_execute() */

/* ② 工厂模式：按约定符号名取工厂函数，产出插件实例 */
entry = (PluginEntry)dll_symbol(h, PLUGIN_ENTRY_NAME);   /* "get_plugin" */
p = entry();                    /* 不关心具体是哪个插件 */

/* ③ 观察者模式：遍历"订阅者名单"，逐个通知并等回调 */
while (cur != NULL) {
    Plugin* p = cur->plugin;
    if (p->init != NULL && p->init(p) == 0) p->state = PLUGIN_INITIALIZED;
    cur = cur->next;            /* 注册即订阅，卸载即退订 */
}
```

**④ 模板方法 —— 框架定流程，插件填步骤。** C 语言没有继承，
但**框架用状态机强制了顺序**，效果一样：

```
框架规定死的骨架（模板）：
    init() → start() → execute() → execute() → ... → stop() → cleanup()
      │        │          ↑ 可反复执行             │         │
      └────────┴──────────┴───────────────────────┴─────────┘
                     插件只填每一步"做什么"

插件实现者不能做的：
    ✗ 跳过 init 直接 start（状态机拒绝：状态不是 INITIALIZED）
    ✗ cleanup 之后再 execute（状态是 CLEANED，检查不通过）
    ✗ 改变框架的调用顺序
```

> 设计模式不是"额外要学的东西"，它是**你在解决真实问题时自然会走上的路**。
> 本系列这 14 讲，你是一步步走过来的，而不是背过来的。

## 2.6 从 C 到架构：思维的六次跃迁

| 阶段 | 你关心的问题 | 你看代码的视角 |
|:---:|:---|:---|
| 第1-2讲 | 这个表达式算出什么？循环执行几次？ | **语法视角**：这行代码对不对 |
| 第3-4讲 | 这个函数该叫什么名字？放哪个文件？ | **结构视角**：怎么组织才不混乱 |
| 第5-8讲 | 这块内存谁分配谁释放？结构怎么串起来？ | **资源视角**：数据活多久、放在哪 |
| 第9-10讲 | 这段代码能不能给别人直接用？ | **复用视角**：怎么让更多人用上 |
| 第11-13讲 | 别人要加功能，需不需要动我的代码？ | **边界视角**：谁稳定、谁易变 |
| 第14讲 | 这个系统三年后还能不能长？ | **演进视角**：怎么让系统随时间变强 |

归结为一句话：

> 从"我要把这段代码写对"，到"**我要设计一个能容纳别人写代码的地方**"。

这不是会的语法多少的差别，而是**思考的单位从"代码"变成了"变化"**。

本讲项目里，每一处"多想了一步"都是架构的味道：

| 设计 | 防的是什么变化 | 第2讲会怎么写 |
|:---|:---|:---|
| 插件用独立 DLL | 未来要加新功能 | 每加一个功能改一次 `switch` |
| 菜单用链表 | 未来菜单项会增减 | `printf` 写死菜单 |

| 账务数据放共享库 | 未来会有更多插件读写同一份数据 | 全局变量，各自一份 |
| 加载失败有降级 | 部署环境不一定完整 | 加载失败直接崩 |
| 生命周期有 stop / cleanup | 未来要支持热插拔 | 只有 init，退出靠进程结束 |

## 2.7 AI 时代，这 14 讲该怎么学

AI 能在几秒钟内写出一个 `Plugin` 结构体，甚至写出一整个框架。这 14 讲还值得学吗？
非常值得，而且**学的方式要变**。

**变化一：AI 负责"写出来"，你负责"判断对不对"。**
AI 不知道你的 `atmcore.dll` 是共享库还是静态库、加载失败该崩还是该降级、
菜单要硬编码还是配置化。**这些判断不来自语法，来自 14 讲建立的取舍意识。**

**变化二：把 AI 当"对照组"，而不是"答案"。** 看到 AI 写的框架，问三个问题：
① 为什么生命周期是三阶段而不是五阶段？② 插件注册是静态还是动态？代价是什么？
③ 插件崩了框架会不会一起崩？**能问出这三个问题，说明你学的不是代码，是设计。**

**变化三：让 AI 帮你做"变体实验"。** 本讲项目就是绝好的实验台：
"菜单改成哈希表会快多少、复杂多少？""生命周期砍到 3 阶段会丢什么能力？
""加一个依赖声明让 A 在 B 之后启动，怎么改？"——答案不重要，**推演过程才重要**。

**变化四：动手跑，别只看。** AI 生成的代码有个通病：**看起来都对，跑起来就错**。
本讲项目里就埋了好几个这类点：用静态库装账务模块 → 存完钱查不到；
`menu_add` 不做重复 id 检查 → 菜单出现两个 `1. 存款`；
退出时不 `menu_remove` → 悬空指针；不翻译错误码 → 用户看到 `错误 193` 一脸茫然。
**这些都是必须自己跑一遍才会记住的。**

> AI 让"写出代码"变得廉价，于是"判断代码"变得昂贵。
> 这 14 讲训练的，正是后者。

## 2.8 进阶阅读：真实世界里的插件框架

| 系统 | 插件机制 | 值得看什么 |
|:---|:---|:---|
| **Redis Modules** | 编译成 `.so`，`MODULE LOAD` 加载 | 一个 C 结构体接口 + 一堆函数指针，和本讲几乎同构；看它怎么做 ABI 版本号与错误隔离 |
| **Nginx 模块化** | 编译期静态注册 `ngx_module_t`，运行期按 phase 回调 | 极致的"配置化 + 回调"：模块只声明挂在哪个阶段 |
| **VS Code 插件** | `package.json` 声明 `contributes`，运行时 `activate()` | `contributes` 就是 `menu_id / menu_label` 的工业版；`activate` ≈ `init` + `start` |
| **SQLite 扩展** | `sqlite3_load_extension()` 运行时加载 | 看它怎么用一个 `sqlite3_extension_init` 符号完成约定 |
| **Linux 内核模块** | `insmod` / `rmmod`，`module_init` / `module_exit` | 五阶段生命周期的"工业母版"；`notifier` 链就是观察者模式 |
| **Python C 扩展** | `PyInit_xxx` 入口符号 | 和 `get_plugin` 同构：约定入口符号名，剩下全靠结构体约定 |

**读它们的时候，带着本讲的三个问题：**

1. **契约在哪？** 哪个头文件定义了插件必须长什么样？
2. **谁来加载？** 谁扫目录、谁定加载顺序、失败怎么处理？
3. **怎么隔离？** 插件崩了会不会带着框架一起崩？

再补一个老概念：**ABI 兼容性**。本讲的 `Plugin` 结构体一旦发布，
加字段、改顺序都会让老插件错位。工业框架（如 Redis）用版本号 + 校验来防这件事。
这是本讲没有展开、但真实项目一定会撞上的墙。

## 💭 思考题

### 思考题 ①

**插件崩溃了，框架该怎么办？**

本讲的降级策略覆盖的都是"加载阶段"的失败。但如果插件**已经成功加载并启动**，
在 `execute()` 执行到一半时因空指针解引用或数组越界**直接崩溃**
（Windows 上是访问违例，Linux 上是 SIGSEGV），整个进程会立刻挂掉。

**框架能为这种情况做些什么？哪些能做、哪些做不到？**

<details>
<summary>参考答案</summary>

**先明确一个残酷的事实：进程内的段错误，框架接不住。**
`execute()` 是**同一进程同一线程**在跑，插件越界写内存，
可能把主程序、框架数据结构、账务数据一起踩坏。
即使用信号处理勉强抓住，内存状态已被污染，**继续运行不可信**。

所以正确思路是**分级防御**：

**第一级 · 进程内防御（只能防"软错误"）**
1. **参数校验前置**。本讲的 `manager_execute` 已经做了空指针检查，
   再加一条执行前的 `p->state == PLUGIN_STARTED` 检查，挡住"未初始化/已清理却还在被调用"。
2. **返回值协议**。约定返回 0 成功、负数明确失败，框架对非零值只记日志、不中止系统。
3. **看门狗 + 超时**。如果插件可能死循环，就放到**单独线程**执行，
   主线程超时等待；超时后放弃本次操作，把插件标记为"疑似异常"并摘掉它的菜单项。

**第二级 · 进程级隔离（真解决，但代价大）**
把插件跑在**独立进程**里，用 IPC（管道 / 共享内存 / 套接字）通信。
插件崩了，框架只看到"连接断了"，可以直接重启那个插件进程。

- 代价：一次函数调用变成一次 IPC 往返；接口要改成"序列化参数 + 序列化返回值"；
  数据不能再靠共享库共享。本讲的 `atmcore.dll` 就得换成"服务式访问"。
- 收益：**强隔离**。浏览器（每个标签页一个进程）、现代编辑器插件宿主都选这条路。

**第三级 · 工程与管理手段（成本最低，最易被忽视）**
1. **审核制**：Redis Modules、Nginx 模块都要求插件过审——因为它们和主程序**同进程，本来就没有技术隔离**。
2. **分级目录**：核心插件内置，第三方插件隔离。
3. **文件级回滚**：插件按版本归档，更新前备份，出问题一键回退。
4. **崩溃现场留存**：退出时把已加载插件清单、状态、最后执行的插件名写进日志，
   让"崩在谁身上"至少可追溯。

**一句话结论：**
> 框架能防住"插件加载失败"，防不住"插件跑起来之后把进程带崩"。
> 想真正兜住后者，只有**进程隔离**这一条路，而它要付出性能与接口复杂度的代价。
> **架构的本质就是：你愿意为哪种失败，付出什么代价。**

</details>

### 思考题 ②

**插件之间有依赖关系，怎么保证启动顺序正确？**

现在四个插件互不依赖，按注册顺序启动没问题。但假设新来一个"报表"插件，
它必须在"查询"和"取款"都启动成功之后才能工作——
如果它先启动，调用 `transaction_print_history()` 时数据还没准备好。
本讲的 `manager_start_all()` 只是顺序遍历链表，**不关心任何依赖**。

**该用什么办法表达和满足插件之间的启动依赖？**

<details>
<summary>参考答案</summary>

**第一步 · 把"依赖"变成可声明、可检查的数据。** 在 `Plugin` 里加两个字段：

```c
const char** depends_on;    /* 依赖的插件名称数组，NULL 结尾 */
int          dep_count;     /* 依赖个数（0 表示无依赖） */
```

插件自己声明"我需要在谁之后启动"：

```c
static const char* g_report_deps[] = { "查询", "取款", NULL };
static Plugin g_report_plugin = {
    .name = "报表", .depends_on = g_report_deps, .dep_count = 2,
    /* ... */
};
```

**第二步 · 启动前做一次拓扑排序。** 依赖关系本质是一张有向图，"启动顺序"就是一个**拓扑序**：

```c
/*
 * 1. 每个插件的"入度" = 它依赖的、尚未启动的插件个数
 * 2. 入度为 0 的进队列（可以立刻启动）
 * 3. 每启动一个，把它"解锁"的插件入度减 1，减到 0 就进队列
 * 4. 队列空了但还有未启动的 → 存在循环依赖，报错并中止
 */
int manager_start_ordered(void) {
    int started = 0;
    while (started < manager_count()) {
        int progressed = 0;
        for (每个 PluginNode cur) {
            if (cur->plugin->state == PLUGIN_INITIALIZED && deps_all_started(cur->plugin)) {
                if (cur->plugin->start(cur->plugin) == 0) {
                    cur->plugin->state = PLUGIN_STARTED;  started++;
                }
                progressed = 1;
            }
        }
        if (!progressed) {                       /* 死锁：循环依赖或上游失败 */
            printf("  [错误] 插件依赖无法满足，存在循环依赖或上游启动失败\n");
            report_unresolved();                 /* 打印每个卡住的原因 */
            return -1;
        }
    }
    return 0;
}
```

**第三步 · 处理"被依赖的插件加载不进来"。** 三种策略，各有取舍：

| 策略 | 做法 | 优点 | 缺点 |
|:---|:---|:---|:---|
| **严格** | 依赖缺失 → 插件不启动并明确报错 | 不带病运行 | 一个缺失拖掉一片功能 |
| **宽松** | 依赖缺失 → 打印警告但仍启动 | 可用性高 | 插件可能在前提不满足时工作 |
| **回退** | 依赖缺失 → 优先启用内置实现，内置也没有才判缺失 | 与本讲降级机制自然衔接 | 需为被依赖插件准备内置实现 |

**本讲项目的天然答案是第三种**：`framework_register_fallbacks()` 已经在做
"同名插件缺失就用内置实现"，所以"报表"只要依赖的插件有内置实现，依赖就永远能满足。
**好的机制设计往往能同时解决好几个问题。**

**第四步 · 停止要逆序，失败要回滚。** 启动是 `A → B → C`，停止就该是 `C → B → A`，
否则先停 A，B 和 C 可能还在用 A 的资源。更麻烦的是**中途失败**：
只启动了 A 和 B，C 的 `start` 失败了，必须**回滚已启动的部分**——
按启动的逆序 `stop` + 摘菜单。这个"要么全成、要么全退"的模式，
正是第13讲把 `start` 从 `init` 里拆出来的收益。

**一句话结论：**
> 依赖问题不是"调用顺序"问题，是"**把隐式约定变成显式数据，然后做一次图排序**"的问题。
> 只要依赖能被声明、能检测环、能在失败时回滚，
> 插件系统就从"一堆文件"变成了"一个有秩序的生态"。

</details>

### 思考题 ③

**配置化和硬编码，边界到底在哪？**

第13讲把硬编码菜单改成了配置化菜单，本讲又加了 `need_amount` 这种"插件自己声明行为"的字段。
但注意本讲项目里**仍然有硬编码的地方**，而且是有意为之：

- 插件目录写死为 `"plugins"`（`framework_load_plugins_dir("plugins")`）；
- 入口符号写死为 `"get_plugin"`（`PLUGIN_ENTRY_NAME`）；
- 生命周期阶段写死为五步；
- 菜单"退出"与"插件列表"是内置的。

**什么该配置化，什么该硬编码？判断标准是什么？**

<details>
<summary>参考答案</summary>

**先给一条尺子：**
> **凡是"会变、且变化来自使用者而非开发者"的，配置化；**
> **凡是"稳定、且变化只能来自开发者"的，硬编码。**

**用尺子量一遍本讲项目：**

| 项目 | 结论 | 为什么 |
|:---|:---|:---|
| 功能清单（菜单项） | **配置化** | 加功能的人不是框架开发者；功能会持续增长 |
| 是否需要金额（`need_amount`） | **配置化** | 由插件业务决定，框架无法预知 |
| 菜单编号、菜单文字 | **配置化** | 属于产品形态，随业务变化 |
| 插件目录 `"plugins"` | **硬编码** | 属于部署约定；改它要让所有运维跟着改，反而增加沟通成本 |
| 入口符号 `"get_plugin"` | **硬编码** | 这是 ABI 契约，一变所有已编译插件全废，求稳不怕死 |
| 生命周期五阶段 | **硬编码** | 加阶段＝所有插件接口都要改，这种"全局一致性"必须定死 |
| `退出` / `插件列表` | **内置** | 框架自身的功能，不属于任何插件，用 `plugin == NULL` 区分 |

**再提炼三条更细的规则：**

**① 契约硬编码，策略配置化。**
插件接口 `Plugin` 结构体、入口符号名、生命周期阶段数，是**框架与插件之间的合同**；
合同一改，所有已发布插件全废。所以合同要"窄、稳、定死"。
而菜单长什么样、要不要金额，属于**策略**，随业务变，必须配置化。

**② 变化频率差一个数量级的东西，别放在同一个地方。**
菜单项可能一周加一个；`get_plugin` 可能三年不变。
把两者都做成"可配置"，等于给三年不变的东西多加一层间接，收益为零、排查成本翻倍。

**③ 算清"配置化的成本账"。** 本讲为"插件自己声明菜单"付出的真实成本是：
结构体多 3 个字段；`MenuItem` + 7 个菜单函数；`menu_add` 的有序插入约 20 行；
启动挂菜单 / 停止摘菜单的一致性维护；编号冲突与重复注册检测；
调试时"菜单项从哪来"要靠日志才看得清。
换来的是"加功能改 0 处主程序"——**这个交换值不值，取决于功能会不会持续增长。**

**什么时候应该反过来硬编码？**

1. **功能极少且几乎不变**（比如只做四则运算的计算器）——配置化就是过度设计；
2. **性能极其敏感**——配置化多了遍历和间接调用，在超高频路径上是净损失；
3. **必须编译期校验**——配置化把错误推到运行时（加载失败就是代价），若不可接受就硬编码；
4. **规模太大**——菜单项上千条时 O(n) 链表不如哈希表，
   那时该换的是"载体"，而不是回到硬编码。

**最后一个反直觉的点：** 本讲里 `"plugins"` 这个目录名其实**也可以**配置化
（从命令行或配置文件读），为什么不做？因为教学项目里**"能跑起来"比"能配置"重要**。
配置项每多一个，"第一次运行失败"的可能就多一条。

> **说到底：配置化的程度，应该匹配"用户群的复杂程度"，
> 而不是匹配"开发者觉得这样更优雅"。**

### 思考题 ④

**框架和库的本质区别到底是什么？**

本讲项目里两者**同时存在**：`atmcore.dll` 是**库**（主程序和插件都链接它，
主动调用它的 `account_deposit` 等函数）；`framework.c` 是**框架**
（主程序只调 `framework_start/run/stop`，剩下的由框架反过来调插件的 `init/execute`）。

同一个项目里既有库又有框架——**分界线到底划在哪？**

<details>
<summary>参考答案</summary>

**第一层答案：控制权在谁手上。**
这是最短的答案：**库是你调用它，框架是它调用你。** 控制反转（IoC）就是那条分界线。

```c
/* 【库】插件主动调用 atmcore.dll；库永远不会反过来叫插件 */
balance = transaction_deposit(id, amount);

/* 【框架】框架回调插件，控制流折返 */
if (p->init != NULL && p->init(p) == 0) {   /* 框架调用插件的代码 */
    p->state = PLUGIN_INITIALIZED;
}
```

**第二层答案（更本质）：谁定义"流程"，谁定义"步骤"。**

| | 库 | 框架 |
|:---|:---|:---|
| **流程**（先做什么、后做什么） | 调用方决定 | **框架决定** |
| **步骤**（每一步干什么） | 库提供函数 | 插件提供实现 |
| 谁定 `init → start → execute → stop → cleanup` 的顺序 | —— | 框架（并用状态机强制） |
| 谁实现 `deposit_execute` 里的业务 | —— | 插件 |

框架那句"状态不对就拒绝"，正是"框架定流程"的强硬表达：**库不会拒绝你调用它**
（参数错了它返回错误码，但不没收你的控制权）；**框架会拒绝你没按它的流程走**。

**第三层答案：依赖方向相反。**

```
【库】依赖方向：应用 → 库
    主程序 #include <stdio.h> 并链接 libc；主程序知道库存在，库不知道主程序存在

【框架】依赖方向：主程序 → 框架 → 插件，且插件 → 框架的契约
    插件 #include "plugin.h"，知道框架存在（要导出 get_plugin）
    框架 #include "plugin.h"，但不知道具体有哪些插件（运行时才知道）
    主程序完全不认识任何具体插件
```

注意这个**不对称的依赖**：插件同时依赖"框架契约"和"账务库"，
但**框架不依赖任何具体插件**。这正是框架能容纳无限扩展的根本原因。

**第四层答案：价值来源与代价不同。**

| | 库 | 框架 |
|:---|:---|:---|
| 价值来自 | 复用**代码** | 复用**结构** |
| 你收获 | 不用重写这段逻辑 | 不用重写整套骨架 |
| 你付出 | 学习 API | **把控制权交出去** |
| 失败模式 | 库有 bug，你还能包一层 | 框架设计得不好，你会写得非常别扭 |

框架的代价容易被忽略：**你把控制权交出去，就接受它的流程。**
如果框架规定的五阶段生命周期跟你的业务根本不匹配，你要么硬着头皮适配，
要么绕过框架——那时框架就成了负担。这是"什么时候该用框架"的真正答案：**当你认同它的流程时。**

**第五层：两者不是对立的，而是分层共存的。**

```
                    ┌──────────────────┐
                    │  framework.c     │  ← 框架：它调用插件
                    └────────┬─────────┘
                             │ 通过 Plugin 接口回调
                    ┌────────▼─────────┐
      插件主动调它 → │  atmcore.dll     │  ← 库：插件调用它
      （account_* / │  account.c       │
       transaction_*）│  transaction.c  │
                    └──────────────────┘
```

对**插件**而言，框架是"调用我的那个"，`atmcore.dll` 是"我可以调用的那个"；
对**主程序**而言，框架是它交权给的对象。所以更准确的说法是：

> **"框架"和"库"不是两种东西，是同一段代码在两条不同调用链上的两个身份。**
> 判断一个模块是框架还是库，要看**你和它之间谁调用谁**，
> 而不是看它叫什么名字、有多少行代码。

**一句话结论：**
> 库是**工具箱**，你从里面拿工具，活儿还是你自己干；
> 框架是**车间流水线**，你把零件放上去，流水线会带着零件走完全程。
> 两者可以共存，也经常共存——本讲项目就是最好的例子。

</details>

## 📝 小结

### 一句话总结

> **十四讲走过一条路：把一行 `printf`，变成一台"谁都能往上装功能、而主程序不用改"的机器。
> 这条路的名字，叫从程序员到架构师。**

### 本讲六个知识点

| # | 知识点 | 关键句 |
|:---:|:---|:---|
| 1 | **分层架构** | 主程序 / 框架 / 插件 / 账务核心四层，依赖单向向下；`main()` 只剩三行 |
| 2 | **共享库的必要性** | 账务数据必须放 `atmcore.dll`，否则每个插件一份余额，数据不再一致 |
| 3 | **统一插件接口** | `Plugin` 结构体 = 元数据 + 五个函数指针；`get_plugin` 是唯一入口符号 |
| 4 | **配置化菜单** | 菜单项 = 链表节点，`menu_add` 有序插入；注册即挂载、卸载即摘除 |
| 5 | **优雅降级** | 加载失败 / 无符号 / 返回空 → 三级降级 + 内置实现兜底，能力退化但体验不退化 |
| 6 | **控制反转 IoC** | 库是你调用它，框架是它调用你；交出控制权，换来"加功能不改主程序" |

### 三句话带走

1. **复用的范围，就是架构的高度。** 从一行代码到一个生态，每一步都在扩大"能被复用的东西"。
2. **控制反转是分水岭。** 当你的代码开始"被别人调用"，而不是"到处调用别人"，你就从写程序的人变成了设计程序的人。
3. **AI 能写出代码，写不出取舍。** 为什么用共享库而不是静态库、为什么菜单要配置化、为什么加载失败要降级——这些问题没有标准答案，只有你的判断。
