## 思考题 ①：插件崩溃了，框架该怎么办？

### 题目

本讲实现的三级降级，覆盖的都是**加载阶段**的失败。但如果插件已经成功加载并启动，
在 `execute()` 执行到一半时，因为空指针解引用或数组越界**直接崩溃**
（Windows 上是访问违例，Linux 上是 SIGSEGV），整个进程会立刻挂掉。

**框架能为这种情况做什么？哪些做得到，哪些做不到？**

### 背景

`framework_run()` 里那一行 `p->execute(p, amount);` 是**一次普通的函数调用**——
它和主程序、和账务核心跑在**同一个进程、同一个线程**里，共享同一份地址空间。
插件的一次越界写，可能踩坏的不只是插件自己的数据，还有框架的链表、账务模块的
`accounts[]` 和流水链表。本讲辛苦搭起来的"优雅降级"，只覆盖了"装不进来"，
没覆盖"装进来了却跑崩"。

### 思考方向

1. 崩溃发生在**同一个地址空间**里，框架的"守卫代码"还来得及执行吗？
2. 即使用信号处理勉强抓住崩溃，"继续运行"这件事本身还可信吗？
3. 要让故障**真的隔离**，唯一的技术手段是什么？它要付出什么代价？
4. 除了技术手段，工程和管理上还有哪些成本最低但常被忽视的动作？

### 完整参考答案

**先明确一个残酷的事实：进程内的段错误，框架接不住。**

`execute()` 是同一进程同一线程在跑，插件越界写内存，可能把主程序、框架数据结构、
账务数据一起踩坏。就算用信号处理勉强抓住，内存状态早已被污染，**继续运行不可信**。

所以正确思路是**分级防御**：

**第一级 · 进程内防御（只能防"软错误"）**
1. **参数校验前置**。`manager_execute()` 已做空指针检查，可再加一条执行前的
   `p->state == PLUGIN_STARTED` 检查，挡住"未初始化 / 已清理却还在被调用"。
2. **返回值协议**。约定返回 0 成功、负数明确失败；框架对非零值只记日志，不中止系统。
3. **看门狗 + 超时**。如果插件可能死循环，就把调用放到**单独线程**执行，
   主线程超时等待，超时后放弃本次操作，把插件标记为"疑似异常"并摘掉它的菜单项。

**第二级 · 进程级隔离（真解决，但代价大）**

把插件跑在**独立进程**里，用 IPC（管道 / 共享内存 / 套接字）通信。插件崩了，
框架只看到"连接断了"，可以直接重启那个插件进程。

| | 进程内调用 | 进程隔离 |
|:---|:---|:---|
| 一次调用成本 | 一次函数调用 | 一次 IPC 往返 |
| 接口形态 | 直接传 `double` | 参数、返回值都要序列化 |
| 数据共享 | `atmcore.dll` 共享内存 | 不能再靠共享库，要改成"服务式访问" |
| 隔离强度 | 无 | 强：崩了只丢一个插件 |

浏览器（每个标签页一个进程）、现代编辑器插件宿主都选这条路，原因就在这里。

**第三级 · 工程与管理手段（成本最低，最易被忽视）**
1. **审核制**：Redis Modules、Nginx 模块都要求插件过审——它们和主程序同进程，
   本来就没有技术隔离。
2. **分级目录**：核心插件内置，第三方插件隔离部署。
3. **文件级回滚**：插件按版本归档，更新前备份，出问题一键回退。
4. **崩溃现场留存**：退出时把已加载插件清单、状态、最后执行的插件名写进日志，
   让"崩在谁身上"至少可追溯。

**一句话结论：**

> 框架能防住"插件加载失败"，防不住"插件跑起来之后把进程带崩"。
> 想真正兜住后者，只有**进程隔离**这一条路，而它要付出性能与接口复杂度的代价。
> **架构的本质就是：你愿意为哪种失败，付出什么代价。**

## 思考题 ②：插件之间有依赖关系，怎么保证启动顺序正确？

### 题目

现在四个插件互不依赖，按注册顺序启动没问题。但假设新来一个"报表"插件，
它必须在"查询"和"取款"都启动成功之后才能工作——如果它先启动，
调用 `transaction_print_history()` 时数据还没准备好。

本讲的 `manager_start_all()` 只是顺序遍历链表，**不关心任何依赖**。
**该用什么办法表达和满足插件之间的启动依赖？**

### 背景

`manager_start_all()` 里只有一句 `if (p->state != PLUGIN_INITIALIZED) continue;`，
它只检查"自己准备好了没"，从不检查"我依赖的人准备好了没"。
依赖关系目前只存在于开发者的脑子里，代码里一个字都没有。

### 思考方向

1. 依赖关系本质上是什么结构？"启动顺序"在这个结构里叫什么？
2. 怎么把"我记得 B 要在 A 之后"这种**隐式约定**，变成**代码能检查的显式数据**？
3. 如果 A 依赖 B、B 依赖 A（循环依赖），系统应该怎么办？
4. 启动是 `A → B → C`，那停止该按什么顺序？中途失败了怎么办？

### 完整参考答案

**第一步 · 把"依赖"变成可声明、可检查的数据。**

在 `Plugin` 里加两个字段：

```c
const char** depends_on;    /* 依赖的插件名称数组，NULL 结尾 */
int          dep_count;     /* 依赖个数（0 表示无依赖） */
```

插件自己声明"我需要在谁之后启动"：

```c
static const char* g_report_deps[] = { "查询", "取款", NULL };
static Plugin g_report_plugin = {
    .name = "报表", .depends_on = g_report_deps, .dep_count = 2,
    /* ... */
};
```

**第二步 · 启动前做一次拓扑排序。**

依赖关系本质是一张**有向图**，"启动顺序"就是一个**拓扑序**：

```c
/*
 * 1. 每个插件的"入度" = 它依赖的、尚未启动的插件个数
 * 2. 入度为 0 的进队列（可以立刻启动）
 * 3. 每启动一个，把它"解锁"的插件入度减 1，减到 0 就进队列
 * 4. 队列空了但还有未启动的 → 存在循环依赖，报错并中止
 */
int manager_start_ordered(void)
{
    int started = 0;
    while (started < manager_count()) {
        int progressed = 0;
        for (每个 PluginNode cur) {
            if (cur->plugin->state == PLUGIN_INITIALIZED &&
                deps_all_started(cur->plugin)) {
                if (cur->plugin->start(cur->plugin) == 0) {
                    cur->plugin->state = PLUGIN_STARTED;
                    started++;
                }
                progressed = 1;
            }
        }
        if (!progressed) {                 /* 死锁：循环依赖或上游失败 */
            printf("  [错误] 插件依赖无法满足，存在循环依赖或上游启动失败\n");
            report_unresolved();           /* 打印每个卡住的原因 */
            return -1;
        }
    }
    return 0;
}
```

**第三步 · 处理"被依赖的插件加载不进来"。** 三种策略，各有取舍：

| 策略 | 做法 | 优点 | 缺点 |
|:---|:---|:---|:---|
| **严格** | 依赖缺失 → 插件不启动并明确报错 | 不带病运行 | 一个缺失拖掉一片功能 |
| **宽松** | 依赖缺失 → 打印警告但仍启动 | 可用性高 | 插件可能在前提不满足时工作 |
| **回退** | 依赖缺失 → 优先启用内置实现，内置也没有才判缺失 | 与本讲降级机制自然衔接 | 需为被依赖插件准备内置实现 |

本讲项目的天然答案是第三种：`framework_register_fallbacks()` 已经在做
"同名插件缺失就用内置实现"，所以"报表"只要依赖的插件有内置实现，依赖就永远能满足。
**好的机制设计，往往能同时解决好几个问题。**

**第四步 · 停止要逆序，失败要回滚。** 启动是 `A → B → C`，停止就该是 `C → B → A`，
否则先停 A，B 和 C 可能还在用 A 的资源。更麻烦的是**中途失败**：
只启动了 A 和 B，C 的 `start` 失败了，必须**回滚已启动的部分**——
按启动的逆序 `stop` 加摘菜单。这个"要么全成、要么全退"的模式，
正是第13讲把 `start` 从 `init` 里拆出来的收益。

**一句话结论：**

> 依赖问题不是"调用顺序"问题，是"**把隐式约定变成显式数据，然后做一次图排序**"的问题。
> 只要依赖能被声明、能检测环、能在失败时回滚，
> 插件系统就从"一堆文件"变成了"一个有秩序的生态"。

## 思考题 ③：配置化和硬编码，边界到底在哪？

### 题目

第13讲把硬编码菜单改成了配置化菜单，本讲又加了 `need_amount` 这种"插件自己声明行为"的字段。
但注意本讲项目里**仍然有硬编码的地方**，而且是有意为之：

- 插件目录写死为 `"plugins"`（`framework_load_plugins_dir("plugins")`）；
- 入口符号写死为 `"get_plugin"`（`PLUGIN_ENTRY_NAME`）；
- 生命周期阶段写死为五步；
- 菜单"退出"与"插件列表"是内置的。

**什么该配置化，什么该硬编码？判断标准是什么？**

### 背景

配置化不是免费的。本讲为了"插件自己声明菜单"，付出了真实成本：
`Plugin` 结构体多 3 个字段、`MenuItem` 加 7 个菜单函数、`menu_add` 的有序插入约 20 行、
启动挂菜单与停止摘菜单的一致性维护、编号冲突检测、调试时"菜单项从哪来"要靠日志才看得清。
如果配置化的对象其实"永远不会变"，那这些成本就白付了。

### 思考方向

1. 把项目里每一处"写死的"和"配置化的"列出来，问：它会变吗？谁来改它？
2. 契约（接口、符号名、阶段数）和策略（菜单、金额）该不该用同一把尺子量？
3. 两项变化频率差一个数量级的东西，放在同一个"可配置"层级里，是收益还是负担？
4. 什么情况下，反而应该老实回去写 `switch`？

### 完整参考答案

**先给一条尺子：**

> **凡是"会变、且变化来自使用者而非开发者"的，配置化；**
> **凡是"稳定、且变化只能来自开发者"的，硬编码。**

**用尺子量一遍本讲项目：**

| 项目 | 结论 | 为什么 |
|:---|:---|:---|
| 功能清单（菜单项） | **配置化** | 加功能的人不是框架开发者；功能会持续增长 |
| 是否需要金额（`need_amount`） | **配置化** | 由插件业务决定，框架无法预知 |
| 菜单编号、菜单文字 | **配置化** | 属于产品形态，随业务变化 |
| 插件目录 `"plugins"` | **硬编码** | 属于部署约定；改它要让所有运维跟着改，反而增加沟通成本 |
| 入口符号 `"get_plugin"` | **硬编码** | 这是 ABI 契约，一变所有已编译插件全废，求稳不怕"死" |
| 生命周期五阶段 | **硬编码** | 加阶段＝所有插件接口都要改，这种"全局一致性"必须定死 |
| `退出` / `插件列表` | **内置** | 框架自身的功能，不属于任何插件，用 `plugin == NULL` 区分 |

**再提炼三条更细的规则：**

**① 契约硬编码，策略配置化。**
插件接口 `Plugin` 结构体、入口符号名、生命周期阶段数，是**框架与插件之间的合同**；
合同一改，所有已发布插件全废。所以合同要"窄、稳、定死"。
而菜单长什么样、要不要金额，属于**策略**，随业务变，必须配置化。

**② 变化频率差一个数量级的东西，别放在同一个地方。**
菜单项可能一周加一个；`get_plugin` 可能三年不变。
把两者都做成"可配置"，等于给三年不变的东西多加一层间接，收益为零、排查成本翻倍。

**③ 算清"配置化的成本账"。**
换来的是"加功能改 0 处主程序"——**这个交换值不值，取决于功能会不会持续增长。**

**什么时候应该反过来硬编码？**

1. **功能极少且几乎不变**（比如只做四则运算的计算器）——配置化就是过度设计；
2. **性能极其敏感**——配置化多了遍历和间接调用，在超高频路径上是净损失；
3. **必须编译期校验**——配置化把错误推到运行时（加载失败就是代价），不可接受就硬编码；
4. **规模太大**——菜单项上千条时 O(n) 链表不如哈希表，那时该换的是"载体"，而不是回到硬编码。

**最后一个反直觉的点：** `"plugins"` 这个目录名其实**也可以**配置化（从命令行或配置文件读），
为什么不做？因为教学项目里**"能跑起来"比"能配置"重要**。
配置项每多一个，"第一次运行失败"的可能就多一条。

> **说到底：配置化的程度，应该匹配"用户群的复杂程度"，
> 而不是匹配"开发者觉得这样更优雅"。**

## 思考题 ④：框架和库的本质区别到底是什么？

### 题目

本讲项目里两者**同时存在**：`atmcore.dll` 是**库**（主程序和插件都链接它，
主动调用它的 `account_deposit` 等函数）；`framework.c` 是**框架**
（主程序只调 `framework_start / run / stop`，剩下的由框架反过来调插件的 `init / execute`）。

同一个项目里既有库又有框架——**分界线到底划在哪？**

### 背景

两者都是"别人写好、你给我用"的代码，都能被 `#include`、都能被链接。
如果只看"代码长什么样""有多少行""有没有函数指针"，根本分不清楚。
`framework.c` 里也有大量普通函数，`atmcore.dll` 里也有状态和生命周期——
那么，凭什么一个是框架、一个是库？

### 思考方向

1. 一次调用里，**控制权**在谁手上？谁决定"下一步该做什么"？
2. 谁定义**流程**（先做什么、后做什么），谁定义**步骤**（每一步做什么）？
3. 依赖的方向是应用 → 它，还是它 → 你？
4. 你付出的是什么（学习 API，还是交出控制权）？两者是对立的，还是可以共存的？

### 完整参考答案

**第一层答案：控制权在谁手上。**

这是最短的答案：**库是你调用它，框架是它调用你。** 控制反转（IoC）就是那条分界线。

```c
/* 【库】插件主动调用 atmcore.dll；库永远不会反过来叫插件 */
double balance = transaction_deposit(id, amount);

/* 【框架】框架回调插件，控制流折返 */
if (p->init != NULL && p->init(p) == 0) {   /* 框架调用插件的代码 */
    p->state = PLUGIN_INITIALIZED;
}
```

**第二层答案（更本质）：谁定义"流程"，谁定义"步骤"。**

| | 库 | 框架 |
|:---|:---|:---|
| **流程**（先做什么、后做什么） | 调用方决定 | **框架决定** |
| **步骤**（每一步干什么） | 库提供函数 | 插件提供实现 |
| 谁定 `init → start → execute → stop → cleanup` 的顺序 | —— | 框架（并用状态机强制） |
| 谁实现 `deposit_execute` 里的业务 | —— | 插件 |

框架那句"状态不对就拒绝"，正是"框架定流程"的强硬表达：
**库不会拒绝你调用它**（参数错了它返回错误码，但不没收你的控制权）；
**框架会拒绝你没按它的流程走**。

**第三层答案：依赖方向相反。**

```
【库】依赖方向：应用 → 库
    主程序 #include <stdio.h> 并链接 libc；主程序知道库存在，库不知道主程序存在

【框架】依赖方向：主程序 → 框架 → 插件，且插件 → 框架的契约
    插件 #include "plugin.h"，知道框架存在（要导出 get_plugin）
    框架 #include "plugin.h"，但不知道具体有哪些插件（运行时才知道）
    主程序完全不认识任何具体插件
```

注意这个**不对称的依赖**：插件同时依赖"框架契约"和"账务库"，
但**框架不依赖任何具体插件**。这正是框架能容纳无限扩展的根本原因。

**第四层答案：价值来源与代价不同。**

| | 库 | 框架 |
|:---|:---|:---|
| 价值来自 | 复用**代码** | 复用**结构** |
| 你收获 | 不用重写这段逻辑 | 不用重写整套骨架 |
| 你付出 | 学习 API | **把控制权交出去** |
| 失败模式 | 库有 bug，你还能包一层 | 框架设计得不好，你会写得非常别扭 |

框架的代价容易被忽略：**你把控制权交出去，就接受它的流程。**
如果框架规定的五阶段生命周期跟你的业务根本不匹配，你要么硬着头皮适配，
要么绕过框架——那时框架就成了负担。这是"什么时候该用框架"的真正答案：**当你认同它的流程时。**

**第五层：两者不是对立的，而是分层共存的。**

```
                    ┌──────────────────┐
                    │  framework.c     │  ← 框架：它调用插件
                    └────────┬─────────┘
                             │ 通过 Plugin 接口回调
                    ┌────────▼─────────┐
      插件主动调它 → │  atmcore.dll     │  ← 库：插件调用它
      （account_* / │  account.c       │
       transaction_*）│  transaction.c  │
                    └──────────────────┘
```

对**插件**而言，框架是"调用我的那个"，`atmcore.dll` 是"我可以调用的那个"；
对**主程序**而言，框架是它交权给的对象。所以更准确的说法是：

> **"框架"和"库"不是两种东西，是同一段代码在两条不同调用链上的两个身份。**
> 判断一个模块是框架还是库，要看**你和它之间谁调用谁**，
> 而不是看它叫什么名字、有多少行代码。

**一句话结论：**

> 库是**工具箱**，你从里面拿工具，活儿还是你自己干；
> 框架是**车间流水线**，你把零件放上去，流水线会带着零件走完全程。
> 两者可以共存，也经常共存——本讲项目就是最好的例子。

## 思考题 ⑤：如何实现"插件热更新"？

### 题目

本讲框架已经能在**启动时**从 `plugins/` 目录发现并加载插件。但每次换插件，
都要：退出程序 → 替换 DLL → 重新运行。对一个 7×24 小时运转的系统来说，这不可接受。

**如何在程序不重启的前提下，做到"换掉一个插件，功能照常可用"？**

### 背景

热更新的难点不在于"加载新 DLL"——第11讲的 `dll_load` 已经能做这件事。
难点在于**旧插件还在系统里**：它的菜单项还挂在链表上、它的状态还在 `STARTED`、
它的 DLL 还占着文件句柄（Windows 下被占用的 DLL **无法覆盖**）、
可能有插件正持有它提供的指针或回调。

直接 `dll_unload` 会立刻制造一片**悬空指针**：菜单指向已卸载的 DLL，
下一次点击就是一次崩溃。这正是本讲 `manager_stop_all()` 必须"摘菜单"的原因——
**挂上去的东西，一定要有摘下来的路径。**

### 思考方向

1. 更新一个插件的完整流程，应该分成哪几个步骤？顺序能不能颠倒？
2. 旧 DLL 在 Windows 上被占用，怎么才能腾出手来替换文件？
3. 如果正在执行 `execute()`，这时把它卸载了会怎样？怎么定义"安全卸载点"？
4. 新版插件加载失败（比如编译坏了），系统应该退回旧版，还是干脆没有功能？
5. `Plugin` 结构体一旦改字段，老插件还能用吗？这在工程上叫什么问题？

### 完整参考答案

**第一步 · 定义"热更新"的五个原子动作，顺序不能乱。**

```
① stop(old)      停止旧插件：停止对外服务
② cleanup(old)   清理旧插件：释放它自己申请的资源
③ menu_remove    摘掉旧插件的菜单项（否则留下悬空指针）
④ unload(old)    卸载旧 DLL（FreeLibrary / dlclose）
⑤ load(new) + register + init + start   加载新版，走完整生命周期
```

关键洞察：**热更新 = "一套完整的卸载" + "一套完整的加载"，中间加一次文件替换。**
所以它能不能做，首先取决于你的框架**有没有干净的卸载路径**。
这正是第13讲坚持把 `stop / cleanup` 从 `init` 里拆出来的长期回报——
拆分当时看不出价值，到了热更新这一刻，它是唯一的抓手。

**第二步 · 解决 Windows 的文件占用问题。**

Windows 下 DLL 被加载后文件被锁，无法直接覆盖。工程上有三种做法：

| 做法 | 思路 | 代价 |
|:---|:---|:---|
| **换名加载** | 新版写成 `transfer_v2.dll`，老版留着不动，只换菜单指向 | 磁盘上堆历史版本，需要清理策略 |
| **先卸后拷** | 严格按第一步 `unload` 后再 `CopyFile` 覆盖 | 中间有短暂的"功能真空期" |
| **影子副本** | 先把新 DLL 拷成临时名，卸载后改名替换，失败可回滚 | 多一次磁盘操作，逻辑稍复杂 |

Linux 下 `dlclose` 后即可覆盖，限制少得多——这也是 `dynamic_loader.c` 那层封装的价值：
**平台差异关在接口里，热更新逻辑本身不用到处写 `#ifdef`。**

**第三步 · 定义"安全卸载点"，别在别人用你的时候拆。**

如果某个线程正在 `execute()` 里跑旧插件，这时 `unload` 会造成指令段被释放，
程序必崩。两种收敛方式：

1. **引用计数**：每次进入插件调用 `ref++`，退出 `ref--`；只有 `ref == 0` 时才真正卸载。
2. **单线程串行化**：所有插件调用都在主线程的菜单循环里发生（本讲就是这种），
   那"卸载"只能由菜单命令触发，天然不会与执行重叠。

本讲项目恰好属于第 2 种——**简单，但只适用于单线程模型。**
一旦引入多线程或看门狗线程，就必须升级到第 1 种。

**第四步 · 失败要能退回旧版，而不是"干脆没有功能"。**

```
新版加载失败（文件损坏 / 缺符号 / init 报错）
        │
        ├─ 有旧版备份 → 重新加载旧版，功能不变，只记一条告警
        └─ 无旧版备份 → 连同内置实现一起启用（第14讲第一部分的四级降级）
```

退路的设计原则和第14讲完全一致：**能力可以退化，体验不能退化。**
用户看到的菜单不应该少一项，最差也应该是"旧功能照常、新版没生效"。

**第五步 · 顺带必须面对 ABI 兼容性。**

`Plugin` 结构体一旦发布，**加字段、改字段顺序、改函数指针签名，都会让老插件错位**：
框架按新布局读，插件按旧布局写，读出来的 `init` 可能指向一段无关的数据。
这一步在工程上叫 **ABI（二进制接口）兼容性**问题。工业框架（如 Redis Modules）的做法是：

1. **版本号 + 校验**：约定一个 `API_VERSION`，加载时先比对，不匹配就拒绝；
2. **结构体只增不减**：新字段一律追加在末尾，旧插件读到的是未填充区域（靠 `sizeof` 判断）；
3. **通过函数取字段**：把访问封装成 `plugin_get_api(h)` 这类函数，替代直接读结构体。

本讲为了教学清晰，结构体是"直接读"的——**这就是下一个真实项目一定会撞上的墙。**

**一句话结论：**

> 热更新不是"加载一个新 DLL"这么简单，它是**卸载 + 替换 + 加载**三件事的完整闭环，
> 而它的技术前提，是框架在很久以前就把"卸载路径"设计干净了。
> **能不能热更新，考验的不是加载能力，是设计的对称性——
> 凡能挂上去的东西，都必须能摘下来。**
